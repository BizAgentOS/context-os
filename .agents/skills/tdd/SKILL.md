# Test-Driven Development(TDD)

TDD 是 red → green 循环。本 skill 是让这个循环产出"值得保留的测试"的参考:什么是好测试、测试放在哪、反模式、循环规则。每个循环都适用。

探索代码库时,若项目有 `CONTEXT.md`(领域词汇表),先读它,让测试名和接口词汇匹配项目领域语言。

## 什么是好测试

测试通过**公共接口**验证行为,不触碰实现细节。代码可以彻底重写,测试不该因此失败。好测试读起来像规格说明——"用户能用有效购物车结账"准确告诉你存在什么能力——并因不关心内部结构而能在重构中存活。

## Seams——测试放在哪

**seam** 是你测试所在的公共边界:在不深入内部的前提下观察行为的接口。测试只在 seam 上,绝不对着内部写。

**只在预先确认的 seam 上测试。** 写任何测试前,先写下要测试的 seam 并与用户确认。未确认的 seam 上不写测试。你不可能测一切——预先约定 seam,才能让测试精力落在关键路径和复杂逻辑上,而非每个边界。

问:"公共接口是什么?我们该测哪些 seam?"

## 反模式

- **实现耦合**——mock 内部协作者、测私有方法、或通过旁路验证(查数据库而非用接口)。特征:重构时行为没变,测试却红了。
- **同义反复(tautological)**——断言用代码本身的方式重算期望值(`expect(add(a,b)).toBe(a+b)`),构造上必然通过,永远不会和代码不一致。期望值必须来自独立真值:已知正确的字面量、算好的样例、或规格。
- **水平切片**——先写完所有测试,再写所有实现。批量测试验证的是*想象中*的行为,测的是形状而非用户行为,且在理解实现前就锁定了测试结构。改用**垂直切片**——一个测试 → 一个实现 → 重复,每个测试是一发响应上一轮反馈的 tracer bullet。

## 循环规则

- **先红后绿。** 先写失败的测试,再写刚好让它通过的最小代码。不预判未来测试,不加投机功能。
- **一次一片。** 一个 seam、一个测试、一个最小实现,为一个循环。
- **重构不在循环内。** 重构属于评审阶段(见 `code-review` skill),不属于 red → green 实现循环。

## 与其他 skill 的关系

- `implement`:构建/修复时在 pre-agreed seams 上调用本 skill,测试先行。
- `code-review`:重构产出的评审由 code-review 负责,不在 TDD 循环内做。
