- 状态：代码与新增恢复/保护回归已通过。实际工作区恢复状态以验收记录为准。

**2026-10-18 续验完成：**星桥基础 v22 与执行模型精确绑定，8/8 结构化来源和 5/5 文档全部处理完成，8 个概念与 8 条关系均 bound；58 条对象、8 条关系及指定业务链查询通过。保留业务冲突与未知项，未发布。

## 2026-10-16 原始问题与后续处理


## 一、直接影响使用

### ISSUE-001 Agent 最终回复漏出英文内部推演，用户看不到答案

**2026-10-17 后续状态：**修复实现完成（未发布）。KodaX 驱动只交付最后一次工具调用后的最终文本；推演标签与准备调用工具的结束语不作为答案。缺失答案时按实际查询/验证回执交付结果，并保留局部覆盖、失败与未形成结论的状态；正常英文答案不被一概丢弃。证据：`runtime-output.test.ts`、`agent-completion.test.ts`。

- 现象：投研问答实测中，最后一条助手消息是“I have what I need… Let me record this as a verification.”，没有中文答案；运行在调用 `ontology_verify` 后正常结束。数据本身正确（SEC001/SEC002，2025 合并营收 120 亿元）。
- 影响：用户拿不到回答，也看不出 Agent 做了什么。
- 方向：宿主在运行结束时确保最后一条面向用户的回复为中文结论；模型中间文本不作为最终回复。

### ISSUE-002 Agent 工作时本体空间整体重建，打开的弹窗被关闭

**2026-10-17 后续状态：**修复完成（未发布），桌面与 390px 窄屏浏览器验收通过。本体场景不再因 busy、requesting、任务轮询整体重建；进度局部更新。管理弹窗挂到独立宿主，打开时读取最新内容，不随场景节点销毁。

- 现象：`web/agent/app.js` 的 `canvasFingerprint` 含 `state.busy`/`ui.requesting` 及整份 foundation/engine 状态，变化即重建 Three.js 场景；“本体定义/实际对象/构建与修订”弹窗挂在场景根节点内一并消失。实测发消息后约 300ms 弹窗关闭，一条消息重建 2 次。
- 方向：只在本体内容版本变化时重建；弹窗移出场景根节点。

### ISSUE-003 采用操作没有反馈，失败原因被遮罩挡住

**2026-10-17 后续状态：**修复完成（未发布），桌面与 390px 窄屏浏览器验收通过。弹窗内显示处理中、成功及错误回执；在途禁用交互，成功后采用按钮不再重复提交。服务返回 canAdopt/adoptionReason，失效候选不显示采用入口，服务端采用时仍重新验证。

- 现象：弹窗内点“采用此执行子集”后无处理中状态；服务端拒绝时错误写入弹窗背后的 `#request-error`（`app.js` `mutate`），玻璃主题遮罩模糊 8px 后不可读；成功时又触发 ISSUE-002 的重建，看不到回执。请求进行中按钮仍可点。服务端会拒绝的候选仍显示采用按钮。
- 方向：弹窗内显示处理中/成功/失败；请求期间禁用；不可采用的候选不显示采用入口。

### ISSUE-004 选中的概念不随消息发送，“引用到对话”常被遮挡

**2026-10-17 后续状态：**修复完成（未发布），桌面与 390px 窄屏浏览器验收通过。当前浏览的基础概念/关系默认成为可取消的输入引用，明确选择的引用优先；解析通过后显示“当前浏览”与版本，发送时冻结。使用输入区实际高度为聚焦卡留出空间，卡片过长可滚动。见[协作补记](AGENT_UI_DESIGN.md#2026-10-17-本体浏览引用与回执)。

- 现象：聚焦概念后不会自动作为对话上下文，只有点“引用到对话”才设置；发送消息后对话记录面板（约 430–460px）盖住聚焦卡片的该按钮（1440/1280/1000 宽度实测）。c9a13ea 使两者完全重叠。
- 方向：当前聚焦对象默认作为对话上下文；调整聚焦卡与对话面板避让。

### ISSUE-005 修正时堆积候选，且不提示用户采用

**2026-10-17 后续状态：**修复实现完成（未发布）。同一 task/execution、同一映射基线的完整映射候选沿同一 ID 形成新版本，旧版本可读；不同用户轮次和已采用模型不被覆盖。结束回复列出本轮尚未采用候选的具体版本与检查/采用入口提示。证据：`agent-candidates.test.ts`。

- 现象：投研修复实测中 Agent 连续生成 3 个修订候选，只有最后一个通过全量检查，旧候选仍留在本体页；Agent 不能采用（设计如此），但也没有提示用户去采用。
- 方向：新候选替代同一任务的旧候选；运行结束时明确提示待采用的具体版本。

### ISSUE-006 已有工作区不会自动迁移到规则构建

**2026-10-17 后续状态：**修复及隔离迁移回归通过（未发布）。按用户决定，规则重建候选移出旧 interpretation 概念、关系及对应映射，diff 列出退出项与历史引用；已是 program 的概念及后续命名/说明修正保留。手动重建先生成候选，检查采用后才更新工作版本；旧定义、映射和发布消费者仍可按原版本读取。没有声称已替用户迁移实际投研工作区。证据：`helix-review-issues.test.ts`。

- 现象：投研工作区 12 个概念均为模型解读（`origin: interpretation`），其中混入了具体公司实例，3 条关系在数据上连不上。新逻辑不会自动替换旧概念，需要用户点“按数据重新构建”，该路径尚未在旧工作区实测。
- 方向：在投研工作区实测重新构建；旧解读概念的保留或清理规则需决定。

## 二、规则构建的边界尚未提示

### ISSUE-007 Helix 拿不准的情况没有进入“待核对”

**2026-10-17 后续状态：**修复及星桥公开样例隔离核查通过（未发布）。普通高基数文本/邮箱的显著重合、实际去冗余路径均进入相关概念待核对；重合不证明同一身份，禁止仅凭邮箱自动跨系统合并。实测 people.email↔users.email 为 12/13，tasks.assignee↔users.username 为 10/10。原“任务→负责人被两跳删除”只是推测，核查发现 assignee 原先不属于键式列，未进入发现；实际去冗余的是 requirements.product_key→products.product_key，经版本表且 5/5 一致。证据：`helix-review-issues.test.ts` 及本轮验收。

- 现象：用星桥样例实测，HR 员工与项目系统账号只能靠邮箱对齐，Helix 只按身份键合并，未合并；“任务 → 负责人”关联缺失，推测被两跳去冗余去掉（未逐行核实）。这些情况都没有出现在待核对中，用户和 Agent 看不到需要补的地方。
- 方向：程序把“大量值重合但未合并的普通列”“去冗余删除的关联”等报告为待核对，交给 Agent 修正。

### ISSUE-008 实体名称为英文表名

**2026-10-17 后续状态：**修复及回归通过（未发布）。英文表名产生包含稳定概念 ID、来源表与具体下一步的命名待核对，不用模型猜测中文业务名。用户通过已有修订流程改名后立即移除过时命名提示，规则重建继续保留已确认的名称。证据：`helix-review-issues.test.ts`。

- 现象：实体名取自表名（如 Requirement、User）。Helix 原版用 AI 补写名称与描述的步骤未移植。
- 方向：由 Agent 修正名称，或规则提供中文命名。
