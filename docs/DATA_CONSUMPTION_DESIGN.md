# 第四页：数据消费与访问治理

2026-09-08，依据用户对四个页面职责的补充。归属 FEATURE_007，状态 Planned；当前运行界面仍是已实现的前三页。本文件记录设计，不代表 API 消费权限已经实现。

## 四页各自回答什么

| 页面 | 核心问题 | 持续形成的内容 |
|---|---|---|
| 企业 | 企业是什么？ | 企业认知初稿：业务、服务对象、职责、目标与关键流程，随对话逐步补充 |
| 数据 | 需要接入什么数据和资料？ | 来源清单、内容、业务用途、接入状态与缺口 |
| 本体 | 如何把资料组织为一致、可使用的企业记忆？ | 概念、身份、关系、业务口径、映射、实例与证据，是产品核心 |
| 数据消费 | 谁在使用企业记忆，可以使用什么，实际使用了什么？ | 调用方、授权范围、接口接入信息和真实访问记录 |

第一页的名称和业务只是启动门槛，后续仍须逐步建立企业理解。第二页包含“为什么接这份资料”，不只展示文件。第三页把企业理解与资料联系起来。第四页使这些记忆能被下游应用和 Agent 受控复用。

来源质量、接入时点与来源追溯由第二页承接；定义一致性和本体变化由第三页承接；第四页聚焦消费方身份、访问范围和审计。安全约束在实际读取路径执行，不能仅放在第四页的界面上。

## 页面怎样形成

保持现有黑白画布、底部单一输入框和渐隐对话。初次提示：“哪些应用需要使用这些企业记忆？”

例如用户说：“让客服助手查询投诉和回访，但不要读取联系方式。”助手根据实际已采用的本体提出可检查的授权范围，画布出现“客服助手”以及它能访问的对象、字段和关系。对实际不存在的对象或字段先说明缺口，不能凭空创建授权目标。用户明确授权后保存，凭据通过专门的受控交付显示，不进入模型上下文或聊天历史。

有消费者后，画布显示企业记忆与调用方的连接。点开一个调用方查看允许访问的内容、启停入口、接入方式和最近实际调用。接口地址和必要的接入参数按需显示；原始执行日志、工具轨迹、无用途的技术统计不进入主画面。

数据消费页可以在本体建立后进入；没有已采用本体时，只能了解或准备接入，不能自动发布数据或签发广泛权限。本体采用不会自动授权任何调用方。

## MVP 只验证一条消费链

一个本地企业空间、两个实验调用方、一组只读对象 API。两类客户端可复用同一脚本，用不同凭据验证各自权限。

1. 登记调用方名称和用途，按当前本体指定可读对象类型、字段及允许的关系。未明确允许的内容不可访问；首轮不提供外部写入。
2. 每个调用方使用独立凭据识别，支持停用/撤销。调用方身份指凭据所属的应用或 Agent；如需识别应用背后的具体员工，另需可靠的员工身份机制，本轮不冒充已实现。
3. 通过真实 API 查询授权范围内的对象；相同请求在另一个没有权限的身份下被拒绝。外部调用不需要启动模型才能执行权限检查。
4. 页面出现真实访问记录：调用方、时间、操作与资源、成功/拒绝及必要原因、所用本体/数据依据。记录不保存完整凭据和不必要的原始返回内容；拒绝请求也不能泄露受限内容。
5. 停用调用方后，下一次请求被拒绝，重启后授权与记录仍然保留。

首轮按对象类型和字段控制读取，关系目标也必须在授权范围内。暂不实现按楼栋/片区等记录级隔离，不作这种权限承诺；需要该能力的场景另行扩展。原始文档与完整来源行默认不向消费方开放，避免通过证据入口取回被限制的字段。若要提供来源内容，必须另有明确范围并检查实际返回。

## 与现有引擎怎样结合

复用本体定义、对象查询和固定来源依据，在外部消费入口加入独立的身份与授权检查。Agent 负责理解配置意图并提出方案，应用服务负责授予、撤销和每次请求的实际校验。凭据按不可逆摘要保存，完整值仅在必要的交付环节提供。

授权绑定已采用的具体本体定义和明确字段清单，不用“允许全部未来字段”的隐式授权。新增字段、关系、模型或来源版本不因变化自动扩大可读范围；一次请求使用一致的本体/来源依据。首轮可固定授权对应的已采用版本，迁移时重新检查权限适用性。

应用自己的管理与预览接口包含完整记忆，不能作为消费端的替代入口开放。原始文件读取、关系展开、证据、集合/统计和错误信息同样受消费权限约束；首轮只开放已经有实际校验的读取操作，其余拒绝。

HTTP 消费入口与后续 MCP 是接入形式，复用同一权限边界；本轮不同时建设所有协议。保持本地实验范围，不部署公网、多租户、企业 IAM、复杂审批、计费或完整数据治理平台。

## 完成时应看见的证据

用户通过对话登记一个真实可用的实验调用方；画布显示明确授权；独立客户端实际读到允许的对象，并被阻止读取范围外内容。关系或证据入口不能绕开限制。调用记录和撤销结果在第四页可查看。仅画出调用方卡片、生成 API Key 或展示模拟日志都不能算完成。
