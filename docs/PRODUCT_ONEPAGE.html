Context OS.产品说明 / 设计与 MVP · 2026.09

用 Agent 构建企业记忆

以本体组织知识，让企业信息被持续维护、共同使用。

Context OS 是企业记忆引擎。Agent 协助理解企业、连接数据、构建本体，将分散信息变成有业务含义、可追溯、可查询的企业记忆，再提供给其他 Agent 和应用使用。

01

Agent 怎么做：执行能力 + 对象工作区

KodaX · 负责执行

通过 SDK 管理模型调用、会话与工具执行循环。Agent 选择下一步，根据工具返回的实际结果继续工作。

NOOA 思路 · 组织操作环境

把企业信息、资料、本体和业务记录组织成有状态的对象，供 Agent 按需读取、关联和执行方法。

用户提出目标→KodaX 驱动 Agent⇄对象工作区执行并返回结果

本体本身可被检查与修订；采用后的定义，决定业务对象的结构与方法。
Context OS 负责保存、检查和版本管理；NOOA 作为对象工作区的设计参考。

02

四步建立企业记忆系统

企业 → 数据 → 本体 → 连接
01
建立企业认知这家企业是什么？

通过问答明确名称、业务、职责和目标。Agent 补问关键缺口，用户纠正，保存可持续完善的企业基础信息。产出：企业画像与业务目标

02
连接企业数据数据从哪里读？

通过 API 或 MCP 连接企业系统，Agent 按授权、按需读取。原始数据保留在原系统，Context OS 保存连接与来源引用。产出：数据源连接 + 可用能力目录

03
构建业务本体数据代表什么？

Agent 结合接口结构与数据样例提出概念、身份和关系，定义业务口径，建立对象到源接口的映射；程序检查，用户确认采用。产出：本体定义 + 数据源映射 + 对象视图

热力示例：投诉 → 处理工单 / 居民回访。
“工单办结”与“供热恢复”分别定义，沿关联查证，避免混为一谈。
04
连接第三方谁可以使用？

对外提供基于本体的只读 MCP / HTTP API。第三方 Agent 按授权查询对象与关系；独立密钥限定读取范围，调用可追踪、可停用。产出：可授权、可复用的企业记忆服务

03

保持连接，持续维护企业记忆

源系统更新→按需读取→检查影响→必要时修订本体

业务数据由源系统维护；本体、映射和权限由 Context OS 管理，定义变化需确认。

连接企业数据，沉淀业务理解，让多个 Agent 共享同一套企业记忆。

实现边界：来源端 API / MCP 接入待开发；现有对外只读接口已实现。
