日期：2026-09-11。范围：T013-01；基于本地 `codex/mvp` 的 `90a8654` 开发，未升级 SDK、未发布。当前企业资料与公开研究路径仍属 T013-02/03。

## 已实现

- 产品运行 Skill `company-foundation-ontology` 由现有 KodaX SkillRegistry 加载；本轮实际加载后，才开放基础候选保存。
- 企业与数据、本体工作区读取同一基础领域服务，保存稳定的成果、概念和关系引用；候选与旧采用版本并存。
- 新证据核对当前任务真实用户消息与连续原话；保存引文副本，不能使用助手消息或改写已存证据。原话可定位不证明模型解释正确。
- 概念与关系按 ID 增量补充，未知和冲突持续保留；解决问题须有本轮新的用户原话。采用阻断未解决冲突，允许明确未知。
- 同主体名称纠正使用显式契约与本轮引文，显示原名→新名，保留成果及概念身份；不同企业不能直接混合。
- 采用绑定具体候选与企业资料版本。自然语言明确决定和按钮使用同一宿主入口；成果、决定消息、回执及页面进度在同一事务提交。
- 无来源可先采用基础含义，始终显示未绑定来源、不可查询对象；不生成消费授权或可执行业务 API。

## 真实模型与浏览器

使用产品原有 **KodaX 0.7.96-beta.2 + DeepSeek / deepseek-v4-flash**，独立临时企业空间 `/tmp/dataengine-foundation-real`，不把测试答案、内部生成器或研究材料送给模型。

第一轮输入：介绍澄川热力主营居民供热、客服受理投诉并派发维修工单，要求整理基础概念和关系，服务区域暂未确定。模型实际加载 Skill、保存企业名与业务、调用领域服务生成 **4 个概念、3 条关系**，并保留服务区域未知；所有概念/关系均带实际用户引文，候选 v1 保存后等待采用。

在浏览器打开原话，采用 v1 得到 v2；第二页可查看同一成果，并仍显示未绑定来源。再通过“让助手补充或修正”发送“服务区域是城北片区”，真实模型保留原 4 个概念、增加服务区域及关系，得到候选 v3；原 v2 仍可展开。原未知项通过 `ev-area` 引用“服务区域是城北片区”标记已补充。

刷新后保留 v3/v2 和引文；390×844 窄屏无横向溢出，可通过键盘展开依据、聚焦采用并用 Enter 提交，得到 v4。桌面与窄屏截图、实时结果存于忽略的 `output/playwright/`，不提交临时凭据、运行数据库或模型日志。

第三轮从画布绑定已采用 v4，明确纠正同一企业正式全称为“澄川热力有限公司”。真实模型先更新企业资料，再带本轮原话的 `identityCorrection` 保存 v5；画布显示“澄川热力 → 澄川热力有限公司”，点击“确认名称纠正并采用”后得到 v6。最终保留同一基础成果 ID、原有 5 个概念 ID 和 4 条关系，第二页再次显示同一已采用结果，仍不可查询业务对象。服务升级重启后继续这一轮，未重新生成原基础。
