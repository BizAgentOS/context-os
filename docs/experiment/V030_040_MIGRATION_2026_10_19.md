# FEATURE_040 分层模型隔离迁移验收（2026-10-19）

## 方法

运行 `node scripts/verification/layered-migration.ts`。三个明确指定的真实工作区先复制到系统临时目录，再打开副本中的 `MemoryStore`、`LiveMemory` 和 `Snapshots`。复制排除模型凭据、来源凭据、运行会话和管理员令牌；没有调用 Agent、外网或真实源服务。

迁移前使用固定 M0 提交 `f446b3b` 中的 `LiveMemory` 与 `fusion` 原执行代码，按工作区已采用的不可变快照读取。迁移后把显式语义层、绑定层及兼容投影持久化为副本内的新模型成果，保留所有原模型 ID 和版本，再用当前服务分别查询新模型和原模型。全量对象按每页 20 条读取，沿每条关系对每个起点对象查询，比较业务对象值、关系值以及原有失败回执。

另对只改实体说明的副本重新迁移，逐项比较绑定与属性 ID。各真实数据库文件（含存在的 WAL / SHM）在运行前后的大小和修改时间一致。脚本退出后临时目录清理完成；`--keep` 可显式保留副本用于排查，`--workspace=starbridge|heating|investment` 可单独复现。

## 040 补充：当前措辞、固定发布与关系纠正

工作版查询和分层读取按稳定 ID 投影当前已采用基础本体的名称 / 说明，不重建绑定或改写原成果版本。实体与关系别名仅作兼容入口，当前规范名称优先；显式类型与概念 ID 冲突时拒绝。新发布保存发布当时的完整分层定义，旧发布与历史消费者继续使用自己的定义；相同 `modelRef` 的两次发布不会因后续改名而互相改变。

公共发布工厂回归先恢复旧行为获得红灯（默认工厂返回“来源已改变”，而非“发布时的名称”），再从真实发布强制计算 `fixedSemantic` 与快照集合。默认 options、`fixedSemantic=false`、空快照及错误当前快照都不能覆盖实际发布；显式实时策略仍固定原语义，并按实时源读取。两工厂通过真实临时 HTTP 来源和不可变快照验证，不在真实工作区创造历史发布。

局部纠正采用同一稳定关系 resolver 贯通查询、提议基线、检查和采用，优先使用 snapshot 或原定义的关系 ID，仅无稳定 ID 的历史记录回退名称 key。名称 A→B→A 后，新采用决定会使之前已检查候选失效；不同关系互换名称不会串用纠正。没有基础本体的旧执行模型也保存生成的稳定关系 ID。候选事实复验固定原定义，真实来源变更仍拒绝旧候选。并发基线与名称交换用公共闭环分别取得红灯再修复为绿灯。


业务对象编号的直接 `id` 与 `where.$id` 入口共用有类型的身份解码；适配器行号不是语义身份时，关联递归先按明确绑定的业务属性过滤，不把原始行号误当复合身份。公共回归覆盖数字型适配器行号与字符串业务键、复合身份目标通过适配器行号列关联、目标列未暴露时明确拒绝；上述失败均先取得红灯再修复。旧单列编辑若携带过时 `fromColumns`，按明确修改的业务字段重新规范列名，复合 / 中间表定义不能被静默降维。
