日期：2026-09-11。T014-02，基线 `1ceeea7`；本地提交见 Git 历史。FEATURE_014 仍在开发，后续概念绑定与多源融合未提前实施，本票未发布版本。

## 交付

第一页增加 BI 指标来源，内容类型独立于 HTTP/MCP 协议。用户查看实际定义，再按显式期间和维度查询；Agent 调用同一 MetricReader 的 metric_describe/metric_query。单位、维度、日/月粒度、时区、定义版本、可加总规则、缺失原因与读取时点随观测返回，查询分页完整性与源数据覆盖分开表达。原知识和记录读取路径保持兼容，指标不能映射为业务明细。

每个获准能力一个 metricId，使用固定的 describe/query 只读合同。定义哈希在查数前后核对，变化要求重读；输入期间和维度在观测请求前验证，响应再次检查期间、维度、数值状态和重复身份。合同与限制见[语义契约](../SEMANTIC_CONTRACTS.md#t014-02-bi-指标定义与观测)。

未知总数且上游每页只给1条时，按第一页→第二页→空页实际续读，不能因短页就隐藏后续资料，也不将最终空页解释为已知完整总数。停止测试先遇到自身等待顺序互锁，调整为启动停止、放行上游、等待停止完成；随后发现停止后还会发出第二次观测请求，增加宿主运行有效性检查后，计数反例由3次变为2次通过。

收尾发现校验库会静默丢弃 `__proto__` 记录键，可能使筛选丢失。公共API反例先出现“应拒绝却成功”，再通过原始键检查明确拒绝；定义、可加总维度、过滤和观测都不支持该保留名，HTTP/MCP定义拒绝也已核验。

## 真实模型和浏览器

独立8897预览与虚构指标源，实际 `@kodax-ai/kodax@0.7.96-beta.2`、DeepSeek `deepseek-v4-flash`，未注入测试driver。任务只说明澄川热力、2026年1月、各站办结率及解释缺失和合计，没有给模型测试答案。

实际事件记录 metric_describe 与 metric_query 成功。模型回答清河站80%，育新站缺失且尚未完成对账；保留月粒度、Asia/Shanghai、版本r1，说明不能把比率相加/取平均作为总体办结率，且办结不表示供暖恢复。本体未新建或修改。模型还调用profile_update保存了用户给出的企业名，并将“供热”作为待确认建议；本次并非所有工具都只读。没有工具失败记录。

模型答复没有逐字复述所有读取元数据；实际readAt和完整覆盖字段以工具回执及页面为准，不声称自然语言回答总能完整保留每个字段。这次运行是开发集成验证，不是模型方法优势评测。

页面通过MCP实际读取定义与观测。输入不对齐的月日期显示错误，更正后用键盘发起查询成功，数值与缺失原因逐项显示；查询结果完整但源数据有缺失的提示并存。桌面和390px窄屏均以实际截图检查，页面和弹窗无横向溢出；宽表在局部容器滚动。HTTP配置与查询另通过浏览器核验。用户8899离线演示保持原状。

## 限制

首轮支持显式指标、字符串维度、日/月粒度及最多366天的日期窗口，不支持任意SQL、厂商专属OAuth、自动单位换算或公式生成。可加总规则由来源声明并做一致性校验，数值和业务真实仍需来源质量治理。

观测仅为本次读取，不建立持久观测库；跨页不能保证同一来源数据快照。查询返回的总数只描述当前条件下的观测结果，不证明企业所有数据齐备。当前未接入本体实例绑定、跨源共同证据或对外指标消费接口。
