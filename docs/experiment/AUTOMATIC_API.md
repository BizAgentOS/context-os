# API 自动本体化

2026-09-17，按用户要求补齐「API 接入后自动本体化」，沿用资料自动构建的单一 KodaX 执行槽。

- 手动配置 HTTP/MCP 记录来源或 OpenAPI 向导保存连接后，按连接 ID/版本持久排队；已有连接启动时补入队列。没有模型时等待，重新连接模型后继续，无需确认/采用。
- 每个 `records` 能力读取最多 3 条真实样本与字段契约。优先复用基础概念；确需新增定义时，以本次实际读取的 API 引文为依据保存并自动采用。企业名称无已有定义或样本依据时不能编造。
- 执行映射覆盖本次连接的全部记录能力，保留已有主来源、字段、附来源和关系；经过现有共同服务再次取样、核对依赖和版本后自动采用。新增附来源在提案和采用时均须有实际唯一匹配；全无匹配、含糊或无法确认时不报告完成。新增数据不自动发布到 MCP 或授予消费者权限。
- 页面单列「API 已本体化并可查询 · x/y 个 API 来源」，与资料数量分开。失败显示原因并可重试；未读完/未映射全部能力、样本为空、读取失败、来源停用、任务停止等均不报告完成。已完成的基础定义可以保留，即使后续映射失败。
- 文档使基础本体版本更新后，自动重建 API 映射引用，保持对象可查询；该重绑轮次不允许修改基础定义，避免来源间反复递增版本。知识、指标能力继续走各自的取证流程，不误当成记录。
- API 依据保存有界样本片段、读取时间、覆盖与契约版本；历史引用能定位，但不声称上游支持历史回放。一般本体投影不输出样本全文。
- 嵌入式服务的 `automaticApi: false` 仅供明确采用手工映射的集成宿主；正常产品默认自动。手工映射/消费验收测试显式使用此设置，自动接入测试覆盖默认路径。

## 验证

应用公共边界覆盖接入即构建并查询真实 HTTP 样本、无确认、引用定位、上游失败与恢复、停用后的迟到结果拒绝、遗漏能力不能完成、文档更新后映射跟随、无模型排队与重启恢复、跨 API 补充字段、全无匹配及采用前匹配失效的拒绝；自动流程不创建消费者。

2026-09-17 实际实例验证：重新连接用户配置的 glm-5.3 后，已有「星桥收银系统」自动进入构建队列。首次模型将执行关系端点填错，被共同语义服务拒绝；补充运行方法中类型名称、字段别名及方向规则后重试，宿主自动采用执行映射，无人工采用。通过 `/api/live/query` 实际读取 3 个门店、6 条销售记录（均完整覆盖），沿「门店记录销售」查询首个门店返回 2 条关联销售。API 状态 `completed 1/1`，基础概念「门店」「销售」均为 bound，其他基础定义仍保留，消费者数据集仍为 0。页面资料 5/5 和 API 进度分别显示，已测量状态行与图谱统计无重叠；消费页显示「已连接业务映射」。

全量 175 项测试、类型检查、前端语法与离线导出通过；追加方法变更后，能力加载与自动 API 的 16 项针对性检查通过。双轴审查提出的恢复原子性和无匹配误报完成问题已修复并复核。

运行方法：自动流程加载 `company-foundation-ontology` 中的 API 模式；同一映射规则另提供为可发现的 `api-ontology-mapping` 方法包。当前实例通过既有 Skill 安装入口注册该方法并刷新目录，更新规则无需再次重启或重新输入模型密钥。
