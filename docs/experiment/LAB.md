# Context OS 本地实验室

T005-01 已交付的浏览型前端：用页面观察实验的步骤和已有产物。界面不会执行本体确认或维护任务。

用户随后明确产品应以 Agent 为主入口。本文描述当前已有实现；新的企业理解、资料接入、辅助建模、报告与记忆维护体验以 [MVP 目标](../MVP.md)为准，尚未实现。后续复用来源、对象和证据查看能力，不把当前浮窗算成主 Agent 产品。

## 启动

在产品仓库根目录运行，Python 3.9+ 标准库，无前端安装或构建步骤：

```sh
python3 scripts/lab_server.py
```

打开 <http://127.0.0.1:8787>。可用 `--port 8788` 更换端口。模型问答沿用服务端环境变量 `DEEPSEEK_API_KEY`，不写进网页或 Git。未配置时仍能浏览资料和保存笔记，问答会提示失败。

## 页面与实际能力

| 页面 | 可以查看或操作 |
|---|---|
| 实验室首页 | 解释三个实验问题、当前阶段与企业样本；打开原始基线结果 |
| 企业空间 | 公司设定、服务网络、当前来源清单；选择 CSV 或 Markdown 查看，分页浏览；从来源跳到概念 |
| 建模流程 | 六阶段的输入、应有产物、检查依据及案例关注点；保存每步的讨论笔记 |
| 概念与关系 | 已有技术试样的类型、关系规则和引文；查看业务口径依据，跳到来源或对象 |
| 对象与证据 | 按类型和关键词找实例；查看属性、关系、数据时点、定义版本和源行，沿关联对象跳转，或将对象交给助手解释 |
| Agent 工作台 | KodaX Runtime 与 NOOA 式访问的目标设计，以及当前已可用/未接入能力 |
| 全局助手浮窗 | 用当前页面、选中步骤/概念/企业资料/对象及近期对话作只读讲解，返回真实模型回复和用量 |

本体是技术试样，旧包中的历史 `pending_confirmation` 状态不构成新的批准请求；页面以当前产品记录标为 `technical_trial`。六阶段流程尚未完整执行。KodaX Runtime、维护修改、正式确认与版本演变均未接入。

## 数据边界

服务优先读取 `data/generated/chengchuan-20260119`；没有该目录时使用版本化固定样本。来源用原检查器验证后读入内存。对象包采用 `data/generated/ontology-v1-preview`，校验清单及哈希，并要求来源快照与当前候选字节哈希都匹配；没有匹配包时显示对象未生成。不会启动新的模型抽取，也不会自动重建本体。

需要完整试样时，先按 [生成说明](GENERATOR.md) 导出 Jan19 快照，再按[本体技术试样说明](ONTOLOGY.md)使用已保存候选 build 预览。更新来源或对象包后需重启服务。服务启动不更改已有来源、对象包或评测冻结。

仅开放明确的静态文件和 API 白名单；不把仓库目录当静态资源服务器。来源预览不包含私有评测、生成历史或未来快照。浮窗默认只有企业说明、步骤与来源目录；选择企业资料后增加该资料（CSV 前20行），对象上下文最多带12条关系，并明确截断。它没有 SQL、shell 或改写工具；这里不是被测 Agent，不计入方法收益。

步骤笔记保存在 `local-state/lab/notes.json`，按步骤原子保存，Git 忽略；刷新可恢复。对话仅在当前页面内存保留，刷新清空。保存笔记不改变步骤状态，不作为语义确认。

## 人工体验路径

1. 在首页了解实验，进入企业空间，选择投诉记录。
2. 点击“关联概念试样”，查看投诉单定义、与楼栋/工单/回访的关系依据。
3. 进入对象，打开 `Ticket:CS-009`，查看原始地址，沿关系进入 `Building:SY-03`，核对源记录。
4. 打开建模流程，逐步阅读输入与产物，写一条笔记保存并刷新确认。
5. 打开浮窗询问当前阶段，或在企业资料页询问该资料记录什么。未配置模型或调用失败时，问题会回填以便重试。
6. 打开 Agent 工作台，确认维护 Runtime 显示未接入。
