## 一、与预期一致的部分

R01（引用候选过期）是真修好了，机制比我原来建议的更干净。`structured-compiler.ts:223` 让每一页请求都先过 `rebase(page.input)`，而 `rebase` 在 `:184-185` 对任何同时带 `targetSourceVersionId`/`targetColumns`/`targetCandidateTypes` 的对象调用 `currentReferenceTypes` 重投语义归属；`structured-references.ts:31-34` 的注释把边界写明了——只重投归属，元组证据与稳定绑定 ref 保持冻结。因为 rebase 发生在 `this.step` 之前，缓存重放走的也是重投后的请求，GPT 说的"缓存重放覆盖"成立。分片路径额外在 `:277` 于身份与定义任务改动候选之后重算了一次 `crossTableReferences`。我顺手核了一个可能的残留：引用循环内每轮 `run` 都会再改 `candidates`（`:243`），所以 `:233` 比对绑定候选用的 `references` 对后续轮次是旧的——但候选 `ref` 是 `fingerprint({source,columns,target,key,role})`、`sourceColumns`/`targetColumns` 都不依赖候选类型，只有 `targetCandidateTypes` 依赖，而它每页都重投，所以这处旧值无害。R01 可以结案。

R02（抽样未匹配语义）的实现是正确的，而且比报告描述更严谨。`referenceDataScope`（`structured-references.ts:13-19`）把完整性定义为"固定版本的已加载量等于声明总量且未触 1000 行上限"，`referenceMatchStatus`（`:20-22`）只在两端都完整时才给 `zero_match`，否则 `sample_no_match`；`relationship-validation.ts:43` 的联合检查用同一套判据，并把 `checks` 与 `checkHash` 留痕。

我重点查了一条可能的假阳性路径：如果声明总量本身是被截断的捕获量，那么"完整加载"会在一张实际更大的表上成立，于是 `zero_match` 又变成错误结论。这条路径不存在——`connected-sources.ts:97` 的 `rowCount` 取 `receipt.rows`，而 `mysql-reader.ts:77` 在超过 `maxRows` 时直接抛错、不形成批次（`:90` 的回执恒为 `complete:true`），所以能落库的原生版本一定是整表。完整性语义是干净的，这一条不必再怀疑。

## 二、R02 做的正是我自己写的第一阶段，第二阶段仍待做

先更正我一处不公平的表述。我最初在对话里把 R02 说成"只改了标签、没按建议做"，这站不住——回查《跨表引用与协调表达力-实现核查》§2.1 的修订动作，我当时写的是两段：一段是"为重叠检查单独加载一份有界样本，或直接下推成 SQL 的 COUNT／EXISTS"，另一段是"**在修好之前**，`rowLimit` 应当报真实值，`zero_match` 在样本量过小时应降级为 `insufficient_sample` 而不是 `zero_match`"。本轮实现的 `sample_no_match` 就是后者，而且做得比我写的细（区分未知覆盖、单侧完整、两侧部分、超限四种情形，并把两端覆盖与实读/参与/匹配数一起留痕）。所以这不是 GPT 自行缩小范围，是我自己给的两段路里的第一段，它按原样执行了。

残留一处字面出入：`structured-references.ts:91` 的 `rowLimit` 仍然报 `REFERENCE_ROW_LIMIT`（1000），不是实际检查量。但它现在身旁就是 `sourceScope`/`targetScope`/`checked`/`targetChecked`，真实数字是齐的，所以"自报不实"这个问题实际消失了，只剩字段命名容易被单独摘出来误读。可以留着，但建议改名为 `rowLimitPolicy` 之类，或在 UI 侧永远与 `checked` 同时呈现。

第二阶段仍待做，差额正好落在本轮要解决的那批列上。

原因在上游供给没有动：`jobs.ts:222` 仍是 `sourceVersion(actor,id,10)`，`native-coordination.ts:14` 再 `rows.slice(0,10)`。于是任何超过 10 行的表，两端都不可能"完整加载"，`complete` 恒为假。证据因此变成单向的：10 行里撞上一次重叠就是真证据（`overlap_observed` 足以证明值域有交集），但撞不上就只剩 `sample_no_match`，等于零信息。而等着被解决的 `create_by`/`update_by`/`user_id`/`role_id` 这类列，恰恰是样本里取值最没有多样性的一批——10 行全是同一个管理员 id 或全为 0，正向证据也拿不到。更麻碎的是，目标表那 10 行是 `ORDER BY ordinal LIMIT`（`table-content.ts:10`）取的头 10 行，证据能不能拿到取决于行序，不取决于数据本身。

好消息是补这个缺口比我上一轮设想的便宜得多，因为我原来担心的两条代价都不存在。整表行就在平台库里——`connected-sources.ts:99` 把 `observation_pages` 整批转进 `knowledge.source_records`，`table-content.ts:8` 的默认上限是 100001 行，取 10 行只是发现阶段的请求参数。所以包含性检查可以在 PostgreSQL 内对冻结版本做一条聚合 SQL（源列集合与目标键列集合做 `NOT EXISTS` 计数），不需要连业务库，不会重演 `connected-sources.ts:77-80` 那种在源库一致性读事务里等全局写锁的问题，也不调用任何付费模型。这是本轮之后单位成本最低、对暂缓数影响最直接的一步，建议作为 R02 的续作登记，而不是让"标注清楚了"结束这个话题。

## 六、三项等我答复的歧义项

验收账 `:13` 写了事件抽取、历史先例学习、自引用筛选在等我的答复。逐项给结论。

**自引用筛选：按名称粗筛确实不行，GPT 的顾虑成立，但我原来的意思更窄。** 合法自关联必须留——`system_menu.link.parent` 这条本来就在暂缓关系清单里，按表粗筛会直接杀掉它。我要排除的只是退化候选：同一来源版本、且源列集合与目标键列集合完全相同（`id → id` 自己指向自己）。精确谓词是 `target.id===source.id && fingerprint(columns)===fingerprint(key.columns)` 时跳过，放在 `structured-references.ts:80` 那层循环里。`parent_id → id` 的 `columns` 与 `key.columns` 不同，不受影响。这条安全且能腾出请求预算，建议做。

**事件抽取：本轮不做，但登记时要写明它的来历，不能登记成一个泛泛的后续愿望。** 它是 2026-10-30 那条定论"模态不能做成互斥五选一枚举、要拆成正交维度：事件/状态、肯定/否定、计划/假设、条件、适用时间"里唯一没有实现的那一维。`contracts.ts:22-24` 现在有 `polarity`、`modality`、`condition`，加上 `comparison` 与双时间，但没有任何"事件/状态"维度，也没有事件作为一等公民的表达。所以准确表述是"定论要求的五维里四维已落地、事件/状态维未落地"，而不是"事件抽取是个新需求"。按这个来历写进规格，后面才不会被当成可选项。

**历史先例学习：这里的歧义主要来自命名，我第五轮 §3.3 已经给过具体机制，不是一个开放问题。** 原文写的最小形态是"把已确认的『列形态 → 目标类型』决定存成一张表，`crossTableReferences` 产出候选时把命中过的历史决定作为一档 `basis`（如 `confirmed_binding_precedent`）附上；仍然是建议、仍然要显式确认"。这件事本身不含任何自动学习，它只是把人已经做过的裁决放回候选排序里，和已实现的 `mapping-reuse.ts` 同一性质。被叫成"历史先例学习"之后听起来像另一回事，于是被归进歧义项——按原文的形态做就不歧义。

**真正不要做的是自动学习，这个方向上没有可借鉴的实现。** auto-ontology 的 README 宣称 Learn 能把使用情况折回本体，但 `sql_attribute_suggester.py:69-118` 的 `_usage_score` 直接 `return 0.0`，是他们自己注释说明根因后刻意不修的已知 bug——即这条链路从未运行过。我方近期站得住的形态只有两件：一是已经实现的已批准映射复用（`mapping-reuse.ts`，全匹配才复用、否则回退模型并把 `reviewed` 清零），二是把人工裁决记录作为候选阶段的提示材料呈现，但不自动改定义。"反馈校正"和"自动学习"是两件事，前者我们有、后者不要在没有可信信号的前提下开工。
