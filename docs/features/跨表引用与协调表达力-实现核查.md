# 跨表引用解析与协调表达力：实现核查

核查对象：工作区未提交的 `structured-references.ts`、`discovery-coverage.ts`、`compact-coordination-schema.ts`（v2）、`compact-coordination.ts`，以及 `structured-compiler.ts` / `structured-profile.ts` / `jobs.ts` 的本轮改动。基线是 `docs/features/结构化语义编译器-借鉴审查.md` 的 §0.1–§0.4 和五步顺序。

核查标准不是"借鉴得像不像 auto-ontology"，而是**目标本身**：企业接入自己的数据，AI 辅助建立对象式本体，自动抽取实体/关系/事件，知识携带证据与双时间，可被人工反馈校正。借鉴只是手段，下面每一条都按这个标准判。

本轮未运行测试、未连数据库、未调模型。结论基于静态阅读。

## 一、已经做到的（不要再动）

**表达力回归修好了，而且修得比我建议的好。** `compact-coordination-schema.ts:31` 的 `additions` 三个通道（types/properties/links）都要求 `reason` 和真实 `sourceColumns`（`:18-21` 的 `provenance`），新增成员随后照样走 `validateDiscoveryEvidence` 的目录校验——绑定对不上就暂缓，不是放行。这正是我在 §0.1 要求的"同样要求理由和来源依据、同样走证据校验"。

比我建议的多出来的两处：`removals`（`:32`）让删除变成显式动作而不是靠遗漏表达；`bindings`（`:7`）允许显式替换来源绑定。两者都带强制 `reason`。

**"遗漏即保留"是一处安全性改进，值得单独表扬。** 旧版 `used.size!==entries.size` 要求每个 ref 恰好出现一次，模型漏掉一个成员就整轮失败。新版 `compact-coordination.ts:82-84` 把未被显式处理的成员按原归属补回（类型补回、属性跟随其最终所属类型、关系重投端点），遗漏的语义从"失败"变成"保留"。配合 `removals` 的显式删除，**"模型忘了说"不再可能变成"静默删除已发布成员"**。这比 auto-ontology 的做法稳健——它那边编译只处理没有 Term 的表，根本不面对这个问题。

**基础本体作为增量输入的成员参与协调**（`structured-compiler.ts:121-126`）。已发布或人工编辑过的成员进入 `candidates`，于是"遗漏不能变成隐式删除"这条在有 base 的情况下也成立。注释写明了意图。

**跨表引用解析的三层分离做对了。** `structured-references.ts:35` 每条候选同时给 `bindingValidity`（声明列是否存在／复合映射未知）、`businessMeaning:'unconfirmed'`、`dataMatch.status`（`overlap_observed`／`zero_match`／`not_checked`），外层再给 `adoption:'requires_explicit_coordination'` 和 `identityMerge:false`。这是 GPT 那条修正的准确落地：值有交集只支持连接可行性，不确认"负责""所属"这类业务含义。

**复合键保持为有序元组**（`:28-32`），`targetColumns` 与 `sourceColumns` 按序配对、整元组比对，没有退化成单列重叠。测试 `structured-references.test.ts:20-27` 覆盖了声明外键的异名复合引用，`:38-43` 覆盖了未声明复合引用只给 `composite_mapping_unknown` 不给数据匹配。候选键来源也按 GPT 的要求扩成三档：主键、唯一键、业务标识候选（`:17-21`）。`mysql-reader.ts:40` 确实读了 `uniqueKeys`，`sources.ts:52` 确实透传——这条链路是通的。

**概念同名的线索给了。** `targetCandidateTypes`（`:33`）把目标来源上已有的候选类型 ID 一起给出，`targetComment`／`columnComments` 给注释。这是我在 §0.36 提的"你说的 `Region` 很可能就是 `type.quyu`"那个形态。

**注释枚举按 GPT 的要求连带改了降级分支。** `structured-profile.ts:66` 新增 `commentCodeCandidates` + `commentBasis:'column_comment_candidate'`，与 `enumBasis:'database_declaration'` 分开记录；`structured-compiler.ts:68-74` 的降级分支不再静默清掉——采用物理标量的同时保留原提议值、原注释、代码候选，并**仍然压入 `constraint` 疑问**。注释写了"Physical scalar adoption does not erase a proposed business dictionary"。这条修得完整。

**取值截断按基数分档了。** `structured-profile.ts:63` 默认给完整 `observedValues`（上限 32）并标 `valuesTruncated`／`valuesCoverage`，只有 `legacy` 路径才 `slice(0,5)`。测试 `:28-36` 验了 8 个值全给、legacy 仍为 5。

**暂缓的读路径接上了。** `discovery-coverage.ts` 的 `publishedDiscoveryCoverage` 被 `service.ts:455` 挂到对象查询结果上，按 GPT 的要求**只关联所选发布版本和精确来源版本**（`released`／`allowed` 两层过滤），并带 `note` 说明"未检查或缺少记录不表示没有业务关系，其他草稿不参与"。§2.1 那个缺口关闭。

**请求负载的分层做了，且保留了全局发现能力。** `structured-compiler.ts:137-183`：先试整包，超 48000 字节才按业务对象拆题；每题带 `globalDirectory`（全局目录每轮重算）；**没有采用候选的来源也单独出题**（`:166-179`，注释写明"absence is never evidence that it has no business relationship"）；最后一道全局覆盖检查（`:180-187`）。拆题是顺序执行、复用现有单 worker 和 `analysis_steps`，没有引入并发写入——GPT 要求的"先不为拆任务引入并发"做到了。超预算时抛错而不是静默截断（`:159`、`:174`、`:184`）。

## 二、真正的缺陷

### 2.1 `dataMatch` 只看了 10 行，却自报 `rowLimit:1000`（高）

`structured-references.ts:30` 的 `tuples` 对 `s.rows` 做 `slice(0,1000)`，`:35` 写 `rowLimit:1000`、`scope:'frozen_loaded_records'`。但上游给进来的 `rows` 最多只有 **10 行**：`jobs.ts:221` 用 `this.core.sourceVersion(actor, id, 10)` 加载，`native-coordination.ts:13-14` 的 `discoverySamples` 又 `slice(0,10)` 一次。

所以 `checked` 永远 ≤10，而 `rowLimit:1000` 是一个**不成立的自报**。更要紧的是 `zero_match` 这个判定：10 行样本上的零重叠几乎没有证据力，而它会被模型当成"这个绑定没有数据支持"的信号。最糟的情形恰好是暂缓列表里最多的那一类——`create_by` 这种列，10 行样本里全是 `0`，与真实用户表零重叠，于是"推测关联用户表"被一个无效的零匹配结论继续压住。

对比 auto-ontology：它的 `prune_disjoint_semantic_fks` 是对**整表**跑 SQL `COUNT`（`semantic_fk.py:103-157`），正因为如此"零重叠即删边"才敢作为硬判据。拿 10 行样本做同样的判断，结论强度完全不同。

修订动作：这个检查不要复用给模型看的样本。`table-content.ts:6` 的 `sourceContent` 本来就支持更大的 limit（默认 100001），为重叠检查单独加载一份有界样本（或直接下推成 SQL 的 `COUNT`／`EXISTS`，按 `ProbeExecutor` 那种只读收口的形态）。在修好之前，`rowLimit` 应当报真实值，`zero_match` 在样本量过小时应降级为 `insufficient_sample` 而不是 `zero_match`——否则这是一个会误导决策的假信号。

### 2.2 `analysisCompletion` 是装饰性字段（中高）

`jobs.ts:264` 写的是 `analysisCompletion:native?'completed':undefined`——只要走原生路径就是 `completed`，**没有任何地方计算它**。而 `structured-compiler.ts:131` 的指令明确要求"任务未全部完成不得报告全局发现完成"，`:183` 的 `coverage:{topics:topics.length,completed:topics.length}` 也是恒等式：把 `topics.length` 赋给 `completed` 再送给模型当事实。

这与"区分分析完成但有待确认候选 / 分析任务尚未完成"（GPT 第四批）直接冲突。拆题路径里任何一题抛错（`:159`／`:174`／`:184`）都会让整个 discover job 失败，所以当前不会出现"部分完成却报 completed"——但这是靠异常传播兜住的，不是靠这个字段。一旦将来允许部分成功，这个字段会立刻开始撒谎。

修订动作：要么真的计算（已完成题数／总题数、未覆盖来源数、是否走完全局覆盖检查），要么删掉。送给模型的 `coverage.completed` 同理——恒等式不该出现在模型输入里。

### 2.3 `referenceCandidates` 在拆题循环里会过期（中）

`structured-compiler.ts:128` 的 `references` 在循环**之前**算一次，而 `candidates` 在 `:162`／`:177` 每轮被 `materializeCoordination` 重写。`globalDirectory` 是每轮重算的（`:136` 的 `directory()` 在 `:158`／`:173` 被调用），但 `references` 里的 `targetCandidateTypes` 不是。

后果：topic 1 把 `Region` 改名／合并成 `type.quyu` 之后，topic 2 拿到的 `referenceCandidates` 仍然宣称目标候选类型是 `Region`。模型同时看到一份新鲜的 `globalDirectory` 和一份过期的候选清单，两者对不上——而端点判断恰好依赖这个对应关系。这正是本轮要解决的那类问题（`Region`/`role`/`user` 的命名不一致）被重新引入的路径。

修订动作：`related` 在每轮用当前 `candidates` 重算 `targetCandidateTypes`（结构部分不变、只重投类型 ID 即可，不必重跑值匹配）。

### 2.4 自引用候选会放大 `alternatives`（中低）

`structured-references.ts:14` 的 `for(const target of sources)` 不排除 `source` 自己。对 `system_menu.pid` 这类自层级是必要的，测试 `:26` 也断言了自引用要保留。但副作用是**每张表的每个身份列都会把自己的主键当成一个候选**，`alternatives` 里多出一条通常无意义的项。14 张表、每表若干身份列的量级下，这会实际占用 48000 字节的预算，进而更早触发拆题。

修订动作：自引用候选保留，但要求额外条件才产出（目标键与源列不同名、或源列名含 `parent`/`pid`/`上级` 这类层级线索），否则跳过。这是纯粹的预算优化，不改变语义。

## 三、与最初目标的偏离

这一节是我认为最需要摆到桌面上的部分。前两节都在说"这一轮做得怎么样"，这一节说"这一轮在做的事离目标有多远"。

### 3.0 更正（2026-11-06）：§3.1 关于"验收用例无测试覆盖"的断言是错的，撤回

用户指出测试只需覆盖新版核心。我据此重查 `tests/knowledge/`，**原断言不成立**：`tests/knowledge/postgres.test.ts:18` 这一个用例就把验收用例走完了，而且是真 PostgreSQL 集成测试。

它实际覆盖的链条（`:41-83`）：结构化来源给出 `contract_amount=1000000.00`；PDF 文档声明 `1200000.00`；同一业务时点查询返回 `status:'conflict'`（`:52`）；`CorrectProperty` 人工修正为 `1300000.00` 且 `disputed:true`（`:59-61`）；**按 `knownAt` 查历史仍返回 `conflict`、按当前查返回修正值**（`:57-60`）——双时间两条轴分别可查；幂等重放同一修正返回同一回执（`:56`）、过期修订被拒（`:62`）；`RejectAssertion` 撤回人工声明后回落到来源值 `1100000.00`（`:70-72`）；限定 `source_version` 范围的修正（`:73-74`）；新来源版本使旧修正过期（`:75-77`）；同一对象修订上的并发修正只能成功一次（`:83`）。

这比我引用的验收用例描述还更完整——它多测了撤回、限定范围修正、过期和并发。所以"声明→冲突→修正→双时间查询"这条路在新版核心里是**有测试的**，不是没走通过。

我错在把"本机没跑过"当成了"没有覆盖"。这个用例是 `{ skip: !url }`，需要 `CONTEXT_OS_KNOWLEDGE_TEST_DATABASE_URL` 才执行，本机无 PG 所以一直跳过——而我上一轮自己记过"7 个真 PostgreSQL 集成测试需设环境变量才跑"，这轮却把 grep 命中的文件名当成了未覆盖的证据。两件事不是一件事。

§3.1 下文里"机制从未被端到端走通过一次"这句作废。仍然成立的部分只有一条，而且弱得多：**这条测试走的是 CSV + PDF 来源，不是本轮新建的 MySQL 原生表链路**——原生表走到声明层的那一段（`observe`/`collect` → 协调 → 计划 → 构建 → 声明）还没有等价的端到端用例。建议补的不是验收用例本身，而是**同一个验收用例换成 MySQL 原生来源跑一遍**，确认新链路汇入的声明与 CSV 路径等价。这是个小得多的增量。

### 3.1 本轮全部产出都在"本体定义"一侧，目标的另一半还没被这条链路碰到（已按 §3.0 大幅收窄）

目标是四件事：对象式本体、自动抽取实体/关系/事件、知识携带证据与双时间、可被人工反馈校正。本轮（以及 11-05 那一整轮）的全部工作量都落在第一件上——而且是第一件里最前端的一段：从 MySQL 的声明结构里辅助生成本体候选。

声明层、`assertion_revisions` 的双时间、`projections` 的融合策略、`evidence` 两张 join 表、Action 这些机制都在，而且按 §3.0 的更正，它们在 CSV + PDF 来源上**是有端到端测试的**。

剩下的偏离是另一件事，范围小得多：**本轮新建的 MySQL 原生表链路还没有走到声明层。** 14 张表最终只采用 1 条关系，而那 1 条还是表内的——所以"原生表 → 跨表关系 → 构建 → 声明"这一段，端到端还没发生过。CSV 路径证明了下游机制可用，不能替代证明新链路能把东西喂到那里。

这不是说本轮方向错了。身份列解析确实是当前最大的卡点，不解决它后面走不动。需要明说的风险只剩一条：**连续两轮都在协调前端做精细化（压缩、拆题、候选解析、注释代码表），而原生表路径一次都没汇入过声明层。** 精细化的收益会在某个点之后迅速下降，而把新链路端到端走一次的信息量极大。

建议：第 2 步（跨表引用解析）跑通、能产出若干跨表关系之后，**把 `postgres.test.ts` 那个验收用例换成 MySQL 原生来源跑一遍**，确认原生链路汇入的声明与 CSV 路径等价（同样产生三条声明、同样展示冲突、同样支持双时间查询）。这比我原来建议的"补一个验收用例"小得多——用例已经有了，要补的只是来源形态。

### 3.2 "自动抽取事件"没有对应实现

目标里"实体/关系/事件"三样，事件这一样在本体定义侧只有 `actions` 枚举（`builtinActions`），在声明侧只有 `action_events` 表。本轮的候选生成只产出 types／properties／links 三类成员，`additions` 通道也只有这三类。模态的四个正交维度（`polarity`／`modality`／`condition`／`comparison`）在声明层有，但本体候选阶段不产出任何事件型成员。

这可能是刻意的分期（先实体关系、后事件），但 `docs/implementation/BACKLOG.md` 的 D1 六项里也没有事件抽取。建议明确记一笔：事件抽取是目标的一部分、当前不在任何工作包里，避免它在一轮轮前端打磨中被默认忘掉。

### 3.3 "反馈校正"目前只有人工决定，没有从校正里学

目标里"可通过外部反馈校正"。现在有的是：人工确认集中事项、`decideIdentityBatch`、Action、`reassessNativeDefinition` 本地重算。这些都是**单次校正**——人改一次、系统照做一次。

没有的是：把校正结果喂回候选生成。同一个 `create_by` 列，操作者这次确认了它指向用户表，下一批新表里出现同名同形态的列时，系统不会因此更有把握。auto-ontology 的 README 把这件事列为四大能力之一（"Learn: fold certified corrections and usage back into the ontology"），而我核过它那边**根本没实现**（`_usage_score` 直接 `return 0.0`，刻意保留的已知 bug）。所以这里没有可借鉴的现成实现，但目标是你们自己定的，不会因为参考项目没做就不需要。

最小形态其实很轻：把已确认的"列形态 → 目标类型"决定存成一张表，`crossTableReferences` 产出候选时把命中过的历史决定作为一档 `basis`（比如 `confirmed_binding_precedent`）附上。仍然是建议、仍然要显式确认，但操作者第二次看到的候选排序会明显更准。这件事做与不做，决定了这个平台是"每次都要人从头确认"还是"用得越久越省力"。

## 四、小结

本轮把 §0.1（表达力）、§0.2（三层分离）、§0.35（注释枚举、身份列解析）、§2.1（暂缓读路径）、§3.1（取值分档）、§3.3（协调依据）全部落地了，而且 `removals`／`bindings`／"遗漏即保留"三处比我建议的更稳健。四个缺陷里只有 2.1 是会产生错误结论的（10 行样本的 `zero_match`），其余三个是自报不实或预算浪费。

需要警惕的不是这些缺陷，而是 §3.1 按 §3.0 收窄后剩下的那一条：验收用例在 CSV + PDF 上有完整测试，但本轮新建的 MySQL 原生链路还没汇入过声明层。建议把"同一个验收用例换 MySQL 原生来源跑一遍"插进第 2 步之后，不要等五步全完。

另外 §3.2（事件抽取无实现）和 §3.3（校正不反哺候选）两条与测试覆盖无关，仍然成立。
