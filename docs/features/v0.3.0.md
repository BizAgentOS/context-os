# v0.3.0：本体闭环、双模式 Agent 与企业数据接入

日期：2026-10-19。计划版本 v0.3.0（MINOR：新的功能批次），基于 v0.2.3 及其后未发布修复（`b02f44f`）。`package.json` 保持最近一次发布的版本，未发布内容写入 CHANGELOG `[Unreleased]`。

## 版本目标与授权

2026-10-19 用户与 Fabric IQ 对照、产品全面体检后确认产品方向，并要求把全部改进定义为一个新的开发版本。目标设计见 [v0.3.0 目标产品蓝图](v0.3.0-blueprint.md)（下文以"蓝图 §章节"引用）；本文负责 Feature 拆分、票、依赖与验收，状态只在[功能台账](../FEATURE_LIST.md)。

**版本目标**：

1. 本体成为显式的分层模型；程序、人、Agent 的结构变化经同一流程复验，由人采用。
2. 所有待决定事项进入一个待处理中心；用户可见的版本只有"工作版"和"发布"。
3. 一个 Agent、构建与问答两种模式；Agent 执行过程、改动与待决定项在面板中可见；问答答案驱动可视化，答不出时经缺口单交接修复。
4. 企业常见数据（Excel、数据库、分页接口）可接入并按周期自动更新，质量异常不静默生效。
5. 清理与新方向冲突的旧路径：旧消费接口、旧提示词、口令采用、界面中的内部数据。

**已定决定**（来源见蓝图 §0）：产品定义 D1—D6、体检决定 R1—R8。蓝图中标【默认】的细节按默认执行，蓝图 §18 所列 10 项可在对应 Feature 开工前调整。

**授权边界**：本文登记范围与拆票，不表示开工。按 [DEVELOPMENT](../DEVELOPMENT.md)，由用户指定 Feature 后改为 InProgress 并实施；不自动执行整份路线。发布版本号与时间由用户确认后按 [AGENTS.md · 版本与发布](../../AGENTS.md#版本与发布) 处理。

**2026-10-19 开发授权补记：**用户本轮要求依据索引文档开始新版本开发，已启动 M0，后续按依赖推进；先前“登记不表示开工”保留为规划当时的边界。

**M0 验收（2026-10-19）：**036—039 的票已完成，证据和限制见[M0 隔离验收](../experiment/V030_M0_2026_10_19.md)。当时没有展开 M1—M4 的实现或发布。

## FEATURE_040: 分层语义模型

### 1. 需求概述
把基础本体、执行模型、附来源、Helix 待核对项四套结构整合为显式分层模型：语义层（实体类型、属性、关系类型）与绑定层（实体绑定、属性绑定、关系绑定），对象有稳定 ID（蓝图 §9）。

### 2. 影响范围
`src/agent/foundation.ts`、`src/live/memory.ts`（`modelSchema`）、`src/live/fusion.ts`（`supplementSchema`）、`src/engine/program-builds.ts`、`src/engine/helix-projection.ts`、发布与消费视图对模型的读取、存量数据迁移。

### 3. 技术方案
- 语义层：实体类型（名称、别名、说明、身份键、kind）、属性（值类型、单位、枚举、是否身份、说明）、关系类型（端点、方向、基数、可自引用、可声明无环、反向名称）。
- 绑定层：实体绑定（主 / 补充、数据集、键列、行过滤）、属性绑定（多源、有限转换 `none/trim/lowercase/cast/parse_date`）、关系绑定（`foreign_key` / `link_table`）。
- 复合身份：身份键允许多个属性；中间表以 `link_table` 绑定为多对多关系。
- 绑定引用语义对象稳定 ID，不引用语义版本号；措辞变化不触发重绑。
- 迁移：现有 concept / type / relation ID 保留为稳定 ID；`fields` 每个键迁移为一个属性与一个属性绑定；supplement 迁移为补充实体绑定（身份规则在 042）；已有发布与消费者按原版本可读。
- 规模上限（20 类型、40 关系、3 附源）保留为配置项，本 Feature 不放开（放开依赖 066 的规模验收）。

### 4. 接口契约
新的模型读取接口返回分层结构；旧接口在过渡期由新模型投影生成，保持外部 v4 兼容。

### 5. 实现步骤
- [x] T040-01（依赖：036）：语义层与绑定层模型、校验与持久化；复合身份与 `link_table`。
- [x] T040-02（依赖 T040-01）：程序构建输出分层模型；查询与融合读取新模型。
- [x] T040-03（依赖 T040-02）：存量迁移（星桥、热力、投研工作区隔离副本）；旧发布与消费者回归。

### 6. 验收标准
星桥工作区迁移后，每个实体、属性、关系有稳定 ID 与业务字段；全部 58 个对象与 8 条关系查询结果与迁移前一致；旧发布消费者读取不受影响；文档补充只改说明时不触发重绑。

## FEATURE_041: 统一变更流程与自动采用规则

### 1. 需求概述
程序、人、Agent 的全部修改走同一条"提议 → 复验 → 采用 / 拒绝"流程；自动采用只限首次构建与同结构重绑（R2）；用户可见版本只有工作版与发布（蓝图 §10）。

### 2. 影响范围
`src/engine/program-builds.ts`（自动采用 209—216 行）、`src/agent/automatic-api.ts`（174 行 `autoAdopt: true`）、`src/agent/app.ts`（快照变化入队 200—204 行）、`src/live/mapping-changes.ts`、关系纠正服务、候选服务、`src/engine/releases.ts`、`release-diff.ts`。

### 3. 技术方案
- 变更对象：来源（程序 / 人 / Agent / 问答）、类型（实体、属性、关系、绑定、身份规则、身份决定、命名、说明、局部纠正、弃用、数据问题确认）、依据、复验结果、影响、状态（proposed / verified / failed / adopted / rejected / deprecated / superseded）。

## FEATURE_042: 关系发现修复与身份对应

### 1. 需求概述
修复 ISSUE-016 的关系发现缺口，引入身份规则（same_as / belongs_to）与记录级身份决定，大表降级改为待确认（蓝图 §9.2、§9.3）。

### 2. 影响范围
`src/engine/helix-discovery.ts`（唯一键分支约 450 行、普通字段候选约 393 行、同表排除约 1082 行、身份合并约 447 行、去冗余阈值约 1033 行、活动流判断 644—670 行）、`src/live/fusion.ts`、`src/engine/program-builds.ts`。

### 3. 技术方案
- 唯一外键：小样本中恰好唯一的外键不再被身份键判断吞掉；空字符串不参与唯一值统计。
- 普通责任字段（如 assignee）全匹配时生成关系提议（proposed），由人采用。
- 自引用关系：允许同表连接；声明无环的关系复验时检测环与最大深度。
- 身份规则：`same_as`（补充来源接主来源）、`belongs_to`（如账号属于人员，产生关系实例，不合并对象）；身份决定 `match / no_match` 覆盖规则，记录依据与决定人。
- 跨系统字符串重合不再自动合并身份，生成 `same_as` 或 `belongs_to` 提议；需要类型相容性检查。
- 两跳去冗余：不再静默删除直接边，改为提议"弃用冗余关系"。
- 活动流：不再静默降级，生成"确认为活动记录"待处理；确认前按普通实体处理。

### 4. 接口契约
复用 041 的变更接口；身份规则与身份决定作为变更类型。

- `identity_rule.subject`：`kind: same_as | belongs_to`、`left/right: { bindingId, columns }`、可选 `transform`、必填 `reason/evidence`；归属规则可指定既有 `relationTypeId`。同一身份可从两个独立主绑定建立补充，保留原对象。
- `identity_decision.subject`：`ruleId`、`left: { bindingId, recordId }`、`right: { bindingId, recordId } | null`、`decision: match | no_match`、`reason/evidence`。空右侧只用于整体排除；服务端记录决定人、时间与复验输入。
- 关系提议可声明 `acyclic`、`cardinality: N:1 | 1:1`、`maxDepth`（最多 10）。去冗余提议带已采用直接关系与两跳端点；活动分类以 `data_issue` 提议。
- 新程序构建只自动采用首次独立实体；本票发现的关系、身份、弃用与活动分类均需明确采用。决定进入工作版、固定发布、消费及历史恢复；旧发布缺字段视为空集。
