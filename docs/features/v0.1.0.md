# v0.1.0 — 本地方法验证实验

## Part A — 版本目标

跑通“虚构企业数据 → 初始本体与对象 → 外部消费 → 内部 Agent 维护 → 新版本与答案变化”，用简单前端和对照结果判断方法的价值。

沿用 [产品目标](../PRODUCT.md)与 [MVP 范围](../MVP.md)。本版本仍采用小样先行、文件或一个轻量数据库、单机单用户、人工确认变更和脚本评测，不扩展为生产平台。

用户已确认采用虚构热力公司，企业案例为澄川热力；沿已登记票据逐项建设。名称、规模和内部规则是实验设定，Runtime 版本和框架仍在对应任务开始时核实。实际交付以任务勾选和验证记录为准。

**版本完成条件：**六项 Feature 交付并通过各自验收、MVP 完成条件有实际记录、实验结论可复核。当前无产品发布；本文件的版本号是开发目标。

**主要验收边界：**用来源生成与导入命令检查数据，通过对象服务和只读 MCP 检查消费，通过维护任务的输入输出和实际版本结果检查演变。先在这些公共边界验证可观察行为；具体测试命令随首段代码加入，不为文档编造已运行测试。

**票据规则：**每张票交付一条可独立检查的路径。依赖满足后才开始；勾选代表实际交付并验证。无需界面的任务用文件或命令演示，数据和对象可用后逐步接入页面。未知实现细节在开工时补齐该设计块。

## FEATURE_001: 虚构企业、原始数据与基线

### 1. 需求概述

构建虚构区域热力公司，围绕投诉关联与供热异常复盘，说明跨源身份、口径和时间问题。先交付企业与固定小样，再完成生成器；在 T001-03 准备约 10—15 道开发/留出问题及原始消费基线。

### 2. 影响范围

当前企业说明在 `docs/experiment/`，固定样本在 `data/samples/chengchuan-heating/`；`config/heating.json` 配置生成参数，`scripts/heating_data.py` 提供生成、导出和变化包，`scripts/validate_heating_sample.py` 检查固定及生成快照。后续增加原始基线入口。批量数据写入 `data/generated/`，评测私有材料写入 `data/private/`，运行结果写入 `runs/`；三者已被 Git 忽略。可复现配置、公开开发题、冻结哈希和评分逻辑进入版本管理；留出题和预期答案不提交。

### 3. 技术方案

固定样本包含 1 个外购热源接入点、2 座换热站、4 个小区、12 栋楼和 14 天记录；保留台账站号、监测标签、客服原始地址，以及办结和回访的不同口径。生成器基于小样补造记录历史，按种子生成新增监测，按配置启用事实、映射和制度变化；依可见时间回放，导出最新行版本和已发布文档。来源快照、未来事件、生成器内部状态与答案分别管理；建模/消费只允许当前 sources 与 manifest，实际 Agent 的运行时隔离在基线前实现并验证。检查涵盖哈希、时间、源引用、面积、合成热量和监测标签有效区间，不直接提供统一对象模型。

### 4. 接口契约

`generate` 输入固定规模的企业案例配置（seed、总天数、三类变化开关），输出作者侧 run.json 与 history.jsonl；`export` 输入作者运行和带时区的截止时点，输出 sources 与 manifest；`diff` 输入前后快照，输出改动文件及 changes.json。快照声明来源 ID、时间范围、列、行主键、记录数、字节数及校验和。命令成功返回 0，非法数据或参数返回非零；已有输出目录不覆盖。变化包包含前后 manifest 哈希和新增/修改/删除路径，不含作者历史。T001-03 的每道问题记录请求时点、公开题面、私有预期及证据要求，评测材料隔离存放。

**T001-02 实现约定：**沿用已确认的命令行生成/导出验收边界，仅用 Python 标准库和本地文件。现有两周小样作为版本化固定起点，补造其创建/派单/完成记录历史；种子控制新增监测，配置控制总天数（14—31 天）和三类变化开关，企业规模固定。生成器工作目录为作者资料；按可见时间导出的 sources 与 manifest 才是后续 Agent 输入。历史记录是实验构造，不声称还原真实系统日志。只实现该案例，不建设通用仿真平台。

**T001-03 实现约定：**沿已有评测命令与工具输入输出边界验收，使用标准库脚本 `scripts/raw_baseline.py`。冻结5道开发题和5道留出题、来源快照、预期字段、人工评分依据、提示与调用预算；每题独立模型会话，只提供当前问题与可见来源导航。原始CSV逐表加载到内存SQLite，不预设实体对齐或业务函数；模型只使用list/read/search/只读sql。凭据通过环境变量提供，真实运行保存答案、证据、API用量、耗时与失败；先机械比对字段和原文，再逐题核查结论支持并标明复核者。原始基线完成以实际运行、输入隔离及可核查记录为准，不要求模型答对全部题，更不代表本体有效。范围和复现方式见[基线说明](../experiment/BASELINE.md)。

**T001-01 验证记录（2026-09-07）：**[企业与实验说明](../experiment/README.md)、[固定样本](../../data/samples/chengchuan-heating/README.md)已交付。`python3 scripts/validate_heating_sample.py` 通过：17 份来源（9 CSV、8 Markdown）、738 条 CSV 记录；验证清单/哈希、时间、引用、面积与监测数量关系。独立复核沿地址、台账、监测、维修和回访核查跨源场景及统计分歧，修正一条维修记录提前描述后续测温的措辞。临时副本的文件篡改、无效站点引用、未来记录、错误热量、未登记来源五类反例均被检查器拒绝。

以上记录对应 T001-01 的固定小样验收，不代表生成器或 Agent 基线验收。

**T001-02 验证记录（2026-09-07）：**[生成与回放说明](../experiment/GENERATOR.md)所列命令已实际运行：作者历史 1,171 个源版本，导出 4 个时点快照及 3 个变化包。9 项 CLI 验收测试通过，覆盖逐字节可复现、历史与发布时间、种子、变化开关、14/31 天范围、快照校验、变化包重建及失败时保护现有数据；`compileall` 语法检查和原固定样本检查通过。只用标准库，无新增运行服务。

**T001-03 验证记录（2026-09-07）：**冻结5道开发题、5道留出题及两个数据时点，以独立DeepSeek会话实际运行10题。6题形成答案、4题耗尽轮次；5题字段及引文机械检查全通过，开发助手逐题复核后4题结论与证据通过，尚无独立人工评分。保存108次调用、输入446223/输出9728 Token及每题耗时。13项自动测试、语法及原样本检查通过。模型工具只读取当前来源内存副本，拒绝任意文件、shell、网络、SQL写入及外连；私有题库/答案/历史不进入模型请求。详见[首跑结果与局限](../experiment/BASELINE_RESULT.md)。

## FEATURE_002: 初始本体与只读数据服务

### 1. 需求概述

让原始数据经辅助本体建设后成为可使用的对象、关系、业务口径和函数，并让外部 Agent 通过只读 MCP 完成真实查询。

### 2. 影响范围

T002-01 已新增 scripts/ontology.py、config/ontology/ 候选/提示/来源记录，以及来源到对象的验收测试和确认摘要。对象包写入忽略目录 data/generated/，真实模型调用记录写入 runs/。查询函数、MCP 和外部消费留到T002-02。

### 3. 技术方案

先接最小模型与工具调用，以来源字段、样本和业务说明产生本体及 Mapping 候选；人工确认业务定义后保存 v1。按规则对齐身份，计算交给确定性函数。采用简单持久化；完整 KodaX 维护 Agent 在 003 建设，避免先后依赖成环。

### 4. 接口契约

来源观测保留来源 ID、时间、权限或访问范围与版本。本体定义类型、属性、关系、口径和函数，Mapping 单独版本化。对象持有稳定引用、事实、关系及证据。只读入口包括 `search_objects`、`get_object`、`traverse_relations`、`get_evidence`、`run_function`、`compile_context`；输出带适用时间与定义版本。

**T002-01 当前实现约定：**先按[建模流程草案](../experiment/ONTOLOGY_MODELING.md)设计业务任务、资料观察、概念候选、语义审查、映射与实例化、任务与反例验证。每阶段保留输入、产物、依据和未决项；不强制每表一个概念。现有提取脚本与9类对象为来源到对象的技术试样，可复用导入和追溯能力；只有流程实际执行、关键决定有记录、实例可支撑任务后才讨论正式v1。当前不请求批准旧试样。

### 5. 实现步骤

| 完成 | Ticket | Title | Blocked by | What it delivers |
|---|---|---|---|---|
| [ ] | T002-01 | 来源到初始本体与对象 | T001-03 | 导入来源，产生有依据的本体/Mapping 候选，确认后形成 v1 对象；可从对象追溯原始记录 |
| [ ] | T002-02 | 函数、MCP 与外部消费 | T002-01 | 外部 Agent 实际调用对象和计算接口回答问题，返回证据和版本，重启后结果仍可复现 |
| [ ] | T002-03 | 专用表与静态本体对照 | T002-02 | 从同样的清洗与身份对齐结果建立专用表参照，保存初始问题的两组结果及建设投入 |

### 6. 验收标准

- 初始本体来自可见业务依据，不能用评测标准本体冒充抽取结果；争议口径允许待确认或分别定义。
- 查询、聚合和关系结果可检查来源及计算定义；普通数据更新能更新对象。
- 外部 Agent 真正通过 MCP 消费，不读取内部建模过程的答案草稿；专用表与本体的证据及数据条件可比较。

**T002-01 当前验证记录（2026-09-07）：**两次真实模型调用（初次抽取和来源校验反馈后的修订），输入33185、输出7198 Token，调用实测耗时合计38.148秒；另有明确记录的开发助手整理，未伪装成零干预抽取。9类对象、9类关系、两项指标定义形成待确认候选。已生成738个对象、731条关系；8项无匹配记录是来源中确实缺少回访/测温，没有补造记录。本体/Mapping、完整可见来源和对象包已持久化，CLI get/evidence实际运行。18项测试、语法和原样本检查通过；原始基线冻结未改动。候选字段错误、引文伪造、未来来源、篡改、地址/有效期、空值和确认哈希绑定均有验证。

**用户纠偏后的状态：**上述产物降为历史技术试样，撤回直接批准请求；剩余工作包含建模任务、概念身份与粒度设计、语义审查及任务/反例验证，并非只差人工盖章。后续按[本体建模流程草案](../experiment/ONTOLOGY_MODELING.md)推进。T002-01 仍未完成，FEATURE_002 保持 InProgress。

## FEATURE_003: KodaX 与 NOOA 式维护 Agent

### 1. 需求概述

建立一个实际运行的内部 Agent，按需理解当前数据环境、调查问题并提出候选修改。复用 KodaX Runtime，借鉴 NOOA 的对象引用、类型化方法和受限代码组合。

### 2. 影响范围

拟新增 Runtime 适配、对象工具、维护任务与运行记录；复用 002 的来源、对象、函数及证据能力。运行结果保存在 `runs/`，模型凭据通过本地配置提供。

### 3. 技术方案

开工时核对 KodaX 仓库、版本和现有接口。内部和外部 Agent 隔离会话与工具范围。传递对象引用并按需取字段、关系和证据；受限代码只能调用数据工具。先输出候选建议，正式应用由 004 接入。

### 4. 接口契约

任务输入包含问题、可见来源或对象引用、当前本体版本。工具覆盖来源画像、本体描述、对象读取和函数调用。输出包含调查结论、证据引用、修改候选、理由与预期影响；运行记录保留真实调用和错误。

### 5. 实现步骤

| 完成 | Ticket | Title | Blocked by | What it delivers |
|---|---|---|---|---|
| [ ] | T003-01 | 真实 Runtime 的对象调查 | T002-02 | KodaX Agent 使用对象引用按需查证一个问题，输出可追踪的调查结果 |
| [ ] | T003-02 | 类型化工具与候选修改 | T003-01 | Agent 在受限工具环境中组合查询和验证，针对 Mapping 或语义缺口提出有证据的结构化修改 |

### 6. 验收标准

- 有实际 Runtime 和工具调用记录，模拟回复或固定脚本不能代替 Agent 集成。
- 能追踪建议的来源与适用范围；证据不足时保留不确定性。
- Agent 不读取评测答案，不直接操作正式存储或发布版本；候选建议可以被后续维护流程接收。

## FEATURE_004: 本体演变与结果恢复

### 1. 需求概述

把 Agent 的候选修改接入简单检查与人工确认，保存新版本、重算相关结果，并能恢复旧版本的结果，验证维护实际价值。

### 2. 影响范围

拟新增候选变更保存、验证、确认应用、版本与结果恢复入口；复用 002 的数据服务和 003 的 Agent。保留变化输入与结果记录，不建设复杂审批或并发合并系统。

### 3. 技术方案

以文件或轻量存储保存基础版本、变更和证据。检查类型、引用、口径及原有问题；错误建议返回原因。人工确认后保存新版本并重算。旧输入、Mapping、本体及函数版本一起保留，使结果恢复可验证。

### 4. 接口契约

ChangeSet 包含基础版本、修改操作、理由、证据与状态；检查输出通过项、失败项及影响。应用输入包含人工确认与通过检查的变更，输出新版本及重算结果；恢复入口指定旧快照与定义版本。

### 5. 实现步骤

| 完成 | Ticket | Title | Blocked by | What it delivers |
|---|---|---|---|---|
| [ ] | T004-01 | 候选建议到确认应用 | T003-02 | 实际建议通过检查与人工确认成为新版本，错误建议被拒绝，外部查询能看到更新结果 |
| [ ] | T004-02 | 变化回放、回归与恢复 | T004-01 | 分别处理事实更新、Mapping 变化、本体或口径演进，重跑目标及原有问题，并恢复旧版本结果 |

### 6. 验收标准

- 至少一次真实本体或口径变化得到应用，普通实例更新不计作本体演进。
- 修改前后输入、定义、证据与答案可对照；未确认建议不成为正式事实。
- 原有问题有回归记录，旧版本能够恢复实际查询结果；记录一次人工修复参照与 Agent 维护投入。

### 3. 技术方案

## FEATURE_006: 对照实验与规模验证

### 1. 需求概述

用可复核的对照判断数据组织、本体复用和 Agent 维护各自的贡献；用同一生成规则扩展数据，检查超过上下文后的按需访问。

### 2. 影响范围

拟新增统一实验运行与汇总入口，复用 001 的问题/生成器、002 的基线与服务和 004 的变化记录；结果保存在 `runs/`，总结进入 `docs/experiment/`。005 负责显示，不作为脚本运行的依赖。

### 3. 技术方案

比较原始资料、专用表、静态本体、动态本体四组；普通 RAG 仅作可选参照。相同原始信息、计算能力、请求身份、数据时点和预算；各组都可收到正常事实增量。允许专用表适配新问题并记录成本。分别分析初始题、未参与调试的新组合题和变化后题，不用停更系统制造维护优势。

### 4. 接口契约

实验配置声明数据集、模型、问题划分、可见输入、预算和版本。每题记录答案、证据、正确性、Token、时间及错误；维护记录人工与模型投入。规模报告标明同一案例的实际 Token 数与 Tokenizer。
