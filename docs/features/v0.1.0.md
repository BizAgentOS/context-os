## FEATURE_001: 虚构企业、原始数据与基线

### 1. 需求概述

构建虚构区域热力公司，围绕投诉关联与供热异常复盘，说明跨源身份、口径和时间问题。先交付企业与固定小样，再完成生成器；在 T001-03 准备约 10—15 道开发/留出问题及原始消费基线。

### 2. 影响范围

当前企业说明在 `docs/experiment/`，固定样本在 `data/samples/chengchuan-heating/`；`config/heating.json` 配置生成参数，`scripts/heating_data.py` 提供生成、导出和变化包，`scripts/validate_heating_sample.py` 检查固定及生成快照。后续增加原始基线入口。批量数据写入 `data/generated/`，评测私有材料写入 `data/private/`，运行结果写入 `runs/`；三者已被 Git 忽略。可复现配置、公开开发题、冻结哈希和评分逻辑进入版本管理；留出题和预期答案不提交。

### 3. 技术方案

固定样本包含 1 个外购热源接入点、2 座换热站、4 个小区、12 栋楼和 14 天记录；保留台账站号、监测标签、客服原始地址，以及办结和回访的不同口径。生成器基于小样补造记录历史，按种子生成新增监测，按配置启用事实、映射和制度变化；依可见时间回放，导出最新行版本和已发布文档。来源快照、未来事件、生成器内部状态与答案分别管理；建模/消费只允许当前 sources 与 manifest，实际 Agent 的运行时隔离在基线前实现并验证。检查涵盖哈希、时间、源引用、面积、合成热量和监测标签有效区间，不直接提供统一对象模型。

### 4. 接口契约

`generate` 输入固定规模的企业案例配置（seed、总天数、三类变化开关），输出作者侧 run.json 与 history.jsonl；`export` 输入作者运行和带时区的截止时点，输出 sources 与 manifest；`diff` 输入前后快照，输出改动文件及 changes.json。快照声明来源 ID、时间范围、列、行主键、记录数、字节数及校验和。命令成功返回 0，非法数据或参数返回非零；已有输出目录不覆盖。变化包包含前后 manifest 哈希和新增/修改/删除路径，不含作者历史。T001-03 的每道问题记录请求时点、公开题面、私有预期及证据要求，评测材料隔离存放。

**T001-02 实现约定：**沿用已确认的命令行生成/导出验收边界，仅用 Python 标准库和本地文件。现有两周小样作为版本化固定起点，补造其创建/派单/完成记录历史；种子控制新增监测，配置控制总天数（14—31 天）和三类变化开关，企业规模固定。生成器工作目录为作者资料；按可见时间导出的 sources 与 manifest 才是后续 Agent 输入。历史记录是实验构造，不声称还原真实系统日志。只实现该案例，不建设通用仿真平台。

**T001-03 实现约定：**沿已有评测命令与工具输入输出边界验收，使用标准库脚本 `scripts/raw_baseline.py`。冻结5道开发题和5道留出题、来源快照、预期字段、人工评分依据、提示与调用预算；每题独立模型会话，只提供当前问题与可见来源导航。原始CSV逐表加载到内存SQLite，不预设实体对齐或业务函数；模型只使用list/read/search/只读sql。凭据通过环境变量提供，真实运行保存答案、证据、API用量、耗时与失败；先机械比对字段和原文，再逐题核查结论支持并标明复核者。原始基线完成以实际运行、输入隔离及可核查记录为准，不要求模型答对全部题，更不代表本体有效。范围和复现方式见[基线说明](../experiment/BASELINE.md)。

## FEATURE_003: KodaX 与 NOOA 式企业主 Agent

### 1. 需求概述

用户希望从一个 Agent 入口建立企业理解、接入资料、辅助构建本体、查看报告并持续维护记忆。现有浮窗只能解释预载资料，不能主动建立企业空间或调用工具推进工作。

主 Agent 的职责是围绕用户当前业务目标，建设、使用并维护可复用的企业记忆。每项任务明确问题、范围与交付条件，按“查证或提问 → 对象操作 → 检查与保存 → 继续或结束”推进。用户能纠正、暂停和继续，不必填完企业问卷才能开始工作。

本体、KodaX 与 NOOA 式对象 harness 共同构成 DataEngine。以 KodaX SDK 为执行底座，本体的概念、实例、关系、口径与证据形成主 Agent 可操作的对象环境。每段工作保存可独立查看的成果，关键判断展示依据和备选。[Agent 设计方案](../archive/AGENT_BLUEPRINT_2026-09-07.md)定义组成、配置及应用契约；[行为设计](../archive/AGENT_DESIGN_2026-09-07.md)定义协作、连续对话、完成条件与技术依据。

### 2. 影响范围

增加主 Agent 宿主与 SDK 适配、企业空间的成果持久化和类型化数据工具；复用既有来源读取、对象导入/证据能力。FEATURE_005 负责主对话、模型设置、上传和当前成果视图；002 负责业务建模与实例能力；004 承接后续修改应用与演变。

2026-09-07 已交付主 Agent 实现；2026-09-08 按[企业记忆画布](../archive/CANVAS_DESIGN_2026-09-08.md)新增 T003-04，将执行改为每页一个有界上下文。旧设计中的任务仅保留为内部运行记录。后续企业理解与首份资料接入不等待正式本体或完整 MCP，本体对象操作仍属于首轮核心范围。

### 3. 技术方案

- KodaX SDK 管理模型、会话和执行；DataEngine 定义工作方法、企业对象与保存规则。直接消费 SDK，不另写模型调用循环，也不引入第二套 NOOA Runtime。
- Agent 配置、KodaX Runtime、任务宿主、对象工作区和企业记忆构成单个本地应用；上下文装配是任务宿主的职责。使用统一身份说明和五张简短方法卡，不另设意图分类模型。
- 一个主 Agent 使用理解企业、接入资料、辅助建模、调查报告、维护记忆五种工作方法。先处理用户最新指令/纠正，再读取已有成果、执行不受歧义影响的工作；只在目标相关缺口无法由资料解决时补问 1—2 个问题。
- 首轮只有一个活动任务，保存目标、范围与交付条件、成果/版本引用、已完成事项、未决项、等待问题和下一步。任务采用进行中、待补充、已暂停、已完成四种状态，单次运行失败或结束不等于任务完成。
- 停止时保留已成功成果，继续时重新读取状态与相关版本；临时追问不丢失原目标，明确换目标才暂停旧任务。每次任务结束交代成果、依据/范围和阻塞，不自动开始可选下一项。
- 读取、计算、检查及保存草稿/报告在当前授权范围内直接执行；普通明确编辑和既定映射刷新无需重复确认。首次采用本体、改变关键业务语义或无法解决的冲突，先展示具体候选和影响，再取得关联该版本的用户决定。
- 企业理解、来源、建模草稿等工作对象支撑空白企业启动；业务本体形成后，其概念与实例通过统一适配层成为可发现的类型和对象。关系返回相关对象集合，已实现口径绑定确定性方法，身份、时间和证据随对象保留。
- 当前目标需要跨来源身份、关系或统一口径，且已有相关来源与初步观察时，即可提出本体候选，无需等企业画像全部完成。已有正式定义时优先操作对应对象，缺口才回读原文或提出修订；原始资料摘要可直接交付，不强行建模。
- 首轮 MVP 将验证一段对象方法组合执行，包含关系访问、一个语义方法和证据读取。CodeAct 或受限组合接口留待行为设计评审后的接入验证，当前不预定执行器；不能把 SDK 工具注册等同于已经打通 NOOA live objects。跨进程使用引用，进程内持有对象/代理。
- 同一企业跨会话共享可持久解析的成果引用。KodaX 会话与企业长期知识分别管理；模型假设、用户陈述、来源记录与确认定义保持可辨识。
- 初始上下文仅包含企业/任务摘要、相关成果引用和能力导航，详细内容通过类型化工具按需读取。统计由程序执行，分页与样例不冒充全量结果。
- 首版每次启动/续接通过 SDK 的 runs.start 显式绑定当前上下文与对象能力；若有旧运行，先停止、等待其结束并核对成果，超时保持暂停，不并发新开。运行内通过对象结果反馈变化，不假定尚未验证的逐模型调用上下文钩子或 submitInput 工具继承规则。
- 每次任务绑定来源和定义版本；报告保留其依据。更新产生新版本与差异，旧报告可标记待刷新；引用失效明确显示。
- 首轮一个企业、单用户、串行修改、本地文件与轻量存储。SDK 工具注册、执行范围和 Python 数据能力复用的实际接法见主设计中的源码核对，不把隐藏工具当作执行权限保证。

**Out of Scope：**当前实现已按用户要求启动，范围以 T003-01/02/03 为准。首轮 MVP 保留小型对象执行验证，不复制 NOOA 的完整运行时或通用代码执行平台，不增加多 Agent 调度、全天候自动维护、图数据库、通用连接器平台、外部完整 MCP 或大规模方法评测。SDK 接入与文档设计都不自动证明业务准确率。

### 4. 接口契约

以下是 DataEngine 的领域契约：

- 任务输入：企业/会话引用、用户目标、范围/时点、预期交付、选中成果、可用来源范围及版本。目标清楚时简述后直接执行；选中成果提供指代对象，不自动改写目标。
- 任务续接：保存工作记录与真实成果引用，不保存模型内部推理作为业务状态。用户消息、会话内资料提交或明确继续触发推进；重新打开只展示现状，不自动重算或采用候选。
- 读取能力：空间概览、由本体形成的类型说明与对象视图、字段/关系/证据、已注册语义方法；对象或集合可继续组合操作，跨进程返回引用、版本、总数与分页状态。
- 候选能力：保存企业理解草稿，登记已上传资料及解析结果，提出概念/映射、检查实例预览、保存报告与修改建议。
- 成果输出：稳定 ID、种类、版本、状态、依据和创建/修改来源；前端按成果引用读取，不从模型自然语言推断保存成功。
- 完成判断：交付已保存/可读取、范围与证据可检查、必要检查通过，且达到约定目标；允许未知的证据调查可形成有限结论，但不能自行把要求具体核实的任务降为缺口说明。未满足时保留部分成果并待补充。
- 修订与预览：新推断与用户已编辑内容冲突时保留原陈述并追加未决项；检查通过仍为候选，采用具体定义版本后才用于正式对象查询。候选报告明确标为预览。
- 应用边界：业务定义和重要修订绑定具体候选、基础版本、必要的用户决定与程序检查。普通用户明确编辑和既定映射的数据刷新可在既有授权内完成；Agent 自填确认标记不能替代用户决定。
- 失败边界：解析/模型/工具错误返回具体状态，保留已成功产物；重复请求避免重复写入，过期候选重新检查后才应用。
- 模型凭据由设置或服务端提供，不作为企业资料；Agent 工具只能访问当前企业允许的数据。原始文档中的操作指令不能改变工具范围。

**应用契约：**提交消息、提交资料、提交具体决定、停止运行、读取任务/成果、订阅任务事件，输入输出见[设计方案](../archive/AGENT_BLUEPRINT_2026-09-07.md)第 6 节。任务、KodaX 会话、运行与成果分别标识。Agent 的任务控制动作只包括保存工作摘要、请求用户补充和请求完成；宿主核查实际成果/等待项后推进任务，SDK 运行结束不直接变成任务完成。接受补充/完成请求后关闭本 Run 的业务操作入口，只允许收尾；拒绝时返回缺少条件并继续执行。

**对象与保存契约：**本体定义本身可检查/修订，已采用定义又决定业务接口；关系返回可继续操作的对象或集合。Agent 写入在提交事务内核对运行有效性和任务/成果基础版本，使用操作标识去重。采用新定义前准备并检查对象视图，成功后切换有效引用；正在等待该决定的任务同步更新快照与修订，按原目标继续，不要求重复确认。其他任务按明确请求迁移；在新运行中重建工作区，不混用旧中间句柄。采用失败保留原模型和阻塞。

**事件契约：**SDK 事件说明执行活动，DataEngine 的成果提交/待决定/任务变化事件驱动业务视图。成果先提交，再返回引用并刷新界面；应用事件使用任务范围单调序号，SDK 会话游标仅作来源信息。重连先读带当前位置的状态快照，再补后续事件；游标失效则重取快照。事件重放不重新执行业务写入，应用事件名不冒充 SDK 原生契约。

首条接入先使用 Markdown/文本与 CSV；外部 API 需要真实连接器和授权，无法仅凭自然语言实现任意系统接入。主对话通过真实执行事件展示进度，企业理解、原文、概念/映射、报告与差异在右侧显示。

### 6. 验收标准

**User Stories：**

1. 作为首次使用者，我可以从对话或上传公司资料开始，让 Agent 主动补问一个目标并保存企业理解初稿。
2. 作为企业用户，我可以查看、修改并重新打开企业理解，下一次会话能沿用已保存内容。
3. 作为资料提供者，我可以接入第一份文件，查看原文、解析状态、接入摘要及缺口；失败可以修正后重试。
4. 作为建模参与者，我可以查看概念/关系/口径的依据、备选与映射实例，在关键歧义处作出明确决定。
5. 作为业务使用者，我可以查看 Agent 操作的同一本体对象、关系和证据；Agent 通过对象方法组合查询/计算，产生有证据的简易报告。
6. 作为记忆维护者，我可以补充资料或纠正理解，检查影响并保存更新，后续回答使用新版本，旧结果保留原依据。
7. 作为使用者，我能区分执行中、等待补充、失败和完成，看到已经保存的成果；未实现能力和假设不会伪装成事实。
8. 作为任务发起者，我可以明确目标和交付，Agent 先查已有资料、完成可执行部分，只在真正影响目标的缺口处提问，完成后停止。
9. 作为使用者，我可以暂停、纠正和继续任务，重新打开时看见成果与待办，不重复写入成功成果，也不会因临时追问丢失原目标。

**Testing Decisions：**沿已约定的“用户任务 → 实际工具执行 → 成果/证据读取 → 保存并重开”公共边界验收，复用现有来源与对象验证。设计阶段使用连续对话、对象调查轨迹和工作时序检查；实现阶段的自动与真实模型验收见[运行记录](../experiment/AGENT.md)。实现后首段必须包含真实 KodaX 模型/工具运行；可控响应只用于错误、取消、版本冲突和重复请求等确定性测试，不替代真实连通验证。

沿本体对象接口实际展开至少两种关系、组合一次语义计算并取证，前端和 Agent 对象 ID/版本一致。从热力的一条记录链检查身份、时间与语义，至少覆盖办结不等于恢复、缺失回访、样例不代表全量、未确认建议不成为正式定义。检查当前企业与私有评测/未来数据的工具边界。一次运行成功或结构校验通过不代表本体建模质量已得到全面验证。

同一条体验再检查直接上传启动、缺口补问、暂停/继续及不重复保存；补充资料后发起第二项任务，验证先前定义被复用、纠正影响后续行为、旧证据仍可回查。最终展示真实工作记录与成果差异，不为本轮建立新的大规模评分体系。

契约验证还需覆盖：用户纠正后的迟到写入被拒绝；采用失败保留原模型；新运行重新绑定当前对象能力；工具结束/SDK 运行结束不伪造业务提交与任务完成；重连展示不重复执行。

**实现记录（2026-09-07）：**采用固定 KodaX SDK 0.7.96-beta.2、原生三栏工作台和受限对象组合。用户任务、来源、企业理解、本体检查/采用、对象关系/方法、报告、任务恢复与版本编辑已接通。实际模型与公开行为验证、错误和限制见[运行记录](../experiment/AGENT.md)。完整 NOOA Python Runtime、外部连接器及方法对照仍不在本次实现范围。

## FEATURE_004: 本体演变与结果恢复

### 1. 需求概述

把 Agent 的候选修改接入简单检查与人工确认，保存新版本、重算相关结果，并能恢复旧版本的结果，验证维护实际价值。

**首轮取用范围：**完成一次资料补充或企业理解纠正后的记忆更新，展示依据、差异和保存结果；不把这次更新自动计作真实本体演变。完整三类变化、回归、恢复及人工维护对照留到后续。

### 2. 影响范围

拟新增候选变更保存、验证、确认应用、版本与结果恢复入口；复用 002 的数据服务和 003 的 Agent。保留变化输入与结果记录，不建设复杂审批或并发合并系统。

### 3. 技术方案

以文件或轻量存储保存基础版本、变更和证据。检查类型、引用、口径及原有问题；错误建议返回原因。人工确认后保存新版本并重算。旧输入、Mapping、本体及函数版本一起保留，使结果恢复可验证。

### 4. 接口契约

ChangeSet 包含基础版本、修改操作、理由、证据与状态；检查输出通过项、失败项及影响。应用输入包含人工确认与通过检查的变更，输出新版本及重算结果；恢复入口指定旧快照与定义版本。

### 5. 实现步骤

| 完成 | Ticket | Title | Blocked by | What it delivers |
|---|---|---|---|---|
| [ ] | T004-01 | 候选建议到确认应用 | T003-02 | 实际建议通过检查与人工确认成为新版本，错误建议被拒绝，外部查询能看到更新结果 |
| [ ] | T004-02 | 变化回放、回归与恢复 | T004-01 | 分别处理事实更新、Mapping 变化、本体或口径演进，重跑目标及原有问题，并恢复旧版本结果 |

- 至少一次真实本体或口径变化得到应用，普通实例更新不计作本体演进。
- 修改前后输入、定义、证据与答案可对照；未确认建议不成为正式事实。
- 原有问题有回归记录，旧版本能够恢复实际查询结果；记录一次人工修复参照与 Agent 维护投入。

## FEATURE_007: 数据消费与访问治理

### 1. 需求概述

用户要求第四页负责数据消费：谁通过 API 使用企业记忆、允许读什么、实际调用了什么。延续画布与对话创建方式，复用本体对象。详细范围见[第四页设计](../archive/DATA_CONSUMPTION_DESIGN_2026-09-08.md)。本项状态 Completed；第四页与消费 API 已实现，类型检查、35 项 Agent 测试与 22 项 Python 测试通过，真实模型、浏览器及两个客户端的消费链验收完成。

### 2. 影响范围

复用 `src/agent/` 的本体与对象服务；`consumption.ts` 提供消费身份、授权和访问记录，`server.ts` 提供独立消费与管理入口，`app.ts` 将第四页接入有界上下文。`web/agent/` 展示调用方与具体范围，`config/agent/canvas.md` 限定本页可用能力。`tests/agent/consumption.test.ts` 与 `consumption-canvas.test.ts` 验证真实 HTTP 与页面状态。已有企业记忆与冻结样本保留。

### 3. 技术方案

首轮一个本地企业、两个实验调用方，按已采用本体的对象类型、字段及关系限制只读访问。每个调用方使用独立凭据，支持撤销；程序逐次核验，Agent 辅助解释和配置，不能凭自然语言回复代替权限执行。

调用方、授权和访问记录本地持久化；凭据摘要保存，完整值不进入模型上下文。授权限定明确的本体版本与字段，新增定义不自动扩大权限。消费接口和完整记忆管理入口分开；来源原文默认不开放。关系、证据、集合及错误输出也受同一授权边界控制。

首轮不做外部写入、记录级区域隔离、公网部署、多租户、完整 IAM 或治理平台。第一版 HTTP 与后续 MCP 复用消费边界，不重复建设两套授权。

### 4. 接口契约

实现对象：调用方（身份、名称、用途、启停）、授权（调用方、已采用本体版本、允许的对象类型/字段/关系）、访问记录（调用方、时间、操作与资源、结果及必要原因、数据依据）。身份由凭据校验得到，不相信请求自报的调用方名称。

管理入口支持登记调用方、明确授权、交付凭据、撤销和查看记录；消费入口只执行授权范围内的对象读取。用户明确授权才生效，本体采用不自动开放访问。管理凭据不得交给消费方；调用日志不保存完整凭据或不必要的原始返回内容。消费入口为 `GET /v1/objects`，只接受调用方 Bearer 凭据。`/api/canvas` 返回第四页的调用方及真实记录，`POST /api/consumers/activate` 对当前待确认版本启用并单独返回一次凭据，`POST /api/consumers/revoke` 停用具体版本。上述管理入口以及既有 `/api/objects` 预览均需要管理鉴权。首开使用本机启动链接，浏览器保留 HttpOnly 管理会话。

## FEATURE_009: 第三方 Agent 接入与数据发布

### 1. 需求概述

用户要求构建好的本体能够被第三方 Agent 正式消费，并问接入后数据能否持续变化。第四页提供接入配置与读取范围，清楚区分事实数据更新和本体定义修改。首轮使用本地 MCP 桥接及已有 HTTP API，采用显式检查/发布，不自动读取未经检查的最新文件。

2026-09-08 名称调整：第四页对外称为“连接”，四个导航为“企业 · 数据 · 本体 · 连接”。导航、页面标题、返回入口与管理提示统一使用新名称；内部标识和接口保持原契约。浏览器实测导航与页面标题、JS 语法及差异检查通过，本次仅调整文案。

### 2. 影响范围

`src/agent/consumption.ts` 增加许可结构发现、来源版本预览与单调用方发布；`server.ts` 增加管理接入配置/预览/发布入口；`app.ts` 支持从已启用范围生成独立的待确认草稿。`scripts/dataengine-mcp.ts` 通过标准 MCP stdio 暴露只读工具，复用 HTTP 消费授权。第四页按需展示配置、更新及真实调用。

### 3. 技术方案

一个企业空间，每个 Agent 使用独立消费凭据。MCP `describe_memory` 发现允许的业务对象和关系，`query_objects` 实际调用相同 HTTP 查询。结构发现同样鉴权，不附带未授权字段、源映射或原文。配置里的消费密钥为占位符，完整值只在用户确认启用后单独交付。

消费授权的本体版本与可读范围不变；管理员预览所绑定本体使用的最新映射 CSV，检查列、对象身份、关系与最新来源限制，再明确发布给一个调用方。语义文档继续保持本体采用时的证据。数据发布保存新的消费数据版本，原凭据继续读取新数据。查询可传 `dataVersion` 固定预期版本，发布后若版本不同返回冲突，防止多次查询无感混用前后结果。旧响应和验证记录不变；尚未消费的最新原始文件不会自动外流。

首次独立接入复用一个已启用调用方的明确范围，显示名称、用途与只读字段，生成草稿后仍需用户启用。新草稿从已采用本体的保存数据起步，可再检查数据更新；不能由客户端提交额外 grants 越权。现有连接和密钥不被替换。

### 4. 接口契约

- 消费 `GET /v1/schema`：凭据对应的类型、字段、关系、本体与数据版本。
- 消费 `GET /v1/objects`：原参数加可选 `dataVersion`，仍为类型/字段/关系授权的只读查询。
- 管理 `GET /api/consumers/connection`：本机 MCP JSON 模板、HTTP 地址和本地范围说明，不返回完整密钥。
- 管理 `POST /api/consumers/prepare`：`templateId/templateVersion/name/purpose`，生成独立待启用草稿及当前待确认引用。
- 管理 `POST /api/consumers/data-preview`：`id/version`，返回准确来源版本变更和检查结果。
- 管理 `POST /api/consumers/data-publish`：`id/version/sourceVersions`，仅发布刚确认且仍有效的准确版本集合。

## FEATURE_014: 分类来源接入与多源语义融合

### 1. 需求概述

已接通 API/MCP 并不等于数据融合。当前在线类型只映射一个来源，知识文档、BI 指标与同实体多源属性尚未统一处理。本功能使已建立的概念可以连接真实来源，并形成有依据的业务对象与关系。

### 2. 影响范围

统一来源目录、文档/指标/记录适配、基础概念到可执行映射的绑定、身份解析、融合查询与证据、Agent 对象方法及第一页预览。保持已有只读来源与 v1/v2 消费兼容。

### 3. 技术方案

来源内容类型与传输协议分开，三类内容分别检查。首轮知识源支持获准查询/分段读取；BI 支持明确指标、维度、粒度、单位和期间；记录源复用现有 HTTP/MCP 能力。使用独立可控源作为实现验收，不宣称兼容所有厂商。

基础类型可有零个或多个来源绑定，只有检查通过的执行子集对外可用。首轮用主来源枚举业务对象，附来源按已采用业务键补属性，零/一/多匹配分别返回缺失、融合、歧义或明确关系。唯一匹配须确认匹配范围完整，分页截断或失败时返回未确定状态。不做无界全源并集。每个值、关系和计算结果记录最小出处与读取信息，保留冲突，单位转换和映射需有确定实现。

文档以片段证据关联概念或对象；BI 结果以指标观测关联维度对象/集合，禁止将聚合行当明细或忽略可加总性。对象方法支持有界 describe/query/related/evidence，沿现有受限调用适配到 KodaX；完整 CodeAct 非前提。

### 4. 接口契约

来源描述提供内容种类、获准能力、输入/结果契约和时间/证据能力。映射包含目标概念、主/附来源、身份键、属性与关系规则、检查依据及版本。查询返回稳定引用、逐字段来源、覆盖/匹配状态、冲突及各源读取时点。参数、分页、展开和并发均有界；未执行过滤或无法覆盖时不返回伪全量。

### Part B：设计与实现

1. **需求与范围**：增加自定义 API、OpenAI/Anthropic 兼容协议、Base URL、模型 ID、API Key；复用保存/连接测试。不是任意 REST API，也不增加独立 Agent 循环。
2. **用户交互**：仅自定义时显示协议/URL；明确 OpenAI 通常填含 /v1 的根地址，Anthropic 自动追加 /v1/messages；不填完整生成路径；选厂商、改地址或协议后提示重新核对密钥，禁止把旧端点密钥自动发给新地址；自定义请求不跟随重定向。
3. **服务合同**：管理 HTTP 验证 http(s) URL，拒绝凭据、query/fragment 与完整生成路径。保存非秘密设置；凭据按 URL/协议隔离并仅驻留进程环境，返回结果不含密钥。既有厂商不受影响。
4. **运行接入**：KodaX 公开 registerModelProvider 注册，复用原生兼容 provider 的消息/工具序列化；仅覆盖客户端 fetch 以拒绝重定向；每次执行按当前完整配置选择 provider。测试与聊天共用 driver，保留工具/权限边界。
5. **预先沿用的验收边界**：管理 HTTP、实际独立 HTTP 服务与浏览器。无付费调用的协议夹具通过真实 KodaX transport 检查地址、路径、模型和凭据；配置重启、地址切换/无钥阻断、非法 URL、错误隐藏、两种协议与前端可见性。
6. **限制**：单个当前自定义配置；兼容性取决于上游协议/工具能力，基础连接成功不证明全部业务能力。没有保存密钥到文件、公开发布或新 SDK 升级。
