# v0.1.0 — Agent 企业记忆体验与能力档案

## Part A — 版本目标

首轮跑通“Agent 建立企业理解 → 接入资料 → 辅助构建本体 → 使用记忆生成简易报告 → 维护记忆”，让用户完整体验产品思路。方法对照和规模能力保留为后续目标。

以更新后的 [产品目标](../PRODUCT.md)与 [MVP 范围](../MVP.md)为准。仍采用小样、文件或轻量数据库、单机单用户和关键语义人工确认；首轮以可检查的真实体验验收，完整脚本对照随后开展。

用户已确认采用虚构热力公司，企业案例为澄川热力；保留已登记能力与历史记录，按体验主线重排未完成工作。名称、规模和内部规则是实验设定，Runtime 版本和框架仍在对应任务开始时核实。实际交付以任务勾选和验证记录为准。

**首轮体验完成条件：**MVP 中从企业理解到记忆更新的条件有实际运行记录；不再以六项 Feature 全部完成作为首轮门槛。下方保留能力分工、原票与历史成果；未完成的扩展项不因缩小首轮范围而变成完成。当前无产品发布，发布范围另以实际交付登记。

**主要验收边界：**从用户发起任务到读取实际产物、查看证据、保存并重新打开记忆，沿来源与对象的现有公共接口检查；原有测试继续复用。外部 MCP 和完整演变对照保留在后续票中，不能成为主 Agent 首次体验的前置门槛。

**票据规则：**勾选仍代表历史实际交付。主 Agent 设计已见 FEATURE_003；下一步重排未完成票，拆出首次进入、企业理解及首份资料的完整体验；不直接按旧票的完整方法实验依赖开工，也不把本文设计记作功能完成。

## FEATURE_001: 虚构企业、原始数据与基线

### 1. 需求概述

构建虚构区域热力公司，围绕投诉关联与供热异常复盘，说明跨源身份、口径和时间问题。先交付企业与固定小样，再完成生成器；在 T001-03 准备约 10—15 道开发/留出问题及原始消费基线。

### 2. 影响范围

当前企业说明在 `docs/experiment/`，固定样本在 `data/samples/chengchuan-heating/`；`config/heating.json` 配置生成参数，`scripts/heating_data.py` 提供生成、导出和变化包，`scripts/validate_heating_sample.py` 检查固定及生成快照。后续增加原始基线入口。批量数据写入 `data/generated/`，评测私有材料写入 `data/private/`，运行结果写入 `runs/`；三者已被 Git 忽略。可复现配置、公开开发题、冻结哈希和评分逻辑进入版本管理；留出题和预期答案不提交。

### 3. 技术方案

固定样本包含 1 个外购热源接入点、2 座换热站、4 个小区、12 栋楼和 14 天记录；保留台账站号、监测标签、客服原始地址，以及办结和回访的不同口径。生成器基于小样补造记录历史，按种子生成新增监测，按配置启用事实、映射和制度变化；依可见时间回放，导出最新行版本和已发布文档。来源快照、未来事件、生成器内部状态与答案分别管理；建模/消费只允许当前 sources 与 manifest，实际 Agent 的运行时隔离在基线前实现并验证。检查涵盖哈希、时间、源引用、面积、合成热量和监测标签有效区间，不直接提供统一对象模型。

### 4. 接口契约

`generate` 输入固定规模的企业案例配置（seed、总天数、三类变化开关），输出作者侧 run.json 与 history.jsonl；`export` 输入作者运行和带时区的截止时点，输出 sources 与 manifest；`diff` 输入前后快照，输出改动文件及 changes.json。快照声明来源 ID、时间范围、列、行主键、记录数、字节数及校验和。命令成功返回 0，非法数据或参数返回非零；已有输出目录不覆盖。变化包包含前后 manifest 哈希和新增/修改/删除路径，不含作者历史。T001-03 的每道问题记录请求时点、公开题面、私有预期及证据要求，评测材料隔离存放。

**T001-02 实现约定：**沿用已确认的命令行生成/导出验收边界，仅用 Python 标准库和本地文件。现有两周小样作为版本化固定起点，补造其创建/派单/完成记录历史；种子控制新增监测，配置控制总天数（14—31 天）和三类变化开关，企业规模固定。生成器工作目录为作者资料；按可见时间导出的 sources 与 manifest 才是后续 Agent 输入。历史记录是实验构造，不声称还原真实系统日志。只实现该案例，不建设通用仿真平台。

**T001-03 实现约定：**沿已有评测命令与工具输入输出边界验收，使用标准库脚本 `scripts/raw_baseline.py`。冻结5道开发题和5道留出题、来源快照、预期字段、人工评分依据、提示与调用预算；每题独立模型会话，只提供当前问题与可见来源导航。原始CSV逐表加载到内存SQLite，不预设实体对齐或业务函数；模型只使用list/read/search/只读sql。凭据通过环境变量提供，真实运行保存答案、证据、API用量、耗时与失败；先机械比对字段和原文，再逐题核查结论支持并标明复核者。原始基线完成以实际运行、输入隔离及可核查记录为准，不要求模型答对全部题，更不代表本体有效。范围和复现方式见[基线说明](../experiment/BASELINE.md)。

## FEATURE_003: KodaX 与 NOOA 式企业主 Agent

### 1. 需求概述

用户希望从一个 Agent 入口建立企业理解、接入资料、辅助构建本体、查看报告并持续维护记忆。现有浮窗只能解释预载资料，不能主动建立企业空间或调用工具推进工作。

以 KodaX SDK 为唯一执行底座，提供同一个企业主 Agent；借鉴 NOOA 的对象化状态、类型化方法及按需展开。每段工作保存可独立查看的成果，关键判断展示依据和备选。完整设计与官方源码依据见[主 Agent 设计](../AGENT_DESIGN.md)。

### 2. 影响范围

增加主 Agent 宿主与 SDK 适配、企业空间的成果持久化和类型化数据工具；复用既有来源读取、对象导入/证据能力。FEATURE_005 负责主对话、模型设置、上传和当前成果视图；002 负责业务建模与实例能力；004 承接后续修改应用与演变。

先交付企业理解与首份资料接入，不等待正式本体或完整 MCP。当前仅完成设计，尚未新增可运行能力；FEATURE_003 保持 Planned。

### 3. 技术方案

- KodaX SDK 管理模型、会话和执行；DataEngine 定义工作方法、企业对象与保存规则。直接消费 SDK，不另写模型调用循环，也不引入第二套 NOOA Runtime。
- 一个主 Agent 使用理解企业、接入资料、辅助建模、调查报告、维护记忆五种工作方法。根据当前目标及可用资料选择下一步，每轮优先处理 1—2 个实际缺口，可跳过已经能从资料获知的问题。
- 企业理解、来源、建模草稿、报告、修改建议是预先定义的工作对象；换热站、投诉、回访等业务概念由后续本体建模形成。企业本体以结构定义与映射保存，不为每个概念生成并部署代码。
- 同一企业跨会话共享可持久解析的成果引用。KodaX 会话与企业长期知识分别管理；模型假设、用户陈述、来源记录与确认定义保持可辨识。
- 初始上下文仅包含企业/任务摘要、相关成果引用和能力导航，详细内容通过类型化工具按需读取。统计由程序执行，分页与样例不冒充全量结果。
- 每次任务绑定来源和定义版本；报告保留其依据。更新产生新版本与差异，旧报告可标记待刷新；引用失效明确显示。
- 首轮一个企业、单用户、串行修改、本地文件与轻量存储。SDK 工具注册、执行范围和 Python 数据能力复用的实际接法见主设计中的源码核对，不把隐藏工具当作执行权限保证。

**Out of Scope：**本轮不复制 NOOA 的完整 CodeAct/live-object Runtime，不增加多 Agent 调度、全天候自动维护、图数据库、通用连接器平台、外部完整 MCP 或大规模方法评测。SDK 接入与文档设计都不自动证明业务准确率。

### 4. 接口契约

以下是 DataEngine 的领域契约：

- 任务输入：企业/会话引用、用户目标、选中成果、可用来源范围及版本。
- 读取能力：空间概览、类型说明、来源/对象的有界查询、字段/关系/证据、固定计算；返回引用、版本、总数与分页状态。
- 候选能力：保存企业理解草稿，登记已上传资料及解析结果，提出概念/映射、检查实例预览、保存报告与修改建议。
- 成果输出：稳定 ID、种类、版本、状态、依据和创建/修改来源；前端按成果引用读取，不从模型自然语言推断保存成功。
- 修订与预览：新推断与用户已编辑内容冲突时保留原陈述并追加未决项；检查通过仍为候选，采用具体定义版本后才用于正式对象查询。候选报告明确标为预览。
- 应用边界：业务定义和重要修订绑定具体候选、基础版本、必要的用户决定与程序检查。普通用户明确编辑和既定映射的数据刷新可在既有授权内完成；Agent 自填确认标记不能替代用户决定。
- 失败边界：解析/模型/工具错误返回具体状态，保留已成功产物；重复请求避免重复写入，过期候选重新检查后才应用。
- 模型凭据由设置或服务端提供，不作为企业资料；Agent 工具只能访问当前企业允许的数据。原始文档中的操作指令不能改变工具范围。

首条接入先使用 Markdown/文本与 CSV；外部 API 需要真实连接器和授权，无法仅凭自然语言实现任意系统接入。主对话通过真实执行事件展示进度，企业理解、原文、概念/映射、报告与差异在右侧显示。

### 5. 实现步骤

2. 作为企业用户，我可以查看、修改并重新打开企业理解，下一次会话能沿用已保存内容。

6. 作为记忆维护者，我可以补充资料或纠正理解，检查影响并保存更新，后续回答使用新版本，旧结果保留原依据。

## FEATURE_004: 本体演变与结果恢复

### 1. 需求概述

把 Agent 的候选修改接入简单检查与人工确认，保存新版本、重算相关结果，并能恢复旧版本的结果，验证维护实际价值。

**首轮取用范围：**完成一次资料补充或企业理解纠正后的记忆更新，展示依据、差异和保存结果；不把这次更新自动计作真实本体演变。完整三类变化、回归、恢复及人工维护对照留到后续。

### 2. 影响范围

拟新增候选变更保存、验证、确认应用、版本与结果恢复入口；复用 002 的数据服务和 003 的 Agent。保留变化输入与结果记录，不建设复杂审批或并发合并系统。

### 3. 技术方案

以文件或轻量存储保存基础版本、变更和证据。检查类型、引用、口径及原有问题；错误建议返回原因。人工确认后保存新版本并重算。旧输入、Mapping、本体及函数版本一起保留，使结果恢复可验证。

### 4. 接口契约

ChangeSet 包含基础版本、修改操作、理由、证据与状态；检查输出通过项、失败项及影响。应用输入包含人工确认与通过检查的变更，输出新版本及重算结果；恢复入口指定旧快照与定义版本。

### 5. 实现步骤

| 完成 | Ticket | Title | Blocked by | What it delivers |
|---|---|---|---|---|
| [ ] | T004-01 | 候选建议到确认应用 | T003-02 | 实际建议通过检查与人工确认成为新版本，错误建议被拒绝，外部查询能看到更新结果 |
| [ ] | T004-02 | 变化回放、回归与恢复 | T004-01 | 分别处理事实更新、Mapping 变化、本体或口径演进，重跑目标及原有问题，并恢复旧版本结果 |

### 6. 验收标准

- 至少一次真实本体或口径变化得到应用，普通实例更新不计作本体演进。
- 修改前后输入、定义、证据与答案可对照；未确认建议不成为正式事实。
- 原有问题有回归记录，旧版本能够恢复实际查询结果；记录一次人工修复参照与 Agent 维护投入。

## FEATURE_005: 简单本地工作台
