## 零、2026-11-06 补充：GPT 反馈后的更正与优先级调整

GPT 对本文件提出三处收紧，并报告了一处我漏掉的回归。经代码核实，**它对我错的地方有两处，我的表述过重有两处，优先级需要按它的建议调整。**

### 0.1 我漏掉的回归：协调阶段无法新增跨表关系（最高，应先于本文件所有条目）

`compact-coordination-schema.ts:5` 把协调输出的成员引用限定为 `^[tpl]\d+$`，`materializeCoordination`（`compact-coordination.ts:72-91`）只从 `plan.types`/`plan.links` 组装结果，且每个引用必须恰好出现一次（`:92` 的 `used.size!==entries.size` 失败即关闭）。**协调阶段没有任何字段可以表达"新增一个逐表阶段不存在的成员"。**

要点在于：信息是给足了的。`coordinationReferences`（`compact-coordination.ts:12-20`）送的是**带 ref 的完整逐表候选**，模型在协调阶段能看到所有表的类型定义，具备提出跨表关系的全部依据——只是输出 schema 没有留下说出来的通道。这是纯粹的表达力回归，不是信息不足。

旧的 v16/v6 路径没有这个限制：`structuredDiscoveryModelSchema('coordinate')`（`structured-model-boundary.ts:11-24`）接受完整的 types/links 数组，模型可以直接产出新成员。所以是 v18/v8 这一轮（工作区未提交的 `compact-coordination*`）收窄掉的。当前新任务一律走 `references-v1`（`structured-compiler.ts:118` 无条件设置，`structured-model-boundary.ts:86` 拒绝其他值），旧通道只在重放已存任务时可达。

后果链条：跨表关系在逐表阶段必然带着 `source_binding` 疑问（`discovery.ts:217-221`，端点类型不在本表候选里），进而落入 `deferredIds`（`discovery.ts:329`）。协调阶段**可以**用 `resolutions` 解除该疑问、用 `changes.from/to` 改写端点——前提是**某个逐表阶段先提出过这条关系**。而逐表阶段只看得见一张表，`compactCoordinationInstructions`（`:124`）又明确要求"不为补齐端点虚设新对象"，所以实践中这条关系大多根本不会被提出。这很可能是 147 个暂缓成员里相当一部分的真实成因，比我在 §3.4 推测的兜底机制更直接。

修订动作：协调输出 schema 增加一个显式的"新增成员"通道（新类型/属性/关系），新增成员同样要求 reason 和来源绑定、同样走 `validateDiscoveryEvidence`；未修改成员继续只回 refs，不要为了这个通道放弃压缩收益。

### 0.2 GPT 对关系验证的调整，比我的原建议正确

我在 §3.2 建议"零重叠则降级为 `source_binding` 暂缓项"。GPT 指出：列存在不证明关系成立，但**值重叠也不证明业务含义正确**；零重叠应标记为"当前映射未获支持"并检查数据范围、编码转换等原因，不能直接否定业务关系定义。

这是对的，我的原建议混淆了两件事。auto-ontology 直接删边是合理的，因为它的"关系"**就是** JOIN 路径本身，没有独立的业务语义层；而你们的 link 是业务语义定义，零重叠只说明"这个来源绑定在当前数据上无法验证"，不说明"这个业务关系不存在"。正确做法是按 GPT 的三层分开记录：业务含义、来源绑定、当前数据匹配。这也与 auto-ontology 自己的 `modeling.md` 要求（观测/计算/结构/建模/预测/推荐/承诺七类证据必须区分）一致——我引用了那条纪律，却在自己的建议里违反了它。请以 GPT 的版本为准，§3.2 的"降级为暂缓"一句作废。

### 0.3 我表述过重的两处

**"147 个暂缓成员完全没有读路径"过重。** 本文件 §2.1 正文确实写了 `plans.js:397` 的 JSON 倾倒，但"完全没有读路径"这个说法掩盖了它。准确表述是：**缺少可读、可按范围定位的业务呈现**。另外 147 来自 `work/current-review-reassessment-report.json` 这份离线纯重算报告，不等于当前线上状态——GPT 这一条完全正确。

**"截断是枚举阻断的成因之一"证据不足。** 经核实 `structured-profile.ts:60-62`：`enumValues` 来自 `declaredEnum(c.type)`，解析的是物理类型字符串，**从不被截断**；`slice(0,5)` 只作用于 `observedValues`。而 `structured-compiler.ts:65` 的校验比对的是声明 ENUM，不是观测值。所以对有 ENUM 声明的列，截断根本不参与那条阻断路径。截断真正损害的是**没有 ENUM 声明、需要人工确认业务枚举**那一类列的决策质量——这仍然要修（§3.1 的修订动作不变），但"枚举阻断的成因"这个因果我撤回，需要真实输入输出验证。

### 0.35 第三轮：147 个暂缓的实际成因分布（我和 GPT 都猜错了）

GPT 要求把"新增关系受限／成员暂缓／来源全部跳过"分开统计，不能当成同一个故障。这个要求正确，而且可以现在就算——`work/current-33-review.json` 就是那份 33 项审核事项的草稿快照。我按暂缓原因做了归类：

| 数量 | 成因 |
| --- | --- |
| 57 | 级联（依赖的类型已暂缓） |
| 50 | **跨表身份引用但无声明外键** |
| 17 | 枚举闭合性（多数是列注释已声明取值、样本未覆盖） |
| 12 | 其他 |
| 9 | 样本覆盖不足 |
| 2 | 逗号分隔多值 ID 列 |

成员类别分布：类型 7、属性 129、关系 11。`source_binding` 疑问共 30 条，其中真正是"关系端点尚未在本次候选中定义"的只有 **2** 条。

**所以协调新增关系这条回归最多只能解释 147 里的 11–13 个，不是主要成因。GPT 这一条完全正确，我的归因撤回。** 它仍然是必须修的功能回归（表达力缺失是硬的），但不要指望修完它暂缓数就大幅下降。

真正的大头是第二类，50 个：`create_by` / `update_by` / `delete_by` / `user_id` / `role_id` / `fensuo_id` / `quyu_id` 这类指向用户表、角色表、分所表的身份列，**MySQL 里没有声明外键**，于是逐表阶段只能说"指向哪个实体未知"，协调阶段也没有任何机制去解析它。原因样本：

> `create_by` 为整数，推测关联用户/人员ID，但缺少外键声明，指向对象未知
> `user_id` 与 `role_id` 指向的目标表未在本源中声明，目标实体绑定需跨源协调
> 该表角色菜单两端实体的具体表及键结构未声明外键，跨源身份暂缓

这正是 auto-ontology 的 `semantic_fk.py` 整个模块存在的理由，也是我在首轮分析里写进"值得借鉴"但**没有检查你们是否借了**的一项：声明 FK 走快路径，**没有声明 FK 时才是重点**——嵌入列上下文、在语义向量库里检索相似的列属性、让 LLM 挑候选、LLM 弃权时用样本值跑只读探针验证（`semantic_fk.py:5-24, 466-598`）。你们完全没有这一层。

~~所以每一个无声明外键的身份列都必然永久暂缓。~~ 这句按 GPT 第一条修正收回：协调的 `resolutions` 通道可以解除 `source_binding` 疑问（`compact-coordination.ts:35-44`），属性本身可以作为标量被采用，所以不是"必然永久暂缓"。但解除疑问**不会把标量属性变成关系**——"身份列成为关系"这一步仍然卡在表达力上。两件事各管一段，都成立。

这应当是一项独立工作（GPT 已收为第二批，并要求它**提前参与协调、而不是最后追加的补丁**——这个判断对，见 §0.36）：它不是表达力问题，也不是对已提出关系做验证，而是一个缺失的解析能力。建议的最小形态：宿主侧对"整数/字符串身份列且无声明外键"的列做确定性候选匹配（列名相似 + 类型兼容 + 值域包含），命中唯一候选则作为"结构推断绑定"提交给协调阶段参考，命中多个或零个则保留暂缓并把候选列表一起呈现。不需要向量库，你们是全量表声明在手、候选集有界，确定性匹配就够。

两处按 GPT 第一条修正收紧：**候选搜索范围不能只限声明主键**，否则会漏掉业务唯一编号、复合键等情况——优先搜主键、唯一键和明确的业务标识，无法确定时再扩大检查范围；**即使唯一命中也只是绑定建议，不能自动采用**。按 §0.2 的三层分开记录：这一步产出的是"来源绑定候选"，不是业务含义确认，也不自动合并对象身份。

第三类 17 个里有 10 个有一个共同特征，是一个**可以立刻修的具体缺口**：列注释里已经声明了取值（"0禁用 1启用"、"1目录 2菜单 3按钮"、"1仅本人 2本部门 3本办公室 5本区域办公室 99全部"），但 `structured-profile.ts:62` 只把 `c.comment` 当作 `description` free-text 透传，`enumBasis` 唯一可能的取值是 `'database_declaration'`，而 `structured-compiler.ts:65` 要求与声明 ENUM 精确匹配。**于是一个注释里写得明明白白的值集合，宿主没有任何通道承认它。** 建议增加 `enumBasis:'column_comment'` 这一档：解析出的值集合作为候选依据参与校验，但仍进集中确认（注释可能过时或不完整，不能等同于 ENUM 声明）。这比我首轮提的"取值分档"更直接地命中了实际阻断。

**但仅加 enumBasis 不够——必须连带改降级分支（GPT 第二条修正，核实成立）。** `structured-compiler.ts:66-69` 有一个降级分支：新属性、无匹配 ENUM 声明、证据列物理类型单一且非 enum 时，直接 `p.valueType=fields[0].valueType`、`p.enumValues=[]`，并把该成员的 `constraint` 疑问过滤掉。注释声明的枚举恰好满足这个条件（物理类型是 `tinyint`/`varchar`），所以**只加 enumBasis 的话，注释语义会在这里被静默清掉、连疑问都不留**。必须同时改这个分支：标量类型继续可用，注释代码表与含义保留为候选依据，"是否构成封闭业务枚举"进集中确认，既不静默丢弃注释语义，也不把注释当成数据库强约束。GPT 这条提醒精准，我原来的建议会漏掉它。

顺带修正我 §0.3 里的自我撤回：我当时说"对有 ENUM 声明的列截断不参与阻断路径"是对的，但我由此把整个 §3.1 的严重性降级降过头了——实际数据显示枚举类暂缓 17 个里 10 个是注释声明，这一类恰好**既不走 declaredEnum、又受 observedValues 截断影响**（样本只见 1 个值、注释说有两个，而人工确认时 `discovery.ts:97` 只呈现模型提议值）。§3.1 的修订动作保持，优先级可以比我在 §0.4 里排的更高。

### 0.36 第四轮：11 条暂缓关系的逐条核查，推翻了我自己的优先级论证

GPT 第三条修正（"根本没有被生成的关系不会出现在暂缓列表，所以 11–13 不能作为影响上限"）是对的，我接受——那个数字只能描述列表内的成员，衡量不了全部遗漏，而全部遗漏在现有数据里无法观测。

但顺着这条质疑我去逐条看了那 11 条暂缓关系，结果**推翻了我自己"表达力回归优先"的论证**，也比 GPT 的描述更具体。

先看一个总数：这份草稿里 14 张表、8 个采用类型，**最终只采用了 1 条关系**（`system_menu.link.audit`），而且它的两个端点同属一个来源版本——**跨表关系采用数是 0**。11 条暂缓关系按端点存在性分两类：

**第一类，两个端点都已存在（可以现在就解决，不需要新增成员）：**

| 关系 | 端点状态 |
| --- | --- |
| `BranchOffice_belongs_to_Region` | `BranchOffice` ✓ → `type.quyu` ✓（均已采用） |
| `system_menu.link.parent` | 自关联，两端均 ✓ |
| `lawyer_system.Department_belongs_to_branch` | 两端均 ✓ |
| `lawyer_system.Department_has_head` | 两端均 ✓ |

这几条**协调阶段用现有通道就能解决**：`resolutions` 解除疑问 + `changes.from/to` 修正端点，一个新成员都不用加。它们之所以还在暂缓，不是因为模型没法表达，而是因为**模型没有依据去判断 `quyu_id` 到底指向谁**。

**第二类，端点名在任何候选里都不存在：**

| 关系 | 缺失端点 | 实际应指向 |
| --- | --- | --- |
| `BranchOffice_managed_by_Person` ×2 | `Person` | 无任何表提出过人员类型（`system_user` 本身也被暂缓） |
| `BranchOffice_belongs_to_Region` | `Region` | **`type.quyu`，已采用**——只是模型另起了个名 |
| `link_user_role_relation_to_role` | `role` | **`SystemRole`，已采用** |
| `link_user_role_relation_to_user` | `user` | **`system_user`，被暂缓** |

这一类里**只有 `Person` 是真正的"缺成员"**。`Region`/`role`/`user` 全都是**命名不一致**——同一个概念在另一张表里已经以 `type.quyu` / `SystemRole` / `system_user` 被提出了，模型在逐表阶段看不见那张表，所以自己起了个名。这三条用 `changes.to` 改写端点就能接上，也不需要新增成员。

**结论：表达力回归实际阻塞的关系，比我上一轮说的 11–13 还要少——11 条里至少 7 条用现有通道可解。** 真正的瓶颈是**依据**：模型不知道 `quyu_id` 指向 `type.quyu`、不知道 `role_id` 指向 `SystemRole`、不知道 `Region` 和 `type.quyu` 是同一个东西。这正好是 GPT 的第二批（跨表引用候选解析）要做的事。

所以 GPT 那句"跨表引用解析应提前参与协调，而不是作为最后追加的补丁"**比它自己给的批次顺序更重要**。按影响排，解析能力（批 2）比表达力（批 1）更吃紧；表达力只是更便宜、且是 `Person` 那一类的唯一出路。两者确实要一起补——它这个判断对，而我上一轮把表达力排第一的论证不成立，撤回。

一个附带的设计提示：`Region`/`role`/`user` 这三条说明跨表引用解析**不只要解析列引用，还要解析概念同名**。候选解析的输出里应当包含"你说的 `Region` 很可能就是 `type.quyu`（证据：`system_fensuo.quyu_id` → `system_fensuo_quyu.idquyu` 的声明外键 / 值域包含）"这种形态，否则模型拿到候选列也未必能把端点名对上。

### 0.4 调整后的优先级与四批方案的落地提醒

GPT 的四批划分（恢复表达能力 / 稳定执行 / 补足验证 / 呈现覆盖）我采纳，本文件原六项清单并入其中、不再单独按旧章节打补丁。按 §0.35 的数据，建议在其上加**第五批：跨表身份引用解析**（50/147，当前最大单一成因），并把注释声明枚举（10/147）提到第三批最前。

几条落地提醒，都是已存在的能力或已知约束，避免重造或踩坑：

**类型合并已经实现，不要当成新功能。** `compact-coordination.ts:58-71` 的 `merge` 在一个 group 里放多个 ref 就是合并，且 `:60` 强制合并必须给 reason、`:63-64` 强制字段冲突必须用 changes 明确处理。第一批真正缺的是**新增成员**和**属性跨类型归属调整**——后者目前是被显式禁止的（`:55` 的"协调属性不属于所选类型，禁止跨类型移动"），放开它需要同步考虑属性 ID 的重新限定。

**编号的机械限定也已部分实现。** `:95-116` 对多个类型继承同名属性 ID 的情况会按 `owner:id` 机械限定并处理碰撞。第一批的"程序统一分配或校验编号"应当扩展这段，而不是另写一套。

**金标准方法不用重造。** `docs/implementation/PHASE1_PILOT_EVALUATION.md` 已有可执行的标注/冻结/裁决规范（每条记录的 JSON 字段、双人独立标注 + 裁决人、调参集与验收集分离）。最终验收里"预先独立列出的关键类、属性、关系"直接用它，不要新发明一套。

**第二批的局部任务要算容量。** 全局单写锁 `pg_advisory_xact_lock(80731030)`（`database.ts:23`）+ 连接池 `max:4` 意味着领域写入完全串行；拆出更多局部任务会增加 `analysis_steps` 的写入次数和事务数。建议第二批的验收里直接记锁等待和 p95——这项"无锁等待/p95 埋点"在上一轮就是"方案承诺但未做"的遗留。另外局部任务如果要回读源库，注意不要重演 `connected-sources.ts:77-80` 那个问题（在 MySQL 一致性读事务里 await PG 全局写锁）。

**合同指纹变更会让在途任务失败，这是已知行为而非新风险。** `jobs.ts:134` 在 PROMPT_VERSION 升级时直接让旧任务失败，没有排空或标记机制。第一批改协调合同必然触发这条。GPT 说"修复后的生成结果创建新草稿"是对的，但要明确告知操作者在途任务会失败并需要显式重建——这个告知目前不存在。

**cost 仍然是 null。** `jobs.ts:121` 硬编码，无花费上限、无配额账本。第二批验收要求"记录完整请求大小、首字节耗时、调用次数和费用"，前三项可做，**费用这一项需要先把 cost 从 null 改成真实值**，否则验收项无法满足。这是独立的工作量，不要假设它已经在。

## 一、结论先行

借鉴方向是对的，三件被借的东西（分阶段编译、列画像、确定性候选）都是来源侧的工程手段，与"本体服务 SQL 生成"还是"本体服务事实抽取"这个用途差异无关，所以可以安全迁移。既有承重契约我逐条核过，**没有被旁路**：声明层的 `ontology_id NOT NULL`、双时间、`run_id`/`source_version_id` 溯源、禁止按名称自动合并、本体兼容性闸门、viewer 不能触发付费调用、整计划批准，全部仍然成立（见第四节）。

（下文第一至七节为 2026-11-06 首轮审查原文，仅 §3.2 的一句结论已按 §0.2 作废、§2.1 与 §3.1 的表述已按 §0.3 收紧；最严重的一项回归见 §0.1，首轮漏掉。）

但有三处真正的问题，都集中在同一个地方：**auto-ontology 四段式推断里的第三段"数据证据验证"没有被搬过来。** 借到的是"LLM 提议 → 结构约束过滤"，丢掉的是"数据证据验证 → 全局剪枝"。其中最严重的一处（低基数列取值被截断成 5 个）直接削弱了你们自己连打三轮补丁的枚举判定。另有一处是既有能力在本轮被弄丢了：暂缓项的集中事项生成器消失，147 个暂缓成员现在没有任何读路径会呈现。

## 二、丢掉的既有能力

### 2.1 暂缓项不再生成集中事项，且读路径完全不呈现（高）

`discoveryReviewIssues`（`src/knowledge/discovery.ts:65-104`）现在只生成 `first_release`、`removal`、`semantic_change`、`new_constraint`、`constraint_confirmation`、`datetime_confirmation` 六类。`deferred_candidates` 和 `source_exclusion` 在 `src/` 下**已经没有任何生成者**——我全量搜过，只在 `web/knowledge/plans.js:414` 的标题映射表里留着两个永远不会被用到的死标签。

工作区的离线重算报告印证了后果。`work/current-review-reassessment-report.json` 显示：重算前 33 项审核事项里有 `source_exclusion` 21 项、`deferred_candidates` 1 项，重算后只剩 `first_release` 1 项，而 `deferredRetained` 是 **147**。

把普通暂缓从"必须逐项审批"降级为"覆盖/审计记录"，这个决定本身我认为是对的，与"只在重大节点介入"一致。问题是降级之后**没有补上读路径**。`grep deferred` 在 `src/knowledge/service.ts` 和 `src/knowledge/server.ts` 里是零命中；唯一的呈现是 `web/knowledge/plans.js:397` 把 `validation.deferred` 整个 `JSON.stringify` 倒进一个 `<pre>`。也就是说，147 个暂缓成员既不进集中事项，也不随对象查询返回，只在草稿页面上以一坨 JSON 的形式存在。

这正是我第二轮提过、至今未进方案的那条最高优先级缺口：**部分采用之后，读路径必须随查询返回相关的待决定/失败单元集合。** 本轮的改动让这个缺口从"没做"变成了"做反了"——因为之前至少还有 `source_exclusion` 事项会把它顶到人眼前。

修订动作：对象查询与本体浏览的响应里增加一个"本范围内未采用/暂缓成员"的摘要字段，至少给出数量、成员 ID 和原因分类；草稿页把那坨 JSON 换成按来源和原因分组的可读列表。

### 2.2 文档版本号与代码不一致（低，但影响交接）

`docs/features/structured-semantic-compiler.md` 末节写"提示v17、编译v7"，而 `src/knowledge/structured-compiler.ts:11` 是 `structured-compiler-v8`，`src/knowledge/native-coordination.ts:20` 把 `knowledge-native-sources-v18-compact-coordination` 映射到 `structured-compiler-v8`。文档落后一个版本，且 v18/v8 这一轮的代码（`compact-coordination.ts`、`compact-coordination-schema.ts`）还没提交。交接文档里"DB007不变"是对的，SQL 确实只有 `007-structured-compiler.sql` 两条语句。

## 三、借鉴错了或借漏了的地方

### 3.1 低基数列取值被硬截断成 5 个，丢掉了 auto-ontology 最有价值的一个细节（高）

`src/knowledge/structured-profile.ts:59` 在 `structuredCandidates` 里对每列做 `observedValues.slice(0,5)`，并标注 `displayedValueLimit:5`。截断是无条件的，不看该列的实际基数。

auto-ontology 在同一个位置做的是相反的事：文本列 distinct 值不超过 25 个就跑一次 `SELECT DISTINCT` 把**完整值域**抓下来，而不是只给高频值。它的注释写明了为什么（`visit_enter.py:67-72`）：

> rare-but-meaningful enum values (e.g. 'Banned', 'Restricted') land in the embedded description even when the dominant value fills the row prefix.

你们的 `TableProfiler`（`structured-profile.ts:10-29`）其实已经把这件事做得比它更好：全表完整观测、每列最多留 32 个 distinct 值、超限置 `overflow`、长值和疑似凭据列不留值。`finish()` 产出的 `distinct` 和 `distinctAtLeast` 都是准确的。然后这些辛苦采来的值在送进模型前被砍到 5 个。

后果是具体的：一个有 8 个合法状态值的 `bind_state` 列，模型只能看到 5 个，另外 3 个它不知道存在。而模型提出的枚举要通过校验，必须与数据库 ENUM 声明**完全匹配**（`structured-compiler.ts:65`，比对两边排序后的指纹）。对没有 ENUM 声明的列，这条路本来就走不通，于是落进 `constraint` 不确定项。这就是你们连打三轮补丁（ENUM 阻断、日期阻断、重大决定优先）在处理的那个症状，而其中一个成因就在这行 `slice(0,5)`。

更关键的是人工确认环节也看不到真相。`discovery.ts:97` 生成 `constraint_confirmation` 时，呈现的是 `property.enumValues`——**模型提议的值**，而不是宿主观测到的 distinct 值集合和计数。确认的人既没拿到完整观测，也不知道观测了多少行、有没有 overflow。这是一个决策质量问题，不是显示问题。

修订动作：按基数分档而不是固定截断——`distinct` 已知且不超过某个阈值（建议对齐 25，与 auto-ontology 一致，或按你们的 32 上限取整）时给完整值集合并标注"完整观测"；超限或 `overflow` 时给前 N 个并明确标注"不完整，共 ≥X 个"。`constraint_confirmation` 的文案里补上宿主观测事实：观测行数、distinct 计数、是否 overflow、完整值集合（必要时截断展示但说明总数）。

### 3.2 关系候选完全没有值重叠验证（中高）

`structuredCandidates`（`structured-profile.ts:59`）把 `metadata.foreignKeys` 原样透传。声明外键这条路是可靠的——MySQL InnoDB 会强制，`mysql-reader.ts:41` 从 `information_schema` 读的是真实约束。问题是模型提议的关系候选：它只需要给出一个列绑定作为证据，而列绑定只证明"这一列存在"，不证明"两列的值真的有交集"。

auto-ontology 在这里有两道闸，你们都没有。一是 `prune_disjoint_semantic_fks`（`semantic_fk.py:103-157`）在推断全部完成后对每条边跑一次值重叠检查，**零重叠就删边**，且判据刻意只用"完全不重叠"而不用阈值（"a low share is no proof"）。二是 LLM 弃权时用样本值跑只读探针（`semantic_fk.py:531-598`），样本值全部命中才认。

你们的 `conservativeNativeDefinition`（`discovery.ts:107-117`）把新关系的 `multiple` 强制为 `true`，所以不会误报基数——这很好，但它防的是"过度断言"，不防"关系根本不存在"。一条编造的关系会生成带证据的错误关系事实，证据指向一个真实存在的列，错误因此可审计但不会被拦住。这与 auto-ontology 对同一问题的判断一致：编造的 JOIN 是语法和类型都合法、还能返回行的 SQL，上游没有任何环节会报错（`join_path_check.py:10-14`）。

修订动作：对模型提议的、没有声明外键支撑的关系候选，在构建前跑一次有界只读的值重叠探针（宿主侧，不经模型）；零重叠则降级为 `source_binding` 暂缓项而不是直接采用。探针走你们已有的只读采集路径，注意不要落进我上轮提的缺陷 1（在源库一致性读事务里 await PG 写锁）。

### 3.3 协调阶段剥掉了列画像，跨表证据无法复核（中）

`structuredCoordinationSourceView`（`structured-model-boundary.ts:62-64`）只保留 `tableStructure` 和 `coverage`，不带 `structuredCandidates`。文档说明了动机：14 表的来源视图从 108090 字节降到 22803 字节。省 token 的目的正当，但代价是协调阶段看不到任何列画像和确定性候选，于是跨表才能发现的问题（同一个业务字段在两张表里物理类型不一致、枚举值域不一致、日期表示不一致）在协调阶段无法复核——而这恰好是协调阶段存在的理由。

逐表阶段的 `uncertainties` 会带过去，所以不是完全失明。但那是"模型自己记得提的问题"，不是"宿主可以核对的事实"。

修订动作：协调视图里按需补一个极小的画像投影——只给参与了候选成员的列，且只给 `valueType`、`physicalType`、`distinct`、`enumBasis` 四个字段，不给取值。这几个字段加起来每列不到 100 字节，14 表也就几 KB。

### 3.4 `unresolvedDiscoverySources` 的兜底可能把全部来源拖下水（中）

`discovery.ts:154`：当一个暂缓成员既没有证据、也不在任何 `tableProposals` 里时，`sourceIds.forEach(id=>affected.add(id))` 把**所有来源**标成受影响。随后 `structured-compiler.ts:132-135` 对 `unresolvedSourceIds` 里已有正式构建的来源保留旧构建头、跳过本轮构建。

单独看每一步都是保守的、正确的。合起来看：在 147 个暂缓成员的现实下，只要有一个成员落进这个兜底分支，本轮所有来源都会被跳过构建。这可能就是你们看到的大面积跳过的机制成因。保守本身没错（宁可不构建也不要退休旧事实），但"为什么全跳了"目前对操作者是不可见的——因为 §2.1 说的那个读路径缺口。

修订动作：这个兜底分支触发时单独记一条可读的原因（"成员 X 既无证据也无逐表提案，保守波及全部来源"），并随构建回执呈现。先让它可见，再决定要不要收窄。

## 四、核过的、确实保留住的部分

这一节我写得细一点，因为这些是"方案提议要造但其实已存在"的反面——是"文档说保留了、经核对确实保留了"，不需要再动。

声明层契约完整：`sql/001-core.sql:29,35-36` 的 `ontology_id uuid NOT NULL`、`source_version_id`、`run_id` 都在；`:43-44` 的 `valid_from/valid_to` 与 `system_from/system_to` 双时间在；`:50-52` 三条 CHECK 约束在。声明层仍然没有 `EXCLUDE`/`tstzrange`，符合"声明层绝对不能加时间排斥约束"这条定论。

禁止按名称自动合并仍在 `service.ts:273`，`['name','label','姓名','名称']` 四个命名空间被拒。本体兼容性闸门仍在 `service.ts:444-448`，不兼容则当前视图查询抛错、`knownAt` 历史仍可用。

权限没有被新入口绕过。`recoordinate`（`jobs.ts:104-105`）和 `enqueue`（`jobs.ts:55-56`）都先 `authorize(actor,true)`，而 `contracts.ts:117-118` 的 `authorize` 对 `write=true` 拒绝 viewer。HTTP 层 `server.ts:172` 没有单独的 viewer 判断，但领域层这道闸是有效的——我上轮提的缺陷 10（viewer 可触发对生产库外连）在这个新入口上**没有重演**。

整计划批准没有退化成逐表批准。`structured-compiler.ts:139` 强制每个表级计划只能绑定当前来源，但最终 `plan()` 返回的是一个合并后的 `planProposalSchema`（`:143`），批准仍在计划层。映射复用（`mapping-reuse.ts`）要求已发布本体、构建头、结构指纹、manifest 全部匹配，任何一处不符就 `return null` 回退模型；复用时 `items[...]={...value,reviewed:false}` 把审核标记清零，不把旧批准当新批准。

最终校验没有被单来源快路径绕过。`structured-compiler.ts:112-116` 的单来源分支跳过协调阶段，但 `jobs.ts:257` 对任何路径的产出都跑完整 `validateDiscovery`，而 `discovery.ts:356` 最终仍按严格的 `ontologySchema` parse、`:350` 把端点不在活跃类型里的关系过滤掉。native 路径的若干处放宽（`discovery.ts:231-248,286-289,317-320` 用隔离/暂缓替代抛错）只影响"要不要让整个任务失败"，不影响"未经验证的东西能不能被采用"。

## 五、比 auto-ontology 做得更好、不要在后续迭代里退回去的部分

确定性优先在你们这里是**宿主无条件覆盖**，而不是提示词里的请求。`conservativeNativeDefinition`（`discovery.ts:107-117`）对新类型清空 `identityNamespaces`、新属性强制 `required=false`、新关系强制 `multiple=true`，`structured-compiler.ts:45-49` 在校验后把这三项重新写回候选。auto-ontology 对应的是 `fk_suggester.py` 和 `term_extractor.py` 里的提示词规则——模型不遵守就没有第二道防线。你们这个做法更强。

分阶段编译是**可恢复**的。`analysis_steps`（`sql/007`）按 `(job_id,stage)` 存冻结输入指纹和原始输出，`structured-compiler.ts:24-40` 每步先查租约、再比指纹、不符就拒绝沿用，并且在宿主语义校验**之前**先把 schema 合法的付费响应落库（`:33-38` 的注释写明了理由）。auto-ontology 的编译完全不可恢复，中断就得重跑。

列画像是**全表完整观测**而不是行数上限。`connected-sources.ts:75-97` 按页喂 `TableProfiler` 并把 `profiler.finish()` 写进 `metadata.profile`，coverage 标 `complete_observation`。auto-ontology 是 1000 行有界样本。注意 `discoverySamples`（`native-coordination.ts:13-14`）只取 10 行给模型看，这是对的——画像走的是另一条路，不要误以为画像只看了 10 行。

**最重要的一条：你们有重新编译的入口，auto-ontology 没有。** `POST /api/jobs/:id/recoordinate`（`server.ts:171-172` → `jobs.ts:104-111`）可以在不重买逐表调用的前提下只重跑协调；`reassessNativeDefinition`（`discovery.ts:119-136`）可以在不调模型的前提下按当前规则重算已采用定义。auto-ontology 的编译工作清单是 `fetch_all_tables_without_term`（`dal/datasources.py:852`），**只处理还没有 Term 的表，已编译的永不回溯**——改了提示词、换了模型、修了一个系统性错误，都不会回溯已有产出。这正是我提醒"不要在参考它的过程中弄丢"的四件事之一，你们保住了，而且 `native-coordination.ts:17-21` 的 `compatiblePolicies` 把跨策略复用限制成一张显式白名单，比隐式兼容更安全。

## 七、验证局限
