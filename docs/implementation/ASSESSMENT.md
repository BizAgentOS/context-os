# Context OS 现状评估与持续推进流程

评估日期：2026-10-30。代码目录：`/Users/huangjing/haizhi-project/context-os`。基线提交：`1decb883d4727aef0e0ce74cf872a216f68865e6`。

## 1. 本次结论与适用边界

建议按目标架构直接实现知识核心，选择性复用已有工程资产。项目尚未投入使用，不将旧 SQLite 数据迁移、旧接口兼容、新旧双轨运行作为交付前提；旧实现可以直接替换。代码分阶段实施是为了验证正确性，不是为了兼容旧系统。本次修订仅更新方案，未删除旧数据或修改原项目。

本轮完成核心链路的静态评估、类型检查与一组针对性测试，未修改原项目，未启动真实模型抽取、外部数据库或生产服务，未读取凭据和企业运行数据。数据库连接器的存在不代表真实环境接入已验证。

需求以本次沟通为准：平台面向不同企业销售和复用，默认一个实例服务一家企业，企业接入自身数据；核心能力为对象式本体、结构化/非结构化接入、证据、双时间及反馈修正。通用性体现在跨行业与企业配置复用，不要求同一实例托管多家企业。仓库中的单企业范围符合当前方向；其他历史设计仍按实际需求评估。

定位修订：初版曾将“面向不同企业的平台”误推导为“同实例多租户”，未经用户确认。本版撤回该要求，不强制 tenant_id、多租户路由或跨租户测试。未来如明确提供共享 SaaS，再独立评估多租户设计。

本报告中的“未发现”仅指本轮所检查的核心模型、调用路径与代码搜索结果；最终实现取舍通过新目标的业务验收复核。

### 1.1 方案来源与优先级

本文融合前序产品讨论和代码评估，但初版对旧系统兼容的强调过多，对 OO 设计和参考方案的对应关系表达不足。本节明确：用户确认的产品目标决定架构；已有方案提供设计参考；当前代码只用于识别可复用资产，不反向限定目标。

| 前序讨论 | 目标中的具体落实 |
|---|---|
| Palantir 的对象式本体与 OO 思路 | 以 ObjectType、PropertyDefinition、LinkType、ActionType 组成版本化元模型；对象实例有独立稳定 ID；通过对象服务查询，通过受约束的 Action 修改 |
| 通用平台、单企业实例 | 不同行业通过配置与领域模型复用同一产品；不引入共享实例多租户要求 |
| 自动生成本体 | 数据分析 → 候选类型/属性/关系 → 样本与约束验证 → 按策略发布版本 → 反馈修订；需独立于“按已有本体抽取事实”评估 |
| 结构化及非结构化融合 | 表和字段映射、文档抽取分别产生候选声明，经过校验和身份解析进入统一知识核心 |
| 上下文证据 | 声明关联指定来源版本及字段/原文位置；原文明示、系统推断和事实采纳分开记录 |
| 时序知识 | 业务有效时间与系统记录时间分别管理；变化和纠错分别处理 |
| 外部反馈校正 | 稳定对象/声明上的 Action、审计、冲突策略、依赖重算；验证后再改进抽取规则 |
| PostgreSQL 替代先行引入图数据库 | 关系表与 JSONB 支撑对象、关系、声明和时间；有真实需求后再评估图索引 |

OO 在这里是业务对象及其行为的建模方式，不要求对象数据库，也不要求每个行业类型都编写一个代码类。类型定义属于本体元数据，对象实例属于业务知识，声明与证据记录具体知识的依据，三者分开管理。

参考资料及用途：

- Palantir：[对象与属性](https://www.palantir.com/docs/foundry/object-link-types/properties-overview)、[关系](https://www.palantir.com/docs/foundry/object-link-types/link-types-overview)、[Action](https://www.palantir.com/docs/foundry/action-types/overview/index.html)，参考业务语义及操作模型，不推定其内部存储实现。
- Microsoft：[GraphRAG 数据流程](https://microsoft.github.io/graphrag/index/default_dataflow/)，参考抽取流程与原文关联，不把问答索引等同于整个知识平台。
- Zep / Graphiti：[来源及时间机制](https://www.getzep.com/blog/how-zep-tracks-provenance-in-agent-memory/)，参考事实溯源和时序设计，不预设采用其运行时。
- Neo4j：[知识构建流程](https://neo4j.com/docs/neo4j-graphrag-python/current/user_guide_kg_builder.html)，参考解析、抽取和校验的职责划分，不依赖其数据库。

这些是前序调研的设计参考，尚未逐项完成依赖选型或实现验证。本文的声明存储、PostgreSQL schema 与服务边界是面向本项目的设计建议，不是对参考产品实现的复制。

## 2. 已确认的架构事实

### 2.1 已有可复用的本体基础

`src/semantic/model.ts:19` 定义实体类型；`:54` 定义身份规则；`:65` 的 `createLayeredModelSchema` 分离 semantic 与 bindings；`:194` 起有稳定标识和旧模型迁移机制。

这说明项目已有元数据驱动的语义模型，不能把它简单归类为纯演示。保留稳定类型/属性/关系 ID，以及映射与语义分离的方向。

但 `:98-100` 规定每种实体至多一个 primary，supplement 依赖 primary；`:151-154` 的身份规则也围绕这些角色。当前对象融合仍受主来源锚定，不能直接等同于独立于来源的对象注册表。

`:62` 有实体、关系及补充来源的默认数量限制，且允许显式配置。应按真实工作负载重新定参数，不能把它们当业务上限；也不能无边界删除资源保护。

### 2.2 本地成果持久化已有事务与版本机制

`src/agent/memory.ts:91-110` 创建 `memory.sqlite`，主要保存 artifacts、任务、消息、操作与 settings。`:220-246` 提供同步事务、提交检查和提交后的变更通知。成果以 JSON body 保存，版本与 head 分离。

这些机制可作为事务和版本设计参考，但本轮没有在此存储中发现业务对象、声明、双时间和证据依赖的专用持久化结构。源码显示 `MemoryStore` 被大量模块依赖；新实现应直接定义所需领域接口，并配套调整调用方，不受旧同步 Repository 接口约束。无需为旧数据库编写导入转换器。

### 2.3 多源融合和属性证据已经存在

`src/live/fusion.ts:77-87` 有 PropertyEvidence / ObjectEvidence，区分 resolved、missing、conflict、uncertain；`:135` 的 `fuseRows` 在调用时对主来源行和补充来源做有界融合；`:154-155` 的对象标识取自主来源身份。

保留证据表达、缺失/冲突状态及有界读取经验。将其改造成声明生成/融合适配器，逐步解除“当前查询时拼出对象”的核心依赖。

### 2.4 文档解析及精确引用值得保留

`src/data/document-extraction.ts:2-11` 定义正文偏移、PDF 页码和 DOCX 章节位置；`src/agent/knowledge.ts:204-247` 保存片段版本、哈希、偏移和引用快照；`:234-236` 验证引用唯一匹配已读取原文。

这些能力可支持声明级证据。当前 `KnowledgeReader.cite` 的 `validTime` 明确为 unknown，不能据此声称已支持双时间。

### 2.5 知识文档到事实对象存在明确边界

`src/live/memory.ts:578-602` 的模型准备路径要求实体绑定，并拒绝把 contentKind=knowledge 的知识片段映射为业务记录。

这有防止直接把文档片段冒充业务记录的价值，但新平台还需要独立路径：文档 → 有证据的候选声明 → 校验 → 对象身份解析 → 事实视图。不能仅删除该检查、让任意片段直接成为对象。

### 2.6 纠错机制已有积累，但绑定执行模型

`src/live/property-corrections.ts:20-30` 按 modelRef 及版本选择纠正；`:61-95` 捕获基线并复验事实指纹；`:107-149` 将纠正随模型变更迁移。`src/live/identity.ts:15-29` 支持 match/no_match 决定，并同样关联模型版本。

保留基线复验、防过期写入及历史固定的测试思想。新核心需要把修正锚定到稳定对象/声明，明确覆盖期限、优先级、源数据更新后如何重算，不应长期以模型版本迁移承载全部纠错语义。

### 2.7 单企业实例与企业内部权限

`src/agent/app.ts:245-257` 从一个 directory 创建 MemoryStore / LiveMemory；`src/agent/server.ts:158` 使用本地工作目录。这与当前单企业实例方向一致，不应因缺少多租户设计判为缺陷。`src/security/actors.ts:4-14` 有角色和调用身份上下文，缺失上下文时默认本地管理员，需结合实际部署核查认证、企业内部权限和默认管理员行为。

源码中含 tenant 的样本和复合键测试属于源数据身份处理能力，可按需要保留，不代表平台必须提供多租户服务。部门、项目及敏感文档权限应按企业实际需求定义。

以上是本轮评估建议，不是已执行的删除清单。每项替换核对调用路径和新验收条件；不为未使用的旧数据增加迁移工作。

## 4. 目标边界

```text
数据源 / 文件
  → 接入与原始版本保存
  → 结构化映射或非结构化抽取
  → 候选声明（证据、时间、抽取运行、所用本体版本）
  → 校验与对象身份解析
  → 声明存储及融合策略
  → 当前对象视图 / 历史查询 / 证据查询

用户或外部反馈
  → 授权 Action → 修订/否决/合并/拆分
  → 依赖失效与重算 → 评估样本和规则改进
```

建议分离 OntologyRegistry、ObjectRegistry、AssertionStore、EvidenceStore、ActionService、ProjectionService 六个领域接口。它们可以先部署在一个应用内，不要求拆成微服务。

PostgreSQL 承载本体、对象、声明、时间和审计；JSONB 承载灵活值与配置；对象类型、端点、状态、时间等查询字段采用显式列。文档保留在文件/对象存储。Agent 会话与任务根据新流程实现，不要求搬运旧会话和任务。

最小数据模型应覆盖 ontology_version、object_type/property/link 定义、object、external_identifier、source_record_version、assertion、assertion_evidence、action_event、projection_dependency。表名与拆分在设计阶段确定。

声明必须区分属性值与对象引用，并明确：业务有效时间、系统记录时间、来源版本、明示/推断、采纳状态、抽取器/规则版本、人工修订及替代关系。未知时间允许为空。业务时间变更不能直接从同步时间推断。

默认单企业实例，第一版不强制多租户架构。不同企业通过独立实例及各自数据、配置和凭据使用同一套产品；企业内部权限按业务需要实现。通用性通过另一套独立配置和样本验证，不以共享实例的租户隔离作为验收条件。

## 5. 可持续推进的阶段与完成条件

| 阶段 | 交付 | 完成条件 |
|---|---|---|
| P0 基线与验收 | 真实业务问题、样本、正确答案及依据、模块取舍表 | 样本不混入被测模型输入；结果可重复 |
| P1 核心契约 | OO 元模型、六个领域接口、数据库设计、权限边界、时间语义 | 类型/实例/声明分层清楚，能解释身份、证据、冲突、修订、历史 |
| P2 纵向闭环 | 一个结构化源加一类文档进入新核心 | 同一对象有跨源声明，答案能回到具体来源版本 |
| P3 时序与修正 | 双时间查询、Action、失效重算 | 迟到信息、纠错、业务变更、再次同步均正确 |
| P4 工程整合 | 复用或重写选定连接器、查询和 UI，统一使用新核心 | 不再依赖被替换链路，新业务验收通过 |
| P5 通用性复验 | 另一套独立企业配置及不同业务场景 | 同一套产品核心机制复用，不要求在同一实例运行 |

不预设工期。每轮限定一个可验收缺口；发现新事实后更新后续阶段，不改写历史验收记录。直接在新开发数据库初始化及导入试验数据，不做旧状态回填、新旧 ID 转换或双写。数据库仍应有可重建的初始化脚本和后续 schema 版本管理；这与旧 SQLite 数据迁移是两回事。是否删除旧文件单独执行，不把项目未使用当作已授权删除所有文件。

## 6. 第一批任务

1. 固定试点业务：企业—合同—负责人是候选示例，仍需选择实际数据与问题。先用脱敏样本和 fake extractor 验证存储闭环，再测真实模型质量。
2. 定义三个独立标识：业务对象 ID、来源记录 ID、本体成员 ID；明确来源主键变化时对象身份是否保持。
3. 定义声明和证据契约：结构化字段、PDF 页/偏移、DOCX 章节/偏移都能引用指定来源版本。
4. 直接实现 PostgreSQL 初始 schema、初始化及开发数据重建脚本；从源样本重新接入和抽取，不迁移旧 SQLite 业务状态，不建立旧接口兼容层。
5. 将一个现有结构化接入转换为声明；将一类文档抽取结果送入相同声明接口。
6. 实现当前视图及证据查询；保留冲突候选和所用融合策略版本。
7. 实现一个 CorrectProperty Action，验证审计、人工覆盖策略及再同步。
8. 实现双时间查询及依赖重算，执行下方验收集。
9. 按新业务验收集整合连接器、Agent 和 UI，直接替换不适用的旧路径；旧测试仅复用仍符合目标的部分，不要求结果与旧实现一致。
10. 补齐自动本体生成与版本发布闭环，单独评估概念重复、类型/关系准确性、约束与反馈修订，避免只完成事实抽取。

## 7. 必须保留的验收集

- 同一企业在数据库和文档中名称不同，但有可信标识，可关联并保留原始身份；无足够依据时不强行合并。
- 来源金额不同，两个声明及证据均保留；当前选择能解释，不能只覆盖字段。
- 一份文档先引入来源中不存在的对象，之后结构化数据出现可关联身份。
- 系统 4 月 10 日收到“4 月 1 日已交接”，分别按业务时点和系统获知时点查询。
- 业务负责人变更和历史抽取错误使用不同修订语义。
- 人工修正后再次同步，遵循明确的覆盖范围与有效期。
- 错误合并能拆分，相关关系、证据和视图可追踪并重算。
- 来源修订、撤销、删除或访问权收回后，依赖知识和证据访问按策略更新。
- 本体升级后可解释历史声明使用的类型版本，不静默改变历史含义。
- 对象查询、证据查询、后台任务、缓存及导出遵循企业内部实际权限策略；独立实例的样本、配置和凭据不意外混用。
- 网络失败与重试不重复生产声明，任务可恢复；并发修正不发生无声覆盖。
- 第二业务场景复用时间、证据及反馈机制，不复制一个行业分支的知识核心。

准确率、召回率、来源支持率、时序正确率、反馈后回归结果分别衡量。性能阈值依据样本量和服务目标设定，不凭空承诺。
