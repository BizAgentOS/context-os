# DataEngine 主 Agent 设计草案

日期：2026-09-07。状态：**Agent 行为设计初版已形成，尚未实现。** 依据为用户确认的 [产品目标](PRODUCT.md)、[MVP 范围](MVP.md)及已核对的 KodaX / NOOA 资料。功能规格归入 [FEATURE_003](features/v0.1.0.md#feature-003)，前端由 FEATURE_005 承接。

先读[Agent 设计方案](AGENT_BLUEPRINT.md)，了解组成、身份说明、方法卡、上下文、对象工作区和接口契约。本文件第 4—9 节详述职责、行动选择、工作状态、人机协作与完成条件；第 10—12 节保留技术参考。两份文档共同服务 FEATURE_003，不代表已经进入运行时或界面开发。

## 1. 设计结论

**DataEngine 是本体、KodaX 与 NOOA 式对象 harness 结合形成的整体产品。** 本体定义企业业务语义；对象 harness 将这些语义呈现为 Agent 可发现、可访问和可组合操作的对象；KodaX SDK 承接模型与运行循环。三者共同支撑企业记忆的建设、使用和维护。

产品中的连续体验是：对话明确一个目标，Agent 查看当前资料与记忆，调用工具完成可执行的工作，留下可检查的成果，再针对实际缺口提问。企业理解、数据接入、本体设计、报告和维护是同一 Agent 的不同工作方法，可以往返补充。

**主 Agent 的角色：围绕用户当前的业务目标，建设、使用并维护可复用的企业记忆。** 它负责组织工作、找出信息缺口、提出设计和解释结果；来源解析、关系查询、统计及正式保存由对象方法和应用服务执行，关键业务歧义由用户决定。

一项任务的交付物是可重新打开的企业理解、来源说明、本体候选、报告或修改记录。已有记忆足够回答的简单追问可以直接答复并引用原成果，无需每句话新建报告。长期价值通过后续任务复用这些成果体现；“企业大脑持续完善”不意味着每次对话都必须完成整套建模。

本体决定 Agent 看到哪些业务类型、字段、关系和方法。首轮 MVP 的核心验证包含一段最小的对象方法组合执行。具体采用 CodeAct、受限组合接口或哪些 NOOA 组件，在行为设计评审之后验证；本轮不提前选定执行器。目前没有证据表明 KodaX 与 NOOA 的完整运行时可以直接拼接。

## 2. 整体如何配合

```mermaid
flowchart TB
  U[用户：对话、上传、纠正、查看成果] <--> A[DataEngine 主 Agent 工作台]
  A <--> R[KodaX SDK：会话、运行、模型、工具调用、事件]
  R <--> M[NOOA 式对象 harness：发现类型、访问对象、组合方法]
  O[本体：概念、身份、关系、口径与约束] -->|决定对象接口| M
  M <--> E[企业记忆：实例、证据、来源、理解、报告、变更]
  E --> V[成果视图：卡片、局部关系图、原文、差异]
  V --> A
```

| 部分 | 产品职责 |
|---|---|
| KodaX SDK | 接管模型调用与运行循环、会话继续、执行事件和工具调用；DataEngine 直接消费实际 SDK 契约 |
| 本体与对象 harness | 从本体提供业务类型、实例、关系访问和语义方法；Agent 在这些对象上查证、计算并提出修订 |
| 主 Agent 工作方法 | 根据目标和可用资料选择下一步，提出概念与映射、调查证据、解释结果和缺口 |
| 企业空间与工具 | 保存资料、身份、定义和版本；执行解析、查询、计算、验证、受控保存；返回明确成功或失败 |
| 前端 | 展示对话与真实执行进度，打开当前成果，让人编辑理解、检查证据、决定关键语义 |

前端与 Agent 读取同一批成果。页面上的企业理解、本体定义和报告都来自持久化对象，不从聊天文本临时拼出另一套状态。

## 3. 先有工作对象，再形成业务本体

从空白企业开始就需要少量由产品定义的工作对象：

| 工作对象 | 保存什么 |
|---|---|
| 企业理解 | 企业做什么、用户职责、当前业务目标、工作流程、已知内容与待补充问题 |
| 数据来源 | 原文件或连接器引用、来源版本、读取时间、解析结果、字段与样例、可用状态 |
| 建模草稿 | 概念、关系、口径、映射建议，以及依据、备选和待决定事项 |
| 报告 | 问题、适用时点、使用的记忆版本、事实、解释、证据与未决项 |
| 修改建议 | 要改什么、原版本、理由、依据、影响、检查结果与应用记录 |

这些对象使 Agent 在尚无业务本体时也能工作。企业本体随后描述换热站、楼栋、投诉单、回访、维修等业务概念；实际概念须经资料观察和任务分析决定。一个概念可以由多个来源共同支撑，一张表也可能包含多种业务含义。

工作对象用于空白企业启动；业务本体形成后，其类型和实例成为 harness 的主要业务操作对象。本体定义保留为可版本化的语义契约，通过统一对象适配层生成或解释出类型说明、属性、关系访问与可用方法。无需让模型为每次建模自行部署代码，也无需给每个业务对象配置独立 Agent。

每个可引用成果至少有稳定 ID、种类、版本和状态。业务对象另带本体/映射版本、有效时间及证据定位。跨会话传递可重新解析的引用，不能依赖某次进程的内存地址。

### 本体如何成为可操作对象

以下是 DataEngine 的设计映射，借鉴 NOOA 的对象接口；不是 NOOA 已提供的企业本体转换功能。

| 本体中的内容 | harness 中的表达 |
|---|---|
| 概念及定义 | 可发现的业务类型，包含名称、身份规则、字段和方法说明 |
| 具体实例 | 带稳定业务 ID、类型及快照版本的对象或惰性代理 |
| 属性 | 有类型、单位、时间和来源的字段；详细内容按需读取 |
| 关系 | 返回相关对象/对象集合的访问方法，保留关系自身的时间和证据 |
| 业务口径与已实现函数 | 绑定定义版本的确定性方法；方法返回值也包含适用范围和证据 |
| 约束 | 对象读取、计算或变更采用时的实际检查；不靠类名/类型声明代替业务检查 |
| 本体定义本身 | 可检查的概念、关系、规则等建模对象，提供候选修订与检查入口 |

例如，在拟定的热力对象环境中，Agent 可以取得一个站点，沿其服务楼栋读取投诉，查看投诉关联的维修、回访与测温证据，再组合计算。它访问的关系和方法来自已采用本体及注册的计算实现，而不是每次在原表上重新猜测关联。

对象层是持久企业数据的运行时视图，不需要把全企业装入内存。缺少关系证据时返回未解析/未知，不能把缺失等同于关系不成立；“恢复证据”方法也不能仅凭已办结返回恢复。首轮只实现任务需要的本体语义子集，不声称提供通用逻辑推理器。

事实刷新在既有定义下产生新对象快照；本体修订被采用后，后续任务取得新定义对应的类型/关系说明和对象视图。运行中对象与报告固定原快照；规则执行代码只有在已有受支持实现或经过开发检查后才能绑定，新方法不会仅因模型写下名称就生效。

前端与 Agent 使用同一对象 ID、类型、关系、证据和版本。Agent 展开的关系可以直接在右侧呈现，用户修改后的有效定义也能改变后续可见的对象环境。

## 4. 主 Agent 怎样工作

### 4.1 用当前目标组织工作

每项任务先明确三件事：**要解决的问题、使用的范围、交付什么。** 例如“根据现有投诉与回访资料，找出已办结但缺少恢复证据的投诉，形成一份可回查的简报”。用户的表达已经足够清楚时，Agent 简述理解后直接做；不要求用户先填写任务表或逐项批准计划。

如果用户只说“帮我建立企业大脑”，首个目标收敛为“形成企业理解初稿，并选出第一项值得验证的业务任务”。只了解企业做什么、用户负责什么、当前最关心什么；能从上传资料读到的内容跳过提问。企业规模、所有部门、所有接口不作为开工必填项。

工作循环是：**读取当前目标与成果 → 找出当前缺口 → 选择提问、查证或操作 → 检查并保存结果 → 判断是否完成或需要等待。** 每次工具返回后重新判断，用户也可以随时纠正方向。没有固定的“企业问卷全部完成才接数据、数据全部接完才建模”流程。

### 4.2 下一步的选择规则

先处理用户最新指令或纠正，再读取已有成果，完成不受歧义影响的工作，最后提出真正阻碍当前目标的问题。以下是行为规则，不是新增流程引擎；模型依此选择行动，应用服务强制执行版本、写入和访问约束。

| 当前情况 | Agent 下一步 | 用户看见什么 |
|---|---|---|
| 已有资料可回答当前缺口 | 先读相关来源、定义或对象；取得直接依据再更新理解 | 正在检查哪份资料/哪个对象，以及读到的内容 |
| 目标宽泛，但可先做有用的小成果 | 保存有依据的初稿，补问最影响下一步的 1—2 个问题 | 初稿与一个具体问题；不必反复介绍已知信息 |
| 缺少数据，现有来源无法补足 | 保存已完成部分，指出所需资料、用途与缺失影响 | 上传/选择已授权来源的入口，或范围明确的待补充项 |
| 含义存在会改变对象身份、统计或结论的歧义 | 查现行依据；仍无法决定时提出具体选项及影响 | 两种解释、各自依据和采用后影响，不笼统问“是否正确” |
| 已有适用的本体与方法 | 按定义发现类型、取得对象、沿关系查证和调用计算 | 同一对象、关系、口径、证据与结果 |
| 现有定义不能表达任务需要的业务含义 | 保留可用部分，形成最小本体修订候选并检查 | 缺口为何影响任务、候选定义和实例预览 |
| 新资料与已有企业理解冲突 | 保留两种陈述，记录时间/来源，判断是事实更新还是定义冲突 | 差异和受影响的成果；未决冲突不会被覆盖 |
| 已达到本项任务的交付条件 | 保存或引用成果，说明结论与限制，结束当前执行 | 明确的成果入口，必要时一个可选后续建议 |

未取得新信息或修正条件时，不反复调用同一失败工具。同一参数错误可按反馈修正一次；持续失败、凭据不可用或预算耗尽时保存工作状态并解释阻塞。恢复前重新读取状态，避免重复导入或保存。

### 4.3 哪些事自己做，哪些事需要用户

| 行为 | 默认协作方式 |
|---|---|
| 查已接入资料、查询对象、计算、检查候选、保存草稿与报告 | 在当前目标与已授权来源范围内直接做 |
| 用户明确要求的普通编辑、按既定映射刷新数据 | 直接执行，展示新版本和修改结果 |
| 首次采用本体、改变身份规则/关系条件/统计口径，或无法按既有规则解决的冲突 | 先形成具体候选、检查结果及影响，再让用户决定 |
| 选择业务目标、补足只有业务人员知道的含义、开通新来源访问 | 在真正缺少时提问或打开授权入口 |
| 下一项任务、扩大数据范围、后台持续工作 | 提出建议，由用户发起或明确授权 |

用户的明确决定可通过对话或成果卡片给出，并关联当时展示的具体版本；不会要求再点一次相同确认。如果一句“好”可能对应多个不同操作，不能替用户扩大解释为采用所有候选。已有的有效业务规则直接复用，不为同一语义重复提问。

关键决定不是每个步骤都要审批。本体候选可以连续生成、检查和展示；只有成为正式企业定义时才需要实际的采用决定。无关的未决问题不阻塞其他已具备条件的工作。

### 4.4 一个 Agent，五种工作方法

| 方法 | Agent 的主要判断 | 工具留下的成果 | 什么时候询问用户 |
|---|---|---|---|
| 理解企业 | 找到企业业务、使用者和一个值得处理的问题 | 企业理解初稿 | 只补问会影响当前工作的缺口 |
| 接入资料 | 识别资料用途、内容范围、相关性及缺口 | 来源、解析预览、接入摘要 | 需要选文件/授权；资料含义影响使用但无法从现有内容判断 |
| 辅助建模 | 决定概念粒度、身份、关系成立条件和统计口径 | 概念卡、关系、映射候选、实例预览 | 存在关键歧义或冲突，或新定义将改变业务结论 |
| 调查与报告 | 按问题读取对象/证据、调用计算、识别结论边界 | 有来源的简易报告 | 问题范围不明确，或缺口使核心判断无法成立 |
| 维护记忆 | 判断新增资料影响事实、映射还是业务定义 | 影响说明、修改建议、保存记录 | 需要解决矛盾或确认重要语义变更 |

工作方法先作为简短说明和工具约定实现；不为每种方法建立一个子 Agent，也不增加流程调度平台。建模方法采用现有[六步建模设计](experiment/ONTOLOGY_MODELING.md)，阶段成果可查看，用户无需填完六页表单。

没有正式本体时，Agent 用企业理解、来源和建模草稿这些工作对象进行阅读、画像和建模准备。有正式本体后，业务调查优先使用其对象与方法；遇到缺口再回读原文，不为每个问题重新发明一套关联。用户直接要求原始资料摘要时，可以交付摘要并说明适用范围，无需为了摘要强行建立本体。

出现具体业务目标、相关来源和足以提出概念的资料观察，就可以开始候选建模。跨来源身份、关系成立条件或统一口径影响任务时，优先明确这部分定义；初步资料不足以支持的关系保留未决。无需等待企业画像或所有接口接入完成。

### 4.5 主动性的触发与停止

首次进入且模型可用时发起简短引导；消息、在当前会话提交的资料、用户纠正或“继续”触发当前任务推进。资料提交触发登记与必要的读取/影响检查，不能自动延伸为全企业重建或全量报告。单纯打开一个成果供查看，不产生新的维护任务或模型调用。

“主动”指对当前目标补问、发现缺口、完成已经有条件执行的工作。任务完成、必须等待用户决定、用户停止、持续失败或执行预算耗尽时，本次运行结束。首轮不设置全天候巡检；可选下一步留在界面，不自动执行。

## 5. 企业记忆如何保存与进入上下文

### 5.1 当前任务保存一张工作记录

跨会话续接靠明确的工作记录，不依赖模型记住全部聊天。每项任务最少保存：

| 内容 | 作用 |
|---|---|
| 目标、范围与交付条件 | 知道当前要完成什么；用户改变范围时保留修订记录 |
| 正在使用的来源、本体版本及成果引用 | 找回数据和已保存结果，不复制整个企业到上下文 |
| 已完成事项、未决问题及其依据 | 避免重复工作，保留哪些是事实、哪些仍待判断 |
| 等待用户的具体问题/候选版本 | 用户回答后接续对应事项，避免把旧答复应用到新候选 |
| 状态与下一步 | 重新打开时能解释停在哪里、为什么以及怎样继续 |

这是一份用户可检查的工作摘要，不保存模型内部推理过程。工具实际成功后才登记对应成果；不能仅因 Agent 声称“已导入”就推进状态。

**任务状态**只需进行中、待补充、已暂停、已完成；执行错误作为本次运行结果及暂停原因记录。任务可以跨多次运行，运行停止不等于任务完成；企业理解初稿、来源解析、本体候选各自保留资产状态。

- 用户补充缺失资料或回答待决定项后，重读任务和相关版本，再继续。
- 用户说“先停一下”时，停止后续行动并保留已完成工作。若一个保存操作已完成，则保留并明确显示它；无法确认结果时先核对，不宣称撤销成功。
- 首轮只保留一个活动任务。用户在执行中纠正目标，先处理纠正；可复用已保存成果，尚未完成的旧方向不继续写入。临时解释或状态追问回答后仍沿原目标推进；明确切换到另一目标时建立新任务，旧任务暂停。
- 重新打开会话，先展示上次成果与下一步；不自动重新导入、重新计算或采用草稿。用户继续后检查是否有新版本，再决定沿旧快照完成还是将任务范围更新。

### 5.2 三类内容，三种处理

| 内容 | 处理方式 |
|---|---|
| 会话与临时工作状态 | KodaX 管理对话和执行，DataEngine 保存当前目标、成果引用与待处理事项；压缩会话不会删掉企业成果 |
| 原始资料与已登记的企业知识 | 产品持久化保存；区分用户陈述、来源记录、模型建议和已确认定义，保留时间与依据 |
| 模型解释与假设 | 可存为报告或候选，不能仅因写进聊天就成为企业事实；被引用时保留其假设/待查状态 |

企业理解可以自动保存为草稿，界面明确展示。用户直接修改时留下作者和版本；一句用户陈述可以登记为“用户提供”，不伪装成原始系统已验证事实。作者、依据和状态关联到具体陈述；新资料或模型推断与用户已编辑内容冲突时，保留原内容并追加待决定项，不能用整份新草稿覆盖。明确且有效的原规则可复用，不为每个字段增设确认。

模型每轮先得到少量导航：企业理解摘要、当前目标、资料目录、可用概念、选中成果引用、相关未决项及工具说明。随后按需读取具体字段、文档片段、关系和证据。列表必须返回总数、分页或截断标识，不能把读到的样例当成全部数据。

选中成果提供本轮关注对象，例如“这条投诉”指向当前投诉引用；它不自动改变任务目标。模型上下文只加载当前目标所需的定义与资料。工作方法说明表达“怎样做”，企业记忆表达“已经知道什么”，二者分开保存。

每次调查或建模任务绑定一组来源/定义版本；新资料进入后建立新版本。完成中的报告继续对应原版本；之后可标记“有新资料待更新”并生成新报告，保留旧报告的依据。引用的来源若当前不可用，显示失效状态和历史版本，不能用另一个来源或最新内容悄悄替代旧证据。

首轮一个企业空间、单用户、串行修改，本地 SQLite 保存结构化记录、文件保存原件即可。KodaX 的会话存储和业务记忆各自负责自己的记录，通过会话/运行 ID 与成果引用关联；不把 SDK 会话压缩摘要当成业务知识库。

## 6. 最小工具与保存边界

下面是 DataEngine 的拟定领域契约，不是 KodaX 或 NOOA 的现成 API。工具名称在实现时可按 SDK 注册要求调整。

| 能力 | 输入 → 输出 | 本轮行为 |
|---|---|---|
| 查看空间 | 企业引用 → 理解摘要、资料/成果目录、未决项 | 提供导航，避免全量注入 |
| 了解类型 | 类型引用 → 定义、字段、关系和可用方法 | 按需披露能力，避免加载完整企业模型 |
| 读取/查询 | 引用、版本、字段/查询条件 → 内容片段、关系、证据、分页信息 | 原始来源与业务对象均可使用 |
| 保存企业理解 | 基础版本、结构化修改、依据 → 新草稿引用 | 已有明确用户编辑可直接登记；模型补充标为建议 |
| 接收资料 | 已上传文件引用或已授权连接器配置 → 来源引用与解析状态 | 原件先保存，解析失败也可查看错误和重试 |
| 检查资料 | 来源引用 → 字段、样例、缺失与可用范围 | 程序画像和 Agent 接入解释分别保存 |
| 提出建模草稿 | 业务目标、概念/关系/口径/映射候选、依据 → 草稿引用 | 结构合格不等于语义正确 |
| 检查并预览 | 指定草稿版本、来源版本 → 检查结果、实例预览、未解析项 | 查引文、身份、类型、时间、映射；不强行补关系 |
| 计算 | 已实现函数与定义版本、范围 → 结果、输入/证据与版本 | 首轮少量固定查询/聚合，分母为零和缺失显式返回 |
| 保存报告/修改建议 | 基础版本、内容、证据/影响 → 成果引用 | 报告不会自动改变企业事实 |

正式采用业务定义或重要修订使用应用服务的保存动作：关联具体候选版本、语义决定和检查结果。Agent 可提出并检查修改；不能仅传入一个自己生成的 `approved=true` 代替用户决定。用户已经明确要求的普通编辑、既定映射下的数据刷新可按该范围执行，不重复索要确认。

检查通过的候选仍为预览；用户采用具体定义版本后才成为当前业务模型。普通对象查询和报告默认使用已采用的版本；若用户查看候选效果，结果必须标为预览，并关联该候选与来源版本。

检查与采用期间若基础版本变化，返回过期提示，重新检查后再应用。工具写入使用请求标识避免重试产生重复成果；一次失败不能留下显示为成功的半份正式定义。

数据接入依赖真实解析器和连接器。Agent 可以协助选择、配置、解释和调用已提供接口；腾讯文档等系统仍需各自的连接器与授权。首条路径先接 Markdown/文本和 CSV，后续按明确需求加入 PDF 或一个外部连接器。

凭据通过设置或服务端环境提供，不进入企业资料和模型对话。资料正文中的命令视为来源内容。运行时只提供当前企业的数据能力；任意文件、命令、网络、评测答案和未来事件不属于这个 Agent 的工具范围。

## 7. 用户如何直观看见企业大脑形成

主对话中，Agent 说“已保存企业理解”时，右侧必须出现真实保存的企业理解及版本。说“发现口径冲突”时，打开两种说法、来源和各自影响。工具执行中展示实际操作和结果摘要，不展示未经核实的完成百分比，也不依赖模型内部推理文本。

每次结束执行时优先说明三件事：交付了什么、依据/范围是什么、是否有阻塞。需要用户参与时只突出一个当前最重要的行动，例如补充回访表或选择一项定义；没有阻塞时直接呈现成果。工具技术名、完整日志和详细版本元数据放在展开信息中。

| 当前工作 | 右侧主要视图 |
|---|---|
| 定义企业 | 一页可编辑企业理解，显示已知内容和待补充项 |
| 接入数据 | 原文/表格预览、来源版本、接入摘要与解析问题 |
| 设计本体 | 概念卡：定义、身份、边界、用途、依据；少量关系的局部图 |
| 检查映射 | 某条源记录如何形成对象/关系，未匹配记录为何保留 |
| 使用对象 | 一个对象的属性、相关对象、时间和原始证据 |
| 阅读报告/维护 | 报告的证据入口，或修改前后内容、依据和影响 |

概念关系图和实例关系图分开：前者展示“投诉关联楼栋”这类定义，后者展示某条投诉具体关联哪栋楼。用户从一个对象展开邻居，首轮不渲染全企业的密集网络图。

左侧保留企业空间、任务和成果入口；企业理解、来源、本体、对象、报告可独立打开。它们是同一对话工作的不同查看入口，首次使用不要求用户先学习一套后台导航。

## 8. 用热力公司的连续对话检查设计

以下是拟定行为示例，不是实际运行记录；示例不预填统计结果，也不代表已采用任何本体。

| 用户或事件 | Agent 应有的行为与示例表达 | 可检查成果 |
|---|---|---|
| “我们是一家热力公司，想建立企业大脑。” | “先围绕一个实际问题建立。你主要负责哪块业务，目前最想改善什么？” | 当前任务：明确首个目标；企业理解初稿仅登记用户提供的信息 |
| “我负责客服。经常显示已办结，但居民后来又说不热。”同时上传公司说明、规则和投诉表 | 先读三份资料，保存“投诉处理复盘”的目标；若现行规则已明确办结含义，不再让用户重复定义。指出投诉表能看处理状态，但判断供暖改善还需相关证据 | 企业理解、来源及接入摘要；待补充的回访/测温/维修资料与用途 |
| 用户补充相关资料 | 检查身份与时间，提出投诉、楼栋、回访等任务需要的最小概念；“这里分别保留处理状态和恢复证据。没有恢复证据时显示未知。”如存在身份歧义，集中提出那个具体问题 | 概念卡、关系、映射依据、未解析记录及候选实例 |
| 用户采用已展示的具体本体版本，检查通过 | 保存采用记录，提供对应业务类型和对象；不是把一段聊天文本当成已生效接口 | 当前定义版本与可操作对象；草稿和正式视图可辨识 |
| “用这些资料，列出已办结但仍缺恢复证据的投诉。” | 固定资料范围与时点，发现投诉类型，沿楼栋、回访等关系调查，调用已实现的证据判断方法；缺失关联单列。“以下是现有资料中的证据缺口，不能据此断定仍未恢复。” | 短报告、对象与来源证据、未解析范围；该报告任务完成 |
| “这条回访漏了，补进去。” | 登记新来源，按既定规则更新相关事实，说明影响的投诉与旧报告。如果用户同时要求重出报告，则直接做；否则标记原报告有新资料，展示更新入口 | 新事实版本与变更记录，旧报告及原证据保留 |
| 重新打开后问“再按同样口径看一下现在的情况。” | 沿用已采用定义，用新资料版本执行，不重复建企业、不重问已确定语义 | 引用同一口径版本的新报告，能解释与旧报告的差异 |

两个分支也必须说得通：资料解析失败时先保留原件和错误，不能生成“接入成功”的摘要；用户暂时不给回访资料时，可以完成一份“当前证据缺口说明”，但不能把原本要求的“确认哪些已恢复”标为完成。只有用户接受了交付范围的调整，才按新目标结束任务。

本体演变另用确实改变概念、关系成立条件或统计定义的资料验证。补充回访通常只是事实更新，不能当作本体已经演变的证据。

## 9. 完成条件与 MVP 验证

### 9.1 什么算完成一项任务

任务开始时确定适当的交付条件，结束前逐项检查：成果已保存或有可读取的既有成果引用；依据、数据范围与未决项已交代；必要的程序检查已通过；用户要求的交付已经完成。Agent 不能为了结束运行自行降低目标。

| 当前任务 | 完成条件 |
|---|---|
| 建立企业理解初稿 | 企业业务、当前目标及相关已知内容已保存；未知内容可见，不要求补齐所有企业字段 |
| 接入一份资料 | 原件已登记、所需内容解析可读、来源范围和限制已说明；只保存文件但解析失败算部分完成 |
| 设计本体候选 | 目标所需的概念/关系/口径及映射有依据、检查和实例预览；歧义明确保留。候选交付不等于正式采用 |
| 让业务模型可用 | 具体候选已获采用决定并通过检查，实际形成可查询的对象视图；等待决定时任务待补充 |
| 生成报告 | 针对约定问题和范围，有实际查询/计算结果、证据及限制。交付允许判断现有证据是否支持结论时，“不足以确定”可为结论；若约定必须完成具体核实，则只交付部分说明并保持待补充，范围调整须由用户接受 |
| 更新记忆 | 请求范围内的新事实或修订已保存、影响已说明；需要决定的部分仍待补充，旧成果保留原依据 |

### 9.2 如何检验 Agent 设计是否成立

沿已约定的“用户任务 → 实际工具执行 → 成果/证据读取 → 保存并重新打开”公共边界检查。先评审第 8 节的行为，再在实现后用同一条热力体验真实演示：

1. 从空白对话或直接上传都能启动，不重复询问资料已明确的信息。
2. 能按当前缺口查证、提问或行动；每次提问都有明确用途，普通保存无需层层确认。
3. 保存后的企业理解、来源与未决项可重开；停止和继续不会把旧行动重复写入。
4. 业务调查实际使用本体决定的类型/对象接口，展开至少两种关系，组合一次有明确口径的方法并取证；前端看到相同对象和版本。
5. 热力案例保持“办结不等于恢复”，未知与未解析单列，样例不冒充全量，候选不伪装成已采用定义。
6. 一次纠正或资料更新后，下一项任务复用有效记忆；能说明新旧结果为何变化，旧报告可回查。
7. 解析失败、工具失败、取消、重复请求和版本过期时，状态与实际成果一致；不因一句成功回复就通过验收。

最小实验要观察的价值是：**第一次整理的语义能被第二次任务复用，用户的纠正能影响后续行为，同时证据仍可检查。** 展示对话、对象调用和成果差异即可先判断这条路径是否跑通；一次成功体验不证明普遍准确率或本体的必要性，因果比较仍留给后续同任务对照。

### 9.3 当前阶段与后续边界

当前已形成行为规格、[Agent 设计方案](AGENT_BLUEPRINT.md)及 FEATURE_003 设计块，包含主 Agent 配置、组件和应用契约。后续据此安排“理解与首资料保存/重开”，以及“本体对象组合调查/报告/更新”的体验；本轮仅交付设计，实现票保持未完成。

一个主 Agent、一个企业、少量来源和一条业务链足够开始验证。本体对象组合属于首轮 MVP 核心范围；完整 NOOA 框架复刻、通用代码执行平台、图数据库、多 Agent 编排、全天候维护、通用连接器平台及大规模评测保留为后续范围。

|---|---|

| CodeAct 在方法调用的执行环境中传递实际 Python 对象并保留中间值；见[实现](https://github.com/NVIDIA-NeMo/labs-OO-Agents/blob/e137e1b5eee3f36ad0bba08cea0931aa292563a4/src/nooa/strategies/codeact.py) | 首轮验证本体对象的方法组合和中间结果复用；执行进程中可持有真实对象/代理，跨进程仍传稳定引用与有界结果。不把引用传输声称为跨进程零序列化 |
| 默认上下文与持久化需要区分；可选记忆包提供 SQLite、记忆 UUID、关系和更新能力；见[上下文寿命](https://github.com/NVIDIA-NeMo/labs-OO-Agents/blob/e137e1b5eee3f36ad0bba08cea0931aa292563a4/docs/concepts/prompts-and-context.md#lifetime-persistence-and-memory)和[记忆包](https://github.com/NVIDIA-NeMo/labs-OO-Agents/blob/e137e1b5eee3f36ad0bba08cea0931aa292563a4/packages/nooa-memory/src/nooa_memory/README.md) | 本项目自行维护正式企业资产及证据/定义版本。NOOA 有通用记忆能力，但企业身份对齐、指标口径和本体采用流程仍要由产品提供 |

首轮保留 NOOA 对象环境与组合执行的关键体验，先用一个小型执行边界验证。KodaX 负责模型循环，对象执行器持有企业对象/代理、执行方法组合并返回结果；NOOA 是否有可直接复用的独立组件仍需验证，不另启动一套相互嵌套的模型循环。采用该设计不能直接证明准确率或成本收益。

**对象执行适配仍待验证：**前述 SDK 接口可承载宿主能力，但尚未证明能直接操作 NOOA 的 Python live objects。推荐先验证 KodaX → 会话内对象执行器 → 企业对象代理这一边界，实例/中间结果留在执行器内；Node 与 Python 之间传请求、稳定引用及有界结果。执行器只开放当前企业方法，代码执行需要实际隔离，原始数据库连接与凭据不能直接暴露；单靠提示词、类型或 AST 检查不能视为隔离完成。此项是拟定接法，尚未实现。

**实现时特别检查：**

- inline 不能使用 `runtime.hostTools.register`，该接口属于 shared daemon client；选定的进程内 `extensionRuntime` 路径已存在，无须为首轮增加 daemon。
- 不把 `beforeToolExecute` 回调作为唯一门禁：部分权限模式会提前返回。首轮测试直接伪造 `bash` 及借 `tool_call` 转发都不能越过有效工具范围，并检查没有读取评测与未来资料。
- 工具 schema、SDK verifier 与本体语义验证各有边界；关键业务检查必须在 DataEngine 的保存方法内部执行。
- 首次打开若凭据不可用，展示设置入口和真实错误；模型已可用则直接开始企业理解。API Key 不作为 Agent 的提问内容。

## 12. 技术参考：本体对象运行时的三层边界

“本体作为对象”不是把每一行数据都实例化成一个 Python 类，也不是让模型直接读取数据库。这里指的是：本体的语义定义经过一个对象适配层，成为 Agent 可以发现和调用的业务对象接口。

```mermaid
flowchart LR
  A[本体定义层<br/>概念·关系·口径·约束·证据] --> B[对象运行时层<br/>类型·实例代理·关系方法·语义函数]
  B --> C[KodaX 执行层<br/>Session·Run·Model·Events]
  C --> D[用户任务与报告]
  B <--> E[企业存储<br/>来源·对象·版本·变更]
```

| 层 | 负责什么 | 不负责什么 |
|---|---|---|
| 本体定义层 | 规定“换热站是什么”“投诉如何关联楼栋”“办结率如何计算”，带身份、时间、证据和版本 | 不直接承担模型对话或一次查询的运行状态 |
| 对象运行时层 | 将已采用本体解释为类型、实例、关系访问、语义方法和证据入口；按需读取并执行检查 | 不自行决定有争议的业务定义，不把候选自动发布成正式模型 |
| KodaX 执行层 | 提供模型、会话、循环、工具调用、事件、停止和运行记录 | 不定义企业概念、身份规则或指标口径 |
| 企业存储 | 持久保存原件、对象快照、候选、报告、变更及依据 | 不把聊天摘要当作唯一长期知识，不替 Agent 判断语义 |

### 对象运行时的最小形状

首轮可以用通用代理承载不同本体类型，而不为每个数据表或每条记录生成代码：

```text
OntologyType
  describe() -> definition, fields, relations, methods, version
  get(id, as_of) -> EntityRef

EntityRef<T>
  fields(view) -> typed values + provenance
  related(relation, page) -> ObjectSetRef<U>
  evidence() -> EvidenceSet
  call(method, args) -> TypedResult + evidence + version

ObjectSetRef<T>
  page(cursor) -> items + total + truncation
  filter(condition) -> ObjectSetRef<T>
  aggregate(metric) -> MetricResult + evidence
```

这些是 DataEngine 的领域边界示意，不是 KodaX 或 NOOA 的现成接口。对模型显示的是命名类型、简短说明和可调用方法；完整数据留在运行时。`EntityRef` 可以在一次对象执行中作为惰性代理持有，跨会话或跨进程传递时使用稳定 ID、类型、版本和快照引用。

### 热力案例的最小对象链

首轮对象链只需覆盖一个可解释任务：

```text
Enterprise("chengchuan-heating")
  → Station("Z01")
  → served_buildings()
  → Building("SY-03")
  → related_tickets(window)
  → Ticket("CS-009")
  → callbacks(), work_orders(), measurements(), evidence()
  → recovery_evidence_status()
```

这里的 `recovery_evidence_status()` 不是模型根据名称自由发挥的函数，而是绑定本体约束与现行规则的确定性业务方法：客服办结、维修完成、站点读数、入户测温和居民回访分别返回，缺失或范围不足返回未知/缺口。Agent 负责解释为什么这些证据支持或不支持结论，并可提出本体或映射候选的修改。

### 为什么这种结合可行

本体本来就包含类型、属性、关系、规则和约束；NOOA harness 擅长把对象状态、类型化方法、按需发现和程序控制暴露给模型。因此本体可以成为 Agent 的业务 API，Agent 不必每次面对原始表格重新猜关系。关键是增加一个“本体 → 对象接口”的编译/解释层，将数据定义转换为运行时可执行的对象能力。

这会带来一个可验证的产品主张：**本体不是只供人查看的图，而是决定 Agent 可以如何理解、访问和组合企业数据的运行环境。** 这个主张可以用热力的一条跨源记录链实际检验。

### 不能直接拼接的地方

按前述已核对的源码版本，KodaX 是 TypeScript/Node 运行时，NOOA 的 live-object CodeAct 是 Python 进程内语义；两者没有被核实为可以直接共享同一个 live object。行为设计评审后，接入验证需遵循以下边界：

1. KodaX 继续作为唯一模型/会话运行底座。
2. DataEngine 实现本体对象适配器，并通过 KodaX 的 run-scoped extension 接口暴露对象能力。
3. 若采用独立对象执行器，由它持有代理和中间结果；跨 Node/Python 边界只传稳定引用、结构化参数和有界结果。
4. CodeAct 与受限组合接口都是待验证方案，以能否完成第 8 节对象调查、保留状态和证据为依据。本轮不预先排除 CodeAct，也不将其视为已经选定；若采用代码执行，需要真实隔离，调用范围仍为本体对象方法。

这里借鉴 NOOA 的 harness 设计原则，尚未把 NOOA Python Runtime 嵌入 KodaX。若选用 Python Worker，进程生命周期、协议、权限、对象失效和调试边界需要在接入方案中具体说明；不能因它们尚未验证，就把本体对象环境收缩为仅查询 JSON 的聊天工具。
