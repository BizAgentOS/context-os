# 产品目标

## 产品定位

**DataEngine 是企业记忆引擎：以本体组织企业信息、数据和业务对象，通过 Agent 的协助创建和维护企业级记忆。**

**本体 + KodaX + NOOA 式对象 harness 共同构成 DataEngine：**本体描述企业语义，harness 将概念、实例、关系和业务方法组成 Agent 的操作环境，KodaX SDK 提供执行底座。

用户通过底部输入框逐步建立企业理解、连接企业数据源的 API 或 MCP、构建本体与对象，再管理外部应用对企业记忆的访问。已经形成的企业记忆直接呈现在画布上；对话是操作入口，旧对话逐渐淡出，企业内容持续保留。当前产品不设置传统 Agent 的任务列表、历史聊天窗或多会话导航。具体交互见[企业记忆画布](CANVAS_DESIGN.md)。

底层保留企业语义数据引擎的定位：将业务系统、文档与业务 Agent 产生的数据组织为可追溯、可计算、可复用的数据资产，供产品内任务和外部 Agent 使用。

## 企业记忆包括什么

- 数据源的接口能力、访问范围、映射与来源引用，以及读取时可取得的时间和版本信息。
- 企业目标、职责、业务流程与已确认的理解。
- 业务概念、关系、口径和可执行的映射/计算规则。
- 基于来源按需读取的业务对象视图，以及已确认事实、证据引用与记忆变更记录。

报告用于使用和检查这些资产；报告中的推测与未经确认的聊天内容不自动成为企业事实。

## 数据连接原则

**原始业务数据留在企业原系统。** 第二页连接来源侧 API 或 MCP，按授权按需读取结构、记录和资料；DataEngine 保存企业理解、本体定义、来源能力、映射和引用，不默认整体复制远端数据建立另一套资料库。Agent 基于实际读到的内容提出定义与映射，未经读取和检查的内容不能当作已知事实。

第二页是 **企业数据源 → DataEngine**；第四页是 **DataEngine 的企业记忆 → 第三方 Agent / 应用**。两侧都可使用 API 或 MCP，但访问凭据、权限和用途分别管理。

业务数据在源系统持续维护。本体含义和访问范围的变化仍需检查与确认；是否缓存、保留快照或采用显式发布，以及更新何时对外可见，留待来源连接器设计，不承诺所有查询自动实时或远端历史永久可回放。当前上传文件和热力样本是已实现的实验输入；来源侧 API/MCP 连接器尚未实现，第四页已有的对外服务不等于完成来源接入。

## 要解决的问题

1. 同一个人、站点、设备或项目，在不同系统里有不同编号和名称。
2. 同一个业务术语可能对应不同口径，Agent 每次临时解释，结果不一致。
3. 原始材料混合了当前事实、旧记录和推测，结论难以核对。
4. 新数据与业务变化出现后，原有映射、定义和查询容易失效。
5. 多个 Agent 重复整理和理解相同材料，改进难以复用。

## 希望形成的能力

- Agent 主动了解企业、整理可修改的企业理解，并引导连接来源 API/MCP、检查实际可读内容。
- 用稳定身份组织企业对象，连接属性、关系、状态、历史和证据。
- 将业务口径变成明确的定义，并由程序执行查询与计算。
- 通过对象接口、MCP 和按任务整理的上下文提供数据。
- 登记消费方，管理允许读取的对象与字段，记录实际访问并支持撤销；权限在服务端执行。
- 由内部 Agent 调查语义问题并提出修改，经检查后更新本体。
- 让用户查看来源、本体、对象与变更，纠正业务含义。
- 基于企业记忆回答具体问题、生成简易报告，并在后续任务中复用已经检查的理解。

## 产品边界

DataEngine 的主要工作是建设和维护企业记忆。当前包含企业认知、数据来源、本体与对象、连接四个页面。第四页在本体采用后解锁，管理谁通过 API 调用、能读取哪些字段和关系、实际读了什么，并支持停用访问，见[连接与访问治理](DATA_CONSUMPTION_DESIGN.md)。消费授权由用户确认，权限由服务端逐次执行；管理凭据和调用方凭据独立。报告和记忆更新专页本轮移出主流程；复杂业务执行仍可由外部 Agent 或业务应用完成。

主 Agent 基于 KodaX Runtime，在由本体定义的 NOOA 式对象环境中访问、计算、查证并提出修订，串起企业理解、接入、辅助建模、报告与维护。关键语义选择可审查，确定性加工与计算由程序执行；对外消费使用稳定的数据接口。Runtime 接入状态以实际实现为准。
